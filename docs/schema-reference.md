# Schema reference (`nos-proto`)

Developer reference for the config tree types in `proto/src/schema/`, organised by the pattern each type exemplifies. Read it before adding a section that looks like one of these. The field lists themselves live in the `#[cli]` attributes and `///` comments in the source; this page records the design decisions and cross-validations behind them. Maintenance rules for the crate are in [`proto/CLAUDE.md`](../proto/CLAUDE.md); the wire protocols are in [IPC protocols](ipc-protocols.md).

## Config singletons and `BroadcastDomain`

- Config tree types: `Config` (incl. the singleton `Config.lldp: LldpSettings` — system-wide LLDP timers/management address, diffed field-level via `ConfigDiff.lldp`/`DiffScope::Lldp` rather than as a keyed `SectionDiff` list, since there is only one; `Interface.lldp_destination: LldpDestination` is the per-interface half; the singleton `Config.logging: LoggingSettings` holds `syslog: Vec<SyslogServer>`, the remote syslog collectors `nos-logd` exports to — `name`/`address`/`port`/`transport` (`Udp`|`Tcp`|`Tls`, the last with a `tls: SyslogTls` block — trust anchor xor fingerprint, server name, `allow_tls12`; `parse_fingerprint` is the pure format check)/`routing_table`/`level`/`facility`, validated by garde (unique names, unicast address, port ≥ 1, an existing routing table) and edited by `LoggingOp`, diffed field-level via `ConfigDiff.logging`/`DiffScope::Logging`; `LogLevel` derives `Cli` so `level` is settable), `BgpInstance`, `BgpPeerGroup`, `BgpPeer`, `RoutingTable`, `StaticRoutingInstance`, `StaticRoute`, `Interface`, `Subinterface`, `BroadcastDomain` (whose `vni`/`rd`/`route_targets_import`/`route_targets_export`/`vtep_source`/`mac_redistribute`/`arp_redistribute`/`connected_redistribute`/`neigh_suppress` are the EVPN/VXLAN config `nos-fdbd` acts on: all require a `vni`, and `mac_redistribute` — the BGP instance named on `redistribute from mac to bgp <instance>` — also an `rd` and a `vtep_source`; the diff covers every one, `vni` being the label the watchdog's `claim_label` keys on). Derived `garde::Validate` for commit-time validation. `BroadcastDomain.addresses`/`routing_table` are the same flat `Interface`-loopback shape (no tag concept applies to a domain's own bridge) making the domain's bridge device an SVI, independent of whatever `SwitchingProfile` members enslave into it — validated by the same `unique_addresses`/`routing_table_reference_valid` helpers `Interface`/`Subinterface` use, promoted to `validators` once a third schema type needed them.

## Nesting one level under a parent

- `BgpPeerGroup`/`BgpPeer` nest one level under `BgpInstance`, showing the pattern for a section nested under another section rather than directly under `Config`; `StaticRoute` nests one level under `StaticRoutingInstance` the same way.

## EVPN IP-VRF on a routing table

- `RoutingTable.evpn: RoutingTableEvpn` (`l3_vni`/`rd`/`route_targets_import`/`route_targets_export`/`vtep_source`/`bgp_instance`, every one optional; `#[serde(default)]`) makes the table an EVPN IP-VRF acted on by its `nos-ribd`: a plain struct rather than an `Option<…>` so the CLI reaches each field on its own (an optional struct is set in one line, which can't hold its lists), validated by `routing_table::valid_table_evpn` (wired on `Config.routing_tables`): nothing but an `l3_vni` turns it on, which then needs an RD, an export RT, a `vtep_source` and an existing `bgp_instance` that isn't the table's own, and an L3 VNI no other table or `BroadcastDomain.vni` uses.

## L3VPN on a routing table

- `RoutingTable.vpn: RoutingTableVpn` (`rd`/`route_targets_import`/`route_targets_export`/`bgp_instance`/`label`/`site_of_origin`; `#[serde(default)]`) is the table's RFC 4364 VPN identity. Same plain-struct shape as `evpn`; `nos-ribd` exports and programs it, `nos-bgpd` imports it ([L3VPN](protocols/bgp.md#l3vpn-vpnv4vpnv6)).
- `routing_table::valid_table_vpn` (wired on `Config.routing_tables`): an all-default `vpn` is off. Otherwise it needs an `rd`, every RT valid (`asn:nn` or `a.b.c.d:nn`), at least one export RT (import may be empty, an export-only spoke), and an existing `bgp_instance` that isn't the table's own.
- `label` is optional, 16-1048575 (0-15 are reserved by RFC 3032) and used by no other table. `site_of_origin` is optional and well-formed like an RT (it may equal one).
- The RD is compared as its 8 encoded bytes against every other table's `vpn.rd` and `evpn.rd` (an RD names one VRF, RFC 4364 section 4.2; EVPN Type-5 shares the namespace). A table may reuse its own `evpn.rd` as `vpn.rd`.
- `AddressFamily` gained `Vpnv4Unicast` (CLI `vpnv4`, AFI 1 / SAFI 128) and `Vpnv6Unicast` (`vpnv6`, AFI 2 / SAFI 128), appended after `Ipv6Flowspec` (postcard indexes by position). `BgpMaximumPrefix` gained `vpnv4`/`vpnv6`. `nos-bgpd` negotiates and carries them.
- `AddressFamily::RtConstraint` (CLI `rt-constraint`, RFC 4684, AFI 1 / SAFI 132) is appended last (postcard index 7); `BgpMaximumPrefix.rt_constraint` caps its membership routes. Commit validation: a group that enables it must also enable `vpnv4`, `vpnv6` or `l2vpn-evpn`.

## `redistribute`: a list keyed by `to`

- `RoutingTable.redistribute: Vec<Redistribute>` is a list keyed by `to` (`#[cli(key)]`, `"to"` in `config_path::ELEMENT_KEYS`, whose element lookup is case-insensitive because the enum serialises as `Ospf`): one rule per target, so static routes can feed BGP, OSPF and OSPFv3 at once (`valid_redistribute_rules` refuses a duplicate target). `RoutingTableOp::SetRedistribute` upserts by `to`, `ClearRedistribute { name, to }` removes one rule. A `config.yaml` written when the field was an `Option` (null or one object) still loads: `deserialize_redistribute` accepts null/object/list in human-readable formats only, postcard being not self-describing. The CLI form is `set routing-table <t> redistribute <target>` then `policy`/`metric`/`metric-type` one per line (the old `from static to <target>` is not a key-token rewrite the derive can express).

## References by name, with and without ownership

- `RoutingTable` shows the pattern for a section that only *references* other top-level sections by name (`bgp_instance`, `static_routing_instance`) rather than owning them, with an ownership constraint (at most one table may claim a given instance); `Subinterface.routing_table` is the same by-name reference pattern but without that ownership constraint — many interfaces/subinterfaces may share one routing table (which doubles as a VRF).
- `BfdProfile` (`Config.bfd_profiles`) is referenced by an optional `bfd: Option<String>` on `BgpPeerGroup`, `OspfProfile`, `Ospfv3Profile` and `StaticRoute`, all checked by `validators::bfd_reference_valid`. `Subinterface.bfd_unsolicited` (RFC 9468, `#[serde(default)]`) names one the same way and needs a `routing_table` on the same subinterface. Deleting a profile needs no edit-time check: every dangling reference fails at commit under its own path. `BfdProfile.mode` `sbfd` makes the session a Seamless BFD initiator and excludes `echo_mode`, `padded_pdu_size` and `auth`; `sbfd_remote_discriminator` is an IPv4 address (the 32 bits) and not 0.0.0.0; a static route to an IPv6 gateway with an `sbfd` profile needs it. `Config.sbfd_reflector` (`discriminators`, `allow_from`) is the reflector: discriminators are IPv4-written, not 0.0.0.0 and unique. See [BFD profiles](protocols/bfd.md).
- `Config.spanning_tree` (`SpanningTree`, `#[serde(default)]`, a singleton like `sbfd_reflector`) holds the bridge-wide STP parameters; `Config.stp_port_profiles` (`StpPortProfile`) are named port settings referenced by an optional `stp_port_profile` on `Interface` and `PortAggregate` (`validators::stp_port_profile_reference_valid`). `BroadcastDomain` gains optional `stp_instance`/`stp_priority`/`stp_hello_time`/`stp_max_age`/`stp_forward_delay` and `SwitchingProfileMember` `stp_cost`/`stp_priority`. Commit checks (timer relations, priorities, per-VLAN VID uniqueness for `mstp`/`rapid-pvst`, bond members, the ESI guard rule in `valid_port_aggregates`) are in `schema/spanning_tree.rs`; the list is in [Spanning tree](protocols/stp.md#commit-checks). `StpPortProfileOp::{Ensure, Delete}` is the only op; fields are edited by path. `ConfigDiff` has `spanning_tree` (field-level) and `stp_port_profiles` with their own `DiffScope`s. Nothing consumes any of it until `nos-stpd`.

## Loopbacks by name prefix, and the flat vs subinterface L3 split

- `Interface` has no "kind" field to mark a loopback interface: an `Interface.name` starting with `LOOPBACK_PREFIX` (`loopback-`, e.g. `loopback-rt1`) is a loopback for the routing table named by the rest of the string (`loopback_table_name`) — this is checked as part of `name`'s own validator (which also rejects a literal `.`, reserved for `nos-cli`'s `<interface>.<tag>` subinterface addressing), which also means `name`'s existing global uniqueness already guarantees at most one loopback per routing table, for free. A loopback interface keeps its L3 config flat on `Interface.addresses`/`routing_table` (unchanged from before subinterfaces existed — a loopback has no VLAN/dot1q concept); every other (physical) interface's L3 config lives entirely under `Interface.subinterfaces: Vec<Subinterface>` instead, `tag == 0` being the untagged/native case (what those same flat fields held before this split) and `1..=4094` a real 802.1q VLAN tag — `valid_addressing_split` (`schema::interface`) enforces the split (a loopback must have no `subinterfaces`; a physical interface must have empty flat `addresses` and no flat `routing_table`), and `valid_subinterface_and_switching_profile_tags` enforces that a `Subinterface`'s tag and a `switching_profile` member's tag (`Untagged`->0, `Dot1q(n)`->n) are disjoint on the same interface — Linux only allows one master device per link (physical or per-tag sub-link), and an L2 switching-profile member wants that link's master to be a bridge while an L3 subinterface wants it to be a VRF. `Interface.addresses`/`Subinterface.addresses` (`Vec<InterfaceAddress>`, `{ address: IpNet, label: Option<String> }`) is a list of small structs rather than `Vec<IpNet>` precisely because one field (`label`) needs to travel with each address rather than the whole list — `label` is stored from commit time onward but not yet applied to any kernel by any driver.

## Derived read-only mirror

- `BgpInstance.routing_table` shows a different pattern: a **derived, read-only mirror** of `RoutingTable.bgp_instance` (the other direction of the same association), `#[garde(skip)]` and never touched by any `BgpInstanceOp` — see `crate::derive::sync_routing_table_refs`, called by `nos-config` on load and on every commit, never on a transaction's in-progress config.

## Session authentication

- `BgpPeerGroup.auth: Option<BgpAuth>` is transport authentication (RFC 2385 TCP MD5 or RFC 5925 TCP-AO, `BgpAuth::Md5`/`BgpAuth::Ao{keys: Vec<BgpAoKey>}`, mutually exclusive) — holding admin keystore labels (`key_ref`), never the secret (#508), validated by a single `custom` closure (`valid_auth(auth, &Config)`, shared with `RpkiCache.auth`) covering both variants (the label must exist and its secret be 1 to 80 bytes, which also makes deleting a still-referenced admin key fail the commit; unique `send_id`, exactly one `is_current` key) since garde has no per-enum-variant validation. `BgpAoKey.exclude_options` (`#[serde(default)]`) is RFC 5925 §5.2's MAC-coverage choice (`TCP_AO_KEYF_EXCLUDE_OPT`) — both peers must agree, or authentication fails; unvalidated by `valid_auth` (an unconstrained bool). `OspfProfile.auth: Option<OspfAuth>` (RFC 2328 Appendix D) and `Ospfv3Profile.auth: Option<Vec<OspfCryptoKey>>` (RFC 7166, crypto only so no enum) share `OspfCryptoKey`, whose `key_id: u16` is RFC 7166's 16-bit SA ID — `ospf_profile::valid_profile_timers` caps a classic (non-RFC 7474) OSPFv2 key at 255, the one-octet wire field, and `ospfv3_profile::valid_auth` rejects `Md5`.
- `BgpInstance.bmp_stations: Vec<BmpStation>` (`#[serde(default)]`, #878) are the RFC 7854 BMP collectors `nos-bgpd` dials, keyed by `name` (`name_charset`, unique). `BmpStation.port` is mandatory: no serde default (a REST body without it is rejected), `Default` gives 0 and `valid_bmp_stations` rejects 0, an unspecified address and duplicate names. `BmpStation.monitor` (`BmpMonitor`: `post-policy`, `pre-policy`, `both` default, `#[serde(default)]`, #864) picks the Route Monitoring view; `BmpStation.statistics_interval` (`Option<u32>`, 1..=86400 seconds, unset = no Statistics Reports, `#[serde(default)]`, #864); `BmpStation.monitor_out` (`BmpMonitorOut`: `none` default, `pre-policy`, `post-policy`, `both`, `#[serde(default)]`, #867) picks the RFC 8671 Adj-RIB-Out views, variant order is the postcard index. Ops: `SetBmpStation` (upsert by name), `RemoveBmpStation`.

## Admin keystore (`Config.admin`, #383)

- `Admin { keys: Vec<AdminKey> }`, `AdminKey { label, secret }`: a label (1-64 characters, the object-name charset, unique) and a secret (1-80 bytes, `#[cli(secret)]`, never the text `<hidden>`). It is the one place a secret lives; other sections store only the label (BGP MD5/TCP-AO and RPKI cache auth do since #508; OSPF since #509 and `BfdAuth.key` since #510).
- `Config.admin` is last in `Config` and `#[serde(default)]`: a `config.yaml` saved before it loads with no keys.
- `AdminOp::SetKey` upserts, `DeleteKey` fails with `OpError::AdminKeyNotFound`. Both `Debug` impls print `<hidden>`.
- `Config::key(label)` resolves a label for the daemons; `Config::redacted()` is the config as JSON with every `#[cli(secret)]` field (admin secrets and user password hashes) replaced by `<hidden>`, walked from `cli::root()`, so a new secret field is covered by declaring it `secret`.
- `ConfigOp::kind()` is the variant name without payload; `nos-configd` logs that instead of `?op`.
- The diff has an `admin` slot (`DiffScope::Admin`): a changed secret shows `<hidden>` then `<changed>`.

## Two-level nesting and globally unique profile names

- `OspfInstance.areas: Vec<OspfArea>` nests one level under `OspfInstance` (keyed by dotted-quad `area_id`, unique only within the owning instance — never referenced from outside `OspfInstance`, so plain per-parent uniqueness, unlike the next type); `OspfArea.profiles: Vec<OspfProfile>` nests a *second* level under that (keyed by `name`), the first two-level section nesting in this schema. `OspfProfile.name` is validated **globally** unique across every instance's every area (`ospf_profile::unique_name`, flattening `ospf_instances -> areas -> profiles`) rather than per-area, mirroring `BgpPeerGroup.name`'s own cross-instance uniqueness one level shallower — needed because `Interface`/`Subinterface`/`BroadcastDomain.ospf_profile` reference a profile by bare name with no instance/area qualifier, via the shared `ospf_profile_reference_valid` validator (same flattening lookup, the reference-side counterpart of `unique_name`). Each of those three `ospf_profile` fields also requires a `routing_table` set on that same attach point (`valid_addressing_split`'s loopback-`Interface` case, a `Subinterface`-list closure, and `broadcast_domain::valid_broadcast_domains` respectively) — OSPF has no meaning without an L3/VRF context, the same reasoning as `routing_table_reference_valid` itself.

## `PortAggregate`

- `PortAggregate` is a named Linux bonding device (`PortAggregateMode::Xor` static aggregation, or `Lacp` — membership negotiated by `nos-lacpd` via real IEEE 802.1AX, see `lacp/CLAUDE.md`; `lacp_rate: LacpRate::{Slow, Fast}` only meaningful for `Lacp`, `#[serde(default)]` so pre-existing on-disk config still loads; `esi: Option<String>` is the EVPN Ethernet Segment Identifier — ten colon-hex bytes, not all-zero, unique across aggregates (`valid_esi`/`valid_port_aggregates`, parsed by `evpn_id::parse_esi`), acted on by `nos-fdbd`; `redundancy_mode: EsRedundancy::{AllActive, SingleActive}` (`#[serde(default)]`, all-active) is how the PEs sharing the ESI divide the traffic — `valid_port_aggregates` rejects single-active without an `esi`; `df_algorithm: DfAlgorithm::{Modulo, Hrw}` (`#[serde(default)]`, modulo) is the RFC 8584 DF election algorithm this PE asks for, likewise rejected without an `esi`; `bfd: Option<String>` (a `bfd-profile` name, `bfd_reference_valid`) and `bfd_peer: Option<IpAddr>` (both `#[serde(default)]`) gate each member's enslavement on a micro-BFD session — `valid_port_aggregates` rejects `bfd` without a `bfd_peer` or without an address of the peer's family on the tag-0 subinterface; `lacp_system_id: Option<String>` overrides `nos-lacpd`'s derived Actor System ID with a unicast MAC; `lacp_system_priority: Option<u16>` the Actor System Priority, `None` = 32768, with `Interface.lacp_port_priority: Option<u16>` its per-member counterpart — both `#[serde(default)]`, unvalidated, and also shown by `show lacp` via `LacpPortStatus`/`PortAggregateLacpSummary`) with the same config surface as a *physical* `Interface` (`switching_profile`/`mtu`/`subinterfaces` — no flat `addresses`/`routing_table`, since a bond is never a loopback; all its L3 config lives under `subinterfaces` exactly like a physical interface's does).

## LLDP flags on `Interface`

- `Interface.lldp_transmit`/`lldp_receive: bool` (both `#[serde(default)]` so pre-existing on-disk config still loads, `#[garde(skip)]` individually) enable `nos-lldpd`'s IEEE 802.1AB transmit/receive on that link independently; `valid_lldp_physical_only` (`schema::interface`, wired in `valid_interfaces`) rejects either flag on a `loopback-*` interface — a loopback has no wire to speak LLDP on. `InterfaceOp::SetLldpTransmit`/`SetLldpReceive` carry an `enabled: bool` rather than a `Set`/`Clear` pair, since a bool has no value to clear (`set` = `true`, `delete` = `false` in `nos-cli`).

## Port-aggregate membership

- `Interface.port_aggregate: Option<String>` makes an interface a bonded member by naming an aggregate, the same reference-by-name shape as `switching_profile`; `valid_port_aggregate_membership` (`schema::interface`) rejects a member interface that also carries a `switching_profile` or any `subinterfaces` — the same "one Linux master per link" reasoning as `valid_subinterface_and_switching_profile_tags`.

## Access lists (`Config.acls`, #540)

- `Acl { name, default_action, rules }` (`schema/acl.rs`): `default_action` defaults to `deny` (`AclAction::default`), `rules` is ordered and keyed by `name` (placed with #539's `first/last/before/after/move`). `nos-acld` (#541) compiles them to tc.
- `AclRule` fields all optional or off by default: `protocol` (`AclProtocol::{Tcp, Udp, Icmp, Icmpv6, Number(u8)}`), `source`/`destination` (`IpNet`), `source_port`/`destination_port` (`PortRange`), `established`, `icmp_type`/`icmp_code` (`u8`), `log`. There is no `counter` flag: tc counts every rule.
- `AclProtocol` and `PortRange` are custom text scalars (`80`, `1024-65535`, `tcp`, `89`): `Serialize`/`Deserialize` through one string and `CliValue::kind` = `Kind::Str`, so the grammar, `show config` and the diff need no new `Kind`. `6`, `17`, `1` and `58` parse to the named variants; `Number` of those is refused at commit.
- Commit checks (`acl::valid_rules`, one message per rule): mixed `source`/`destination` families, `icmp` with an IPv6 prefix and `icmpv6` with an IPv4 one, ports without `tcp`/`udp`, port 0 or `start > end`, `established` without `tcp`, `icmp-type`/`icmp-code` without `icmp`/`icmpv6`, `icmp-code` without `icmp-type`, duplicate rule names.
- Attach: `acl_in`/`acl_out: Option<String>` (words `acl in`/`acl out`) on `Interface`, `Subinterface` (also under a `PortAggregate`) and `PortAggregate`. `acl::valid_acl_references`, wired on `Config.acls`, refuses an unknown ACL, and an `Interface` ACL on a `loopback-*`, a bond member or a switching-profile port. A subinterface needs no extra check: those parents cannot have one. An interface or aggregate and its tag-0 subinterface are one kernel device, so they may not both set the same direction (`one_per_device`).
- Flowspec (#562): `flowspec: bool` (word `flowspec`, topic `InterfaceFlowspec`) on `Interface`, `Subinterface` and `PortAggregate`. `acl::flowspec_points` lists each flagged device with its table (a subinterface's `routing_table`, the tag-0 subinterface's for the parent); `acl::valid_flowspec_placements` (also on `Config.acls`) refuses a loopback, a bond member, a switching-profile port, both a parent and its tag-0 subinterface, no table, or a table no `BgpInstance` uses. `nos-acld` maps the points to instances (`plan::flowspec_devices`).
- The diff has an `acls` slot (`DiffScope::Acls`); a reorder of `acls` or of `Acl.rules` goes through the generic list path.

## The `cli` module (`#[derive(Cli)]`)

- The CLI's view of the schema (#109): `#[derive(Cli)]` (the `nos-proto-derive` crate) on every schema struct/enum implements `CliValue`, a static tree of `Node`/`Field`/`Kind`/`Variant` built from the real Rust field types. Every struct field **must** carry `#[cli(...)]` — `topic = <Topic>` (its CLI help, text in `nos-config`'s `docs.rs`), `key` (a list element's key, agreeing with `config_path::ELEMENT_KEYS`), or `hidden` (derived state) — or the crate doesn't compile, so a field can't be added without its CLI documentation. The same attribute carries `words = "…"` (today's CLI spelling, shown; the REST segment `config_path::field_segment` is always accepted too), `alias = "…"` (accepted, never shown), `sugar(word, with, topic)` (a word handled by a `schema/sugar.rs` function returning the field's new value or the canonical words it stands for — `md5-password`, `ao-key`, `crypto-key`, `shutdown <message>`, `orlonger`/`upto`, and a physical interface's L3 words meaning its untagged subinterface) and `sugar = "{a}.{b} => {a} subinterface {b}"` (a list-key rewrite: `eth0.100`). A struct needs `Default` (the starting point of a new element — `Ensure`'s placeholders) unless marked `#[cli(no_default)]`; an enum's `#[default]` variant is what `delete` resets a non-optional field to. `secret` marks a field `show config` prints as `<hidden>`, and `render = path` (a `RenderFn`, `schema/sugar.rs`) gives a sugar-only field its own `show config` lines (auth, `shutdown`). `cli::render` is the inverse of the grammar: it walks the tree over the config's JSON and writes the non-default fields in their CLI words (`render_root`/`render_at`), so `show config`/`show this` can't omit a field; `nos-cli`'s `config_grammar` and `format::render_config` are the consumers.

## `derive`

- `sync_routing_table_refs(config: &mut Config)` — recomputes every `BgpInstance.routing_table` from the authoritative `RoutingTable.bgp_instance` references. Pure and synchronous, like `ops/`'s `apply`/`diff/`'s `diff_*`; called by `nos-config`, never by a client.

## `validators`

- Generic reusable validation helpers (e.g. `unique_key_in`, `unique_addresses`, `routing_table_reference_valid` — the latter two shared by `Interface`, `Subinterface`, and `BroadcastDomain`, each of which validates its own `addresses`/`routing_table` fields with them). Validators that need to search *across* a nested collection (e.g. peer-group name uniqueness scoped globally, not per-instance), or check a cross-reference specific to one schema type (e.g. `RoutingTable.bgp_instance` naming an existing instance claimed by at most one table), live next to their owning schema type instead.
- Names of keyed lists are unique ignoring case, `-` and `_` (`unique_key_in`, the rule the selector uses, #633): a colliding pair (`pga`/`pg-a`) fails every commit, each member under its own field path, until one is renamed. No grandfathering of stored configs.

## `ops/`

- Section-scoped edit types applied to a transaction's in-progress config (e.g. `BgpInstanceOp`, `BgpPeerGroupOp`, `RoutingTableOp`, `InterfaceOp`, `SubinterfaceOp`), wrapped by `ConfigOp`. Never validated — only `garde` at commit time is. A nested section's `Op` variants carry the owning parent's key too (e.g. `BgpPeerGroupOp::SetRemoteAs { instance, name, .. }`, `StaticRouteOp::Set { instance, subnet, .. }`, `SubinterfaceOp::AddAddress { interface, tag, .. }`). `InterfaceOp::AddAddress`/`RemoveAddress` (and `SubinterfaceOp`'s own address variants) show the pattern for a field that's a plain list of scalars (not a keyed sub-collection like `StaticRoute`) — no `Ensure`/`Set` split, just direct add/remove; `AddAddress` upserts by `address` (a repeat call replaces an existing entry's `label` rather than duplicating the address), which is how a label is set, changed, or cleared. There is no dedicated op for marking an interface as a loopback — that's just `Ensure`-ing (or `Edit`-ing) one whose name happens to start with `loopback-`, per `schema::interface::LOOPBACK_PREFIX`. `SubinterfaceOp::AddAddress`/`SetRoutingTable` (unlike `InterfaceOp`'s own address/routing-table ops) cascade-create both the subinterface entry *and* its parent `Interface` if either is missing — `nos-cli`'s `edit interface eth0.100` followed by `set address ...` must work in one step, with no separate "create the subinterface" op. `BgpPeerGroupOp`'s auth variants (`SetMd5Auth`, `SetAoKey`/`RemoveAoKey`, `SetAoCurrentKey`/`SetAoRnextKey`, `ClearAuth`) show a keyed sub-collection nested *inside* one field of an already-nested section (`Vec<BgpAoKey>` inside `BgpPeerGroup.auth`) — `SetAoKey` upserts by `send_id` and starts a fresh list if `auth` wasn't already `Ao`; `SetAoCurrentKey`/`SetAoRnextKey` eagerly clear the flag on every other key in the list at apply time (rather than deferring "at most one" to commit-time validation), since that's cheap and unambiguous.

## `diff/`

- Structural config comparison, **generated** from the CLI tree (#116, `diff/generate.rs`): `diff_configs(base, candidate) -> ConfigDiff` (and `diff_values` on the JSON) walks both configs' JSON through `cli::root()`, so every non-hidden field is compared and a field can't exist without being diffed. A keyed list of structs is a `SectionDiff` (`header` = the field's CLI words + key, e.g. `bgp instance r1`, `peer-group g`; `name` = the key), nested ones in `subsections`; any other field is a `FieldDiff` labelled with its canonical CLI words, valued like `show config` (`unset` when absent, `<hidden>`/`<changed>` for a `secret`); a plain struct field (`lldp`, `logging`, `evpn`) is flattened to labels prefixed with its words. An `Added`/`Removed` section lists only fields that differ from the struct's `Default`. `diff/generate.rs::put` maps each `Config` field to its `ConfigDiff` slot (a test fails when a new `Config` field has none); `REST_API_LABEL`/`VNI_LABEL` are the labels `nos-watchdogd` keys on (a test pins them to the CLI words). `DiffScope` names one top-level `ConfigDiff` section; `ConfigDiff::scoped(&self, scopes)` returns a copy keeping only the requested sections, used by `SubscribeDiff` subscribers. `cli/tests/render.rs` mutates every field of a generated sample and requires each to appear in the diff.

## `config_path`

- URL-style addressing of a subsection of a `Config`'s JSON form: `get`/`set`/`remove` walkers over `serde_json::Value` (`["bgp-instance", "r1", "peer-group", "pg1"]`), shared by `nos-config` (`Request::SetTransactionPath`) and `nos-restd` (reads, and the generated `OpenAPI` paths). A segment is a kebab-case field name (tried as `x`/`xs`/`xes`/`xies`, so `community-alias` → `community_aliases`); a list field is followed by the element's key, found via `ELEMENT_KEYS` (fixed list — extend it if a new list section is identified by another field). `set_at(.., Option<&ListPosition>)` is `set` with an insert/move position (`First`/`Last`/`Before(key)`/`After(key)`; an unknown anchor is `NotFound` and changes nothing), and the config diff reports a reorder of a nested keyed list as a `<list> order` field (#539). `field_segment`/`key_field`/`field_matches` are the naming rules the OpenAPI generator uses, so spec and behaviour can't drift. The optional `openapi` cargo feature adds `utoipa::ToSchema` derives to the schema, diff and show-response types (`IpAddr`/`IpNet` fields need `schema(value_type = String)`, recursive `SectionDiff.subsections` needs `schema(no_recursion)`).

## `paths`

- `DEFAULT_CONFIG_SOCKET`/`DEFAULT_WATCHDOG_SOCKET`/`DEFAULT_PKI_DIR`/`DEFAULT_PKI_CA` — the two bootstrap socket defaults that stay fixed rather than being resolved via the broker.

## `evpn_id`

- Route Distinguisher / Route Target text (`asn:nn`, `a.b.c.d:nn`) ⇄ the 8-byte RD / `u64` extended community `nos-bgp` stores (`parse_rd`/`parse_rt`, and `parse_soo`/`soo_from_rt`: the same value with the Site of Origin subtype 0x03), used by commit-time validation and `nos-fdbd`; `ENCAP_VXLAN`; `Esi` + `parse_esi`/`format_esi`/`parse_mac`/`es_import_rt` (the RFC 7432 §7.6 ES-Import Route Target of an Ethernet Segment route), `esi_label_ext`/`parse_esi_label` (the §7.5 ESI Label community of a per-ES A-D route, whose flags octet carries the Single-Active bit), `df_election_ext`/`parse_df_election` (the RFC 8584 §2.2 DF Election community of a Type-4: DF Alg + the AC-DF capability bit), `router_mac_ext`/`parse_router_mac` (the RFC 9135 §8.1 Router's MAC community, type 0x06 subtype 0x03, of a Type-5), `vxlan_name` (`vx<vni>`, shared by `nos-fdbd`'s and `nos-ribd`'s VXLAN devices), `format_mac`, and `mac_mobility_ext`/`parse_mac_mobility` (the §7.7 MAC Mobility community — sequence number + sticky bit — a Type-2 route carries; see `bgp-internals.md`'s "EVPN" section).
