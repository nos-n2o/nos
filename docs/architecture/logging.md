# Log collection

Contributor-facing; moved from the root `CLAUDE.md` (#260). Operator view: [docs/README.md](../README.md).


Every daemon (`nos-configd`, each `nos-bgpd`/`nos-ribd` instance, `nos-interfaced`, `nos-watchdogd`) already logs via `tracing`; `nos-log-client` provides a second `tracing_subscriber::Layer` (`ForwardingLayer`) that each process installs alongside its existing `fmt` layer. It is a leaf crate depending only on `nos-proto`, so sharing it keeps the star dependency graph intact — no daemon gains a dependency on another daemon. Installing it is purely additive, so stdout/`docker logs` output is unaffected. The layer converts every `tracing::Event` into a `nos_proto::log::LogEntry` (timestamp, level, source identity, target, message, structured fields), pushes it onto a small bounded queue (evicting the oldest entry when full — logging must never block the caller), and a background task drains that queue into one long-lived `LogRequest::Push` connection to `nos-logd`, reconnecting on a fixed 1s delay like every other reconnect loop in this codebase.

`nos-logd` holds an in-memory, bounded ring buffer (`--capacity`, default 10,000 entries) behind `log::store::LogStore`, persisted to `--log-store-path` (default `/var/lib/nos/logd/entries.jsonl`, one JSON line per entry, compacted back down to `--capacity` lines once the file grows past twice that) so recent history survives a restart — the one daemon in this system with disk-backed state purely for its own sake, rather than for cross-restart identity like `nos-ribd`'s table registry. `nos_proto::log`'s `LogRequest`/`LogEvent` serve three request shapes on one socket (`--listen-socket`, default `/run/nos/log.sock`): `Push` (fire-and-forget, no reply, from every other daemon), `GetLogs { source, limit }` (`nos-cli`'s one-shot `show log [<source>]`), and `Tail { source }` (`nos-cli`'s `show log --follow`, replying once with the current buffer before streaming further `Line`s from a `tokio::sync::broadcast` channel until the client disconnects).

- A `GetLogs`/`Tail` reply is capped at `store::REPLY_BYTES` (16 MiB less 1 KiB of estimated entry size) so it always fits one IPC frame: past it the oldest matching entries are left out, the newest kept. With the 16 MiB ring this can only drop a few of the oldest entries; `show log`/`GET /v1/logs` need no change.


**Memory profiling `nos-logd` (#756/#757)**
- Live-heap bound: `cargo test -p nos-log --test resident -- --nocapture` runs a counting global allocator over REST-shaped entries (byte cap binding, 5x overfill) and asserts live heap <= 1.5 x `MAX_MEMORY_BYTES`; it also prints the transient peak of one `snapshot()` (`limit=20000`).
- dhat: `docker build --build-arg CARGO_FEATURES=nos-log/dhat-heap -t nos:local .`, then pass `--logd-arg=--profile-memory-out=/tmp/dhat-logd.json` to the watchdog; the report is written when `nos-logd` exits on SIGINT (load it in dh_view). The feature is off in every default and release build.
- Lab load: `cargo run -p nos-e2e -- up`, then `LOGD_MEM_ROUTES=20000 [LOGD_MEM_POLL=1] cargo run -p nos-e2e -- logd-mem`: sequential per-route `PUT`s into an uncommitted transaction on router-a, `VmRSS`/`VmHWM` sampled every 2000 requests and after an idle wait, then SIGINT to `nos-logd` and the dhat `t-gmax`/`t-end` totals. The dhat totals need the dhat image above; it is not a phase.
- The harness runs `nos-logd` with `--capacity=200000` (`router.rs`), so the 16 MiB byte cap, not the entry count, bounds the ring there; production defaults to 10,000.
- Process RSS is not bounded by the ring: with glibc's per-thread arenas the REST-request churn fragmented to 7-17x the live heap and never returned it. The watchdog therefore starts `nos-logd` with `MALLOC_ARENA_MAX=1` through `ProcessSpec::with_env` (#756; `nos-configd` gets the same since #776, every other child only the scrubbed allowlist), which kept RSS flat in the #757 measurements.
- Startup and compaction read only the last 20 MiB (`MAX_MEMORY_BYTES`) of `entries.jsonl` (`persistence::load_recent`), so a huge `--capacity` cannot spike the heap while seeding; compaction leaves at most that tail.
- Each recorded entry is clamped (`store::clamp_entry`, #640) to `MAX_ENTRY_BYTES` (64 KiB by `entry_size`): message cut at 16 KiB, at most 32 fields (key 128 B, value 1 KiB), source/target 256 B; cut text ends with `...[truncated]` and a warning is logged.
- `entries.jsonl` is also compacted once it passes `MAX_FILE_BYTES` (40 MiB, not configurable), not only on the line count; a larger file at startup is compacted on the first append.
- Shutdown (#679): `nos-logd` stops accepting, then signals `persistence::run` to close its receiver and write the queued entries (live connections keep `LogStore` clones, so the sender never drops); the flush is bounded to 5s from the signal, then the task is aborted. Entries pushed after the close are lost.
- `cargo run -p nos-e2e -- logd-memory-lab` (phase `logd-memory`, manual, not in CI): RSS at 20 000 `PUT`s within +50% or +50 MB of 10 000, idle RSS not above end-of-load (1 MiB slack), and the watchdog `starting process=nos-logd ... env=MALLOC_ARENA_MAX=1` line. `LOGD_MEM_ROUTER=b` points `logd-mem` at router-b; both log every `nos-*` daemon's RSS and the cgroup `memory.current`/`memory.max`.

`nos_log_client::install_panic_hook()` routes panics through the same layers (stderr and `nos-logd`) before aborting; the hook waits up to ~200 ms for the queue to drain (the panic line is the newest entry, so it is never the one evicted); best effort, an empty queue does not prove the bytes reached `nos-logd`. See [supervision](supervision.md).

- **Source is stamped by `nos-logd` from the pushing daemon's certificate** (`nos-<daemon>` plus `[<name>]` when the certificate has one: `nos-bgpd[r1]`, `nos-interfaced`); the `source` a client wrote in a `Push` is overwritten, so a daemon cannot pass itself off as another (#400).
- User-controlled strings (login names, transaction names) are logged Debug-escaped (`user="admin"`), so a newline or ANSI sequence in a name cannot forge a line.
