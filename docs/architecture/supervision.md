# Process supervision

Contributor-facing; moved from the root `CLAUDE.md` (#260). Operator view: [docs/README.md](../README.md).


`nos-watchdog` (binary `nos-watchdogd`) starts and supervises the other component processes as OS child processes, and is the container's entrypoint. It always runs exactly one supervised `nos-configd`. For BGP, rather than a single static `nos-bgpd`, the watchdog subscribes to `nos-configd` over its own `--config-socket` connection (`Request::SubscribeDiff`, independent of whatever address is forwarded to the `nos-configd` child via the opaque `--configd-arg` pass-through) and dynamically spawns one `nos-bgpd --instance <name>` per `BgpInstance` in the live config. It reconciles on every diff it receives: a fresh connection's first diff is synthesized against an empty config (so every currently-configured instance shows up as `Added`) and is treated as the authoritative full membership list — anything already running that isn't in it gets stopped, closing the gap where an instance removed while disconnected could otherwise leak as an orphan process — while every later diff on the same connection is applied incrementally (`Added`/`Removed` only — `Modified` is a no-op at this level, since `nos-bgpd`, like `nos-ribd`, independently subscribes to config and re-resolves its own peers/VRF on every relevant diff rather than needing a restart). The config subscription itself reconnects on a fixed 1s delay with no backoff if dropped (distinct from the exponential process-crash backoff below) — since `nos-configd` is supervised independently, its own crash/restart is transparent to already-running `nos-bgpd` instances. Every supervised process (`nos-configd` and each per-instance `nos-bgpd`) is respawned after an exponential backoff on unexpected exit (starting at 1s, doubling, capped at 30s; a run that stays up 60s decays the level one step rather than resetting, so a process crashing every 61s stays near the cap; five consecutive sub-60s runs, then every tenth, log an `error!` "crash loop" — the watchdog never gives up). Children inherit only `RUST_LOG`, `PATH`, `TZ` and `NOS_LACP_CHURN_SECS` (`env_clear` + allow-list), never `LD_PRELOAD`, proxies or secrets. On SIGTERM or SIGINT to the watchdog, or an instance's removal from config, its process is sent SIGINT (the signal `nos-configd`/`nos-bgpd` handle via `tokio::signal::ctrl_c()`), given up to 10s to exit cleanly, then force-killed — on watchdog shutdown this happens for every remaining process before it exits, so nothing is left orphaned. `docker-compose.yml` gives the `watchdog` service `stop_grace_period: 15s` so a `docker stop` doesn't SIGKILL the container inside that 10s window (`nos-ospfd`'s RFC 6987 on-shutdown hold plus its LSA flush take up to 9s of it).

RIB tables follow the identical dynamic-spawn pattern: the watchdog subscribes to `DiffScope::RoutingTables` and spawns one `nos-ribd --table <name>` per `RoutingTable` in the live config, with the same first-diff-is-authoritative reconciliation, fixed 1s reconnect delay, and exponential per-process crash backoff as BGP instances. `Modified` is likewise a no-op at this level — a table's `bgp_instance`/`static_routing_instance` association changing doesn't restart its `nos-ribd`, since that process independently subscribes to config (`RoutingTables` and `StaticRoutingInstances`) and re-resolves its own associations on every relevant diff, rebuilding its in-memory RIB from a fresh `Request::Get` rather than losing state to a restart.

A same-name respawn waits for the previous process to exit (#639): `stop_instance` parks the task in a `draining` map and `spawn_instance` awaits it (warning every 10s), so an old `nos-ribd`'s teardown can never delete the new instance's VRF, and `shutdown_all` awaits it too.

OSPF instances follow the identical dynamic-spawn pattern too: the watchdog subscribes to `DiffScope::OspfInstances` and spawns one `nos-ospfd --instance <name>` per `OspfInstance` in the live config, with the same first-diff-is-authoritative reconciliation, fixed 1s reconnect delay, and exponential per-process crash backoff as BGP instances/RIB tables. `nos-ospfd` gets a real `--listen-socket` and an `EndpointRegistry`/broker registration (`EndpointKind::OspfInstance`) just like `nos-bgpd`/`nos-ribd` — see `ospf/CLAUDE.md`.

Broadcast domains follow the same dynamic-spawn pattern, but opt-in per object like `nos-restd`: the watchdog subscribes to `DiffScope::BroadcastDomains` and spawns one `nos-fdbd --domain <name>` per `BroadcastDomain` **while its `vni` is set** (`Managed.claim_label = Some(VNI_LABEL)`, so `SetVni`/`ClearVni` on an existing domain — a `Modified` diff — spawns or stops it, and the domain's removal stops it), with the same first-diff-is-authoritative reconciliation, fixed 1s reconnect and exponential crash backoff, and a real `--listen-socket` (`/run/nos/fdb-<name>.sock`) registered as `EndpointKind::FdbDomain`. It creates a VXLAN device, so its SIGINT (unset vni, domain removed, watchdog stopping) deletes that device, like `nos-ribd` deleting its VRF. See `fdb/CLAUDE.md`.

Interfaces are supervised differently: unlike `nos-bgpd`/`nos-ribd`, `nos-interfaced` is a single fixed process — the watchdog always runs exactly one, the same way it always runs exactly one `nos-configd` — rather than one instance per `Interface` in config. Every interface is an OS resource in the same network namespace, so there's no isolation benefit to a per-interface process, and a single process avoids spawn/teardown churn on every interface add/remove. `nos-interfaced` itself subscribes to `DiffScope::Interfaces` and reconciles every configured interface internally on each diff.

`nos-logd` is supervised the same way as `nos-interfaced` — one fixed process, spawned first among the watchdog's children so the window before it's reachable is as short as possible — since log collection has no per-config-object scope to spawn one instance per. Its one config subscription is for remote syslog export (`Config.logging.syslog`, see `log/CLAUDE.md`; it gets `--watchdog-socket` to resolve `nos-configd` and `nos-ribd` in a background task, never blocking startup). Every other supervised process (`nos-configd`, each `nos-bgpd`/`nos-ribd` instance, `nos-interfaced`, and the watchdog itself) is handed `nos-logd`'s address directly via a constructed `--log-socket <path>` argument at spawn time — the same pattern already used for `--config-socket`, rather than a broker round trip, since (like `nos-configd`'s own address) it's needed unconditionally by every process from the moment it starts, not resolved lazily. See "Log collection" below.

`nos-lacpd` is supervised the same way too — one fixed process, since `PortAggregate` (unlike `BgpInstance`/`RoutingTable`/`OspfInstance`) has no per-VRF/per-instance multiplicity for a dynamic per-object spawn to key off: one `nos-lacpd` handles every currently-configured `Lacp`-mode aggregate's member ports itself, internally, the same way `nos-interfaced` handles every configured interface. It resolves both `nos-configd` (to learn which aggregates/members are `Lacp`-mode) and `nos-interfaced` (to push its negotiated active-member set, see "Endpoint broker" below) via the broker rather than a directly-handed address, since neither is needed unconditionally from the very first instant the way `nos-configd`'s/`nos-logd`'s own addresses are. See `lacp/CLAUDE.md`.

`nos-lldpd` is supervised the same way — one fixed process, since LLDP is per-interface with no per-instance multiplicity: one `nos-lldpd` handles every LLDP-enabled physical interface itself, internally. It resolves only `nos-configd` (via the broker) to learn which interfaces have `lldp transmit`/`lldp receive` set and what hostname to advertise; unlike `nos-lacpd` it pushes to no other daemon. It has `CAP_NET_RAW` only. See `lldp/CLAUDE.md`.

`nos-bfdd` is supervised the same way — one fixed process (`--bfdd-listen-socket`, `ServiceRef::Bfd`), since BFD sessions are shared by every client daemon and keyed by `(table, peer, ...)`, not by a config object. It resolves each session's `nos-ribd` through the broker to learn the table's VRF device and binds its sockets there; it subscribes to no config (clients send the profile in `Register`). It has `CAP_NET_RAW` and `CAP_NET_BIND_SERVICE`. See `bfd/CLAUDE.md`.

`nos-stpd` is supervised the same way — one fixed process (`--stpd-listen-socket`, `ServiceRef::Stp`), since spanning tree is bridge-wide: one core handles every STP port. It resolves `nos-configd` (ports and parameters) and `nos-interfaced` (the kernel link stream, and the port states it pushes) through the broker. It has `CAP_NET_RAW` only and never touches rtnetlink. See `stp/CLAUDE.md`.

`nos-acld` is one more fixed process (`--acld-bin`, `--acld-arg`, `Role::Acld`), started with the others: every ACL on every device is one kernel concern. It serves no socket yet (#543 adds `show acl`), so it gets only `--watchdog-socket` and `--log-socket`. It resolves `nos-configd` and `nos-interfaced` (the link stream) through the broker. It has `CAP_NET_ADMIN` for tc. See `acl/CLAUDE.md`.

**Every** supervised process — including each dynamically spawned instance — is started with a fresh certificate identity on its stdin (`ProcessSpec::with_identity(pki, role, name)`, `supervise_one`), and a task pushing rotations until it exits; `--pki-dir`/`--pki-leaf-lifetime`/`--pki-rotate-every`/`--pki-user-lifetime` configure it. See "IPC security".

In every family's pass-through flags (`--bgpd-arg`, `--restd-arg`, ...) a literal `{name}` is replaced by the instance name, so a per-instance path such as `--profile-memory-out=/tmp/dhat-restd-{name}.json` is possible.

`nos-restd` is the one family that is **opt-in per object** rather than one per object: it runs for a `RoutingTable` only while that table's `rest_api` field is set, and pinning/unpinning happens on an already-existing table (a `Modified` diff, a no-op for every other family). `Managed.claim_label` (`Some("rest-api")`) makes `instances::manage` key on that `FieldDiff` — set (`new` other than `"unset"`) spawns, unset or the table's removal stops — instead of on section membership; it has no IPC query listener, so `Managed.endpoint` is `None`. See `rest/CLAUDE.md`.

`nos-config`'s IPC protocol supports this via `Request::SubscribeDiff { scopes }`: a subscriber names which `ConfigDiff` sections it cares about (`DiffScope::{Hostname,BgpInstances,RoutingTables,OspfInstances,StaticRoutingInstances,Interfaces}`) and only receives `Event::Diff` for commits that touch a requested scope — commits outside every requested scope are never sent. This is a separate, additive path alongside the original `Request::Subscribe`/`Event::Config` (full snapshot on every commit, used by `nos-cli`'s live hostname prompt), which is unchanged. Both paths rely on a documented but easy-to-miss connection-lifecycle rule in `server.rs`: a subscriber (of either kind) is expected to send its request and then never write to the connection again — "the caller owns its lifetime" — so the server must not treat EOF/an error on the *request* side of a subscribed connection as reason to close the whole connection; it only stops reading further requests; the connection stays open to keep pushing events until the client is actually gone (detected when writing to it fails).


- A daemon never survives a panic (#419): `nos_log_client::install_panic_hook()` (called right after the tracing subscriber in every daemon `main`) logs `panic at <file:line>: <msg>`, waits ~200 ms for the forwarder, then aborts in every profile; the release profile is also `panic = "abort"`. The watchdog's crash backoff restarts it.
- The rtnetlink connection futures in the `fdb`/`interface`/`rib` Linux drivers are spawned with `nos_log_client::spawn_critical`: if one ever finishes (netlink socket died) the daemon logs and exits 1 rather than carrying on with a dead kernel handle.

**User ids** (#512, #513): `nos-watchdogd` runs as `nos-wd`; `supervise_one` starts each child with `ProcessSpec.uid`, the role's own uid (`ProcessSpec::with_role_uid`, from `--child-gid` in the image) after creating `/var/lib/nos/<role>` and logs `uid=`/`gid=` in its `starting` line. The ids switch before exec, so the children's file capabilities are unaffected. See "uid model" in [IPC security](ipc-security.md).

- Per-process env (#756): `ProcessSpec.env`/`with_env` is applied after the scrubbed `CHILD_ENV` allowlist, so a child gets extra variables only when its spec asks; only `nos-logd` (#756) and `nos-configd` (#776) use it, both for `MALLOC_ARENA_MAX=1`; `nos-configd` also gets `MALLOC_TRIM_THRESHOLD_=131072` and `MALLOC_TOP_PAD_=0` (#796). `nos-restd` does not: the #766 measurements showed its RSS unchanged by it.
