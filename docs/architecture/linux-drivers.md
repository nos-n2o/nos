# Linux drivers

Contributor-facing; moved from the root `CLAUDE.md` (#260). Operator view: [docs/README.md](../README.md).


Both `nos-ribd` and `nos-interfaced` apply their reconciled desired state to the real Linux network stack via `rtnetlink`, behind a swappable `Driver` trait per crate (`interface::driver::InterfaceDriver`, `rib::driver::RibDriver`) selected with `--driver linux|noop` (default `linux` on Linux, `noop` elsewhere — the `noop` driver is today's original log-only placeholder behavior, kept as a portability/test fallback). This is deliberately in-process rather than a separate privileged process, so a future non-Linux/hardware backend only needs a new `Driver` impl, not new IPC or supervision wiring. Both binaries run as the unprivileged `nos` user; the kernel access their Linux drivers need comes from `CAP_NET_ADMIN`/`CAP_NET_RAW` file capabilities baked onto the two binaries at image build time plus a matching `cap_add` on the `watchdog` container (see `Dockerfile`/`docker-compose.yml`).

`no-new-privileges` must stay off: the kernel then ignores file capabilities on exec, so every `setcap` binary would lose its capabilities.

`nos-ribd`'s Linux driver owns creating a Linux VRF device + kernel routing table for its `RoutingTable`, allocating a kernel table id on first use and persisting the name→id mapping to a local file (`--table-registry-path`, default `/var/lib/nos/ribd/table-ids.yaml`) purely so a crash/restart reuses the same id and VRF name — this file is never read by any other process. On shutdown (the same SIGINT used for both "watchdog is stopping" and "this table was removed from config") it deletes the kernel VRF and its routes, but never the registry entry, so an ordinary restart recreates the identically-named VRF.

Because `nos-interfaced` needs to enslave an interface into the VRF device that backs its configured `routing_table`, but has no way to derive that VRF's real Linux interface name on its own (it's allocated entirely inside `nos-ribd`'s driver), `nos-ribd`'s per-table socket gains one more request: `RibRequest::GetVrfName` → `RibEvent::VrfName(Option<String>)`. `nos-interfaced`'s Linux driver resolves the owning `nos-ribd` instance via the broker (`ServiceRef::RibTable(name)`) and queries it directly — **this is the first direct daemon-to-daemon IPC link in the system** (every other component only ever talks to `nos-configd` or the watchdog broker). A `None` answer (table not running yet, or running but hasn't created its VRF yet) is treated as an ordinary transient condition, not an error, and retried automatically by both daemons' periodic re-apply tick (in addition to their existing config-diff-triggered resync) — needed here specifically because "the other daemon became ready" isn't a config change either daemon would otherwise be notified of. The link also runs the other way: `nos-ribd` derives its table's **connected routes** (`RouteSource::Connected`, preference 0 — below `Static`) from what `nos-interfaced` actually applied, asking it on every resync (`rib/src/interface_client.rs`, `ServiceRef::Interfaces` via the broker) for `GetInterfaces` (every `Interface`/`Subinterface` address whose `routing_table` is this table — a loopback's is always the table in its name, whatever the field says), `GetPortAggregates` when some aggregate subinterface is in this table, plus `GetBroadcastDomain` per SVI-carrying domain of this table (there is no "list every domain" request). They show up in `show route`/`GET /v1/routes/{table}` as `connected` and in `RibRequest::IgpCosts` at cost 0, but are **never installed** (`Rib::best_routes_for_kernel` leaves a prefix whose winner is `Connected` to the kernel, so a `Static`/`Bgp`/`Ospf` route for a connected prefix is listed but not installed either, #139): the kernel adds its own on-link route the moment the address is applied, and `LinuxRibDriver`'s dump already ignores gateway-less routes as unmanaged, so a connected prefix never appears on either side of its diff. Their purpose is RFC 4271 §9.1.2 in `nos-bgpd` — see `docs/protocols/bgp-internals.md`'s "Next-hop feasibility".

`nos-bgpd` resolves its VRF the same way: a `BgpInstance` carries a reflexive, read-only `routing_table` field (mirrored by `nos-config` from the owning `RoutingTable`'s `bgp_instance` reference on every commit — never independently editable, and never shown in `nos-cli`'s config rendering, since it exists purely for `nos-bgpd` to read over IPC), which it resolves to a VRF name via the same `ServiceRef::RibTable` + `GetVrfName` call `nos-interfaced` uses. A `BgpInstance` with no owning `RoutingTable` is treated as invalid operating state, not a "default VRF" fallback — `nos-bgpd` never opens a session for it, only logging an error and rechecking on every resync in case config is fixed. Once a VRF name is resolved, `nos-bgpd` opens raw, VRF-scoped TCP connectivity to its configured peers (both an active outbound connect per peer and a shared passive listener on port 179, scoped into the VRF via `SO_BINDTODEVICE` rather than `rtnetlink` since no interface/route is being programmed) — the foundation the BGP FSM (OPEN/KEEPALIVE message exchange) will be layered on top of later.

`nos-lacpd` (see `lacp/CLAUDE.md`) is a second, independent daemon-to-daemon link into `nos-interfaced`, but in the opposite direction from `GetVrfName`: instead of *querying* `nos-interfaced` for something only it knows, `nos-lacpd` *pushes* something only `nos-lacpd` knows — a `Lacp`-mode `PortAggregate`'s currently-negotiated active-member set (`InterfaceRequest::PushLacpMembers`, fire-and-forget, the same "data plane push" pattern as `nos-ribd`'s `RibRequest::PushBgpRoutes`) — over a persistent connection resolved via `ServiceRef::Interfaces`. `nos-interfaced`'s Linux driver still owns every actual `rtnetlink` call for the bond device (`ensure_port_aggregate`, member enslavement); `nos-lacpd` never touches rtnetlink at all, and the kernel bond is created identically for `Xor` and `Lacp` modes (`BondMode::BalanceXor` in both cases — **not** the kernel's own `Ieee8023Ad` bonding mode, which would silently steal every LACPDU from `nos-lacpd`'s own raw sockets before userspace ever saw them). The `PortAggregateMode` only changes which control plane decides *membership*: unconditional for `Xor`, gated on this push for `Lacp`.

`nos-interfaced` also *watches* the kernel: its Linux driver holds an `RTMGRP_LINK` netlink subscription (plus a 30 s re-dump) feeding an in-memory link table, and `InterfaceRequest::SubscribeLinks` streams it — `LinkSnapshot` first, then `LinkChanged`/`LinkRemoved`, a fresh snapshot after any lag — to `nos-ospfd`/`nos-ospfv3d`. See [interface internals](../internals/interface.md#link-watcher).

`nos-interfaced`'s Linux driver owns L2 switching the same way `nos-ribd`'s owns VRFs: one real Linux bridge device per configured `BroadcastDomain`, named from a bridge id allocated on first use and persisted to its own private registry (`--bridge-registry-path`, default `/var/lib/nos/interfaced/bridge-ids.yaml` — the same `linux-driver/` directory `nos-ribd`'s `table-ids.yaml` already lives in). Because a `BroadcastDomain` is one L2 domain but two different interfaces can tag it with two different local dot1q values (the tag is locally significant per interface, not global to the domain), there is deliberately no single shared 802.1Q-aware bridge with one global VID→domain mapping: an `Interface.switching_profile`'s `Untagged` member enslaves the physical link itself into its domain's bridge, and each `Dot1q(N)` member gets its own 802.1q sub-interface (`<interface>.<tag>`) enslaved into that domain's bridge instead — so two interfaces can use different tags for the same domain and still land on the same bridge. `routing_table` and an `Untagged` switching-profile member are mutually exclusive on the same interface (rejected at commit time), since the physical link has only one master; a `Dot1q` member never conflicts, since it lives on an independent sub-interface. `BroadcastDomain` itself also carries an optional `addresses`/`routing_table` — the same flat L3 shape as a loopback `Interface` — making the domain's own bridge device an SVI (switch virtual interface): `nos-interfaced` reconciles them directly onto the bridge with the identical `reconcile_addresses`/VRF-enslavement calls it already makes for an ordinary link, independent of whatever interfaces are enslaved into that bridge as L2 members (a separate Linux device, so no conflict with any member's own VRF assignment).

`nos-interfaced` also owns spanning-tree port safety (#326): while `spanning-tree mode` is not `disabled`, every bridge port is written DISABLED (the only blocking state a `BR_NO_STP` bridge keeps) and gets an ingress `flower`+`gact drop` BPDU trap, until `nos-stpd` pushes a state with `SetStpPortStates`. Details and kernel findings: [STP internals](../internals/stp.md#kernel-side-nos-interfaced-326).

## Route replace (`nos-ribd`, #598)

- A changed next-hop set (shrink, grow, labels, gateway, discard <-> gateway) at an already-installed slot is one `RTM_NEWROUTE` with `NLM_F_REPLACE | NLM_F_CREATE` (`RouteChannel::replace`), never a delete then an add: the route is never absent from the table, so a labelled or ECMP flow does not blackhole.
- `NLM_F_CREATE` without `EXCL` is deliberate: when the shadow state drifted and the old route is gone, the replace still installs.
- Both `apply_delta` and the dump-diff `apply` do it (`slot_op`: a slot in both lists with different keys is a `Replace`); only a slot that vanished is a `del`.
- A failed replace is surfaced and the shadow keeps the old hops (the kernel still has them); there is no del+add fallback.
- Logs: the usual `added route` / `installed labelled route` line with a trailing `replaced=true`; no `removed ...` line for the old key. Check with `assert_quiet` on `removed route prefix=` in `nos-e2e`.
- IPv4 and IPv6 are both replaced; the `vpn-v6`, `vpn-multipath`, `bgp-multipath` and `ospf-spf` phases are the kernel regression guard. IPv6 ECMP replace needs a kernel that replaces a multipath route whole (the behaviour of current kernels; very old ones could replace only the first hop).

## MPLS (L3VPN, `nos-ribd`, #581)

- `RibDriver::sync_mpls(table, Some(Mpls { label, underlay }))` installs the AF_MPLS route `<label> dev <vrf>` (pop, then an IP lookup in the VRF; one route serves IPv4 and IPv6). Each call dumps the AF_MPLS routes, deletes any other label pointing at this VRF first (a changed `vpn.label`, a previous run), then adds ours with `NLM_F_REPLACE` if missing. `None` and `teardown` delete it. Logs: `installed mpls pop route` / `removed mpls pop route` with `table`, `vrf`, `label`.
- Labels below 16 are refused (RFC 3032 reserved), as defence in depth behind config validation.
- Ingress: a `Vpn` route is `RTA_ENCAP_TYPE=MPLS` pushing its labels, `via <gw> dev <if> onlink` in the customer table. Several next hops are one `RTA_MULTIPATH` route with an encap and `RTNH_F_ONLINK` per next hop (`nexthop encap mpls <l1> via <gw1> dev <if> onlink nexthop encap mpls <l2> via <gw2> …`); the same gateway twice with different labels is accepted. The gateway and ifindex come from `nos-bgpd`'s resolution in the underlay table; without an ifindex the driver asks the kernel (`RTM_GETROUTE` with `RTA_OIF` = the underlay VRF, `ip route get <gw> vrf <underlay>`). Logs: `installed labelled route` / `removed labelled route` with `prefix`, `labels` (one stack per hop), `gateway`.
- Sysctls are `/proc/sys` file reads and writes (`driver/mpls.rs`, no external command, #228), each read first and written only when not already enough:
  - `net.mpls.platform_labels`: grown to the next multiple of 1024 above the label, never shrunk (that would delete routes). A failure is an `Err`, so the export is withheld.
  - `net.mpls.conf.<if>.input=1` on every interface enslaved to the underlay VRF. A failure is a one-time `warn!` per interface (a loopback faces no PE).
- `/proc/sys/net/mpls` missing means `mpls_router` is not loaded: the error says so. It only appears in network namespaces created after the module loads.
- Docker mounts `/proc/sys` read-only: the driver can only read, so the operator (or the e2e helper, `vpn-dataplane`) sets the values.

## tc filters (`nos-tc`)

Several daemons put filters on the same device's `clsact` qdisc, all through the `nos-tc` crate (hand-encoded netlink: `netlink-packet-route` has no `gact`/`skbedit`/`fw`/`mirred`):

- Every owner ensures the qdisc (`Request::Clsact`, tolerating `EEXIST`) and never deletes it.
- Each owner keeps to its own priorities on chain 0 (table in `tc/CLAUDE.md`): `nos-fdbd` 1 and 2 (local bias), `nos-interfaced` 1 (BPDU trap, bridge-port ingress, never a VXLAN port; fdbd's prio 1 there is on egress) and 3 (bond egress / member ingress, #895), `nos-acld` flowspec band 10..99 (#561) and ACL 100 (#541). A lower priority runs first.
- Delete by priority (`DelFilter`, `handle` 0 for all of it) or by chain (`FlushChain`), never the whole hook.
- Calls block: run them on `spawn_blocking`.
- Chains and fall-through (spike of #563, Linux 7.2, `spike_goto_chain_miss_and_unspec_fall_through` in `nos-tc`'s kernel test):
  - A miss inside a `goto chain` target does **not** fall back to the remaining chain-0 filters: classification of that packet ends there. Anything that must run after a chain (a lower-priority chain-0 filter) is never reached.
  - A filter whose last verdict is `Verdict::Unspec` (matched, counted, `TC_ACT_UNSPEC`) **does** fall through to the next filter of the same chain (and of chain 0 when it sits in chain 0).
  - So a rule that must fall through uses `Verdict::Unspec`, and an ordered rule list that must be followed by other chain-0 owners (the ACL at 100) lives directly in chain 0, one priority per rule (band 10..99 for flowspec), never behind a `goto chain` entry.
- Rewrites and policing (#563):
  - `ActionKind::Police { rate, burst, unit }`: exceed drops, conform `pipe`. `Bytes` is bytes/s and bytes (above 2^32 bytes/s the kernel gets `TCA_POLICE_RATE64`); `Packets` is packets/s and packets (`PKTRATE64`/`PKTBURST64`; the kernel meters it against the one TBF burst, so `nos-tc` writes the burst in both). Both are accepted by Linux 7.2. The packet bucket starts empty, so the first packet after install can be dropped.
  - `Pedit::Dscp` rewrites the DSCP only (ECN, and for IPv6 the version and flow label, are kept). Pair it with a filter of the same family (`Protocol::Ip`/`Ipv6`). The IPv4 form is encoded as two table entries, `pedit` then `csum` (IPv4 header): without it the rewritten header fails its checksum and is dropped (`InHdrErrors`), as checked in the kernel test.
  - `FlowerKeys.ip_tos` matches the DSCP and never the ECN bits. Flower has no IPv6 flow-label key on Linux 7.2 (no `TCA_FLOWER_KEY_*` for it in `pkt_cls.h`): that match is unsupported and must be refused by callers.
- VLAN redirect (#955): `Protocol::Dot1Q` + `FlowerKeys.vlan_id` (host-order u16, proven against the kernel) match tagged frames only; `ActionKind::Mirred { ifindex }` is an egress redirect (`TC_ACT_STOLEN`). Behaviour of a redirect to a down device is for #895 to prove.
- Check by hand in a throwaway namespace: `unshare -Urn`, then `tc filter show dev <dev> ingress` (add `chain <n>`, `-s` for counters).

## Access lists (`nos-acld`, #541)

`nos-acld` (`acl/`) owns its chain-0 priority and two chains on every device with an `acl in`/`acl out`:

- `acl in` is the `clsact` ingress hook, `acl out` the egress hook (no ifb). Egress sees forwarded and locally generated packets; on a bond it runs before the slave is chosen.
- Chain 0, priority 100 (`ACL_PRIO`), handle 1: one keyless flower filter, `gact goto chain <live>`, whose action cookie holds the live chain number. `nos-fdbd`/`nos-interfaced` filters (priorities 1, 2) run first, so their drop wins.
- The ACL itself is in chain 1000 or 1001 (`ACL_CHAIN_A`/`ACL_CHAIN_B`): level `l` at priorities `2l+1` (protocol `ip`) and `2l+2` (`ipv6`), since the kernel allows one protocol per priority; a level holds the filters of every user rule the optimiser (#542) packed there (pairwise disjoint rules, so one flower priority per family costs one lookup per mask); then one keyless default filter per family. Permit is `gact ok`, deny `gact drop`; each action's cookie is the rule's index (`u32::MAX` for the defaults), for `show acl`'s counters (#543).
- Non-IP frames (ARP, LACP, LLDP, STP) match nothing in the chain and pass.
- `log` (#544): the rule's filters carry `sample rate 1/100 trunc_size 128 group 0x4e4f53` (`ACL_PSAMPLE_GROUP`, control `pipe`) before the `gact`, with the same cookie. Only about one packet in 100 is sampled (`SAMPLE_RATE`, #699), so a flood no longer costs a netlink multicast per packet and a lone denied packet logs only about 1 time in 100; the verdict counters stay exact. A rate gate (`police` with exceed = continue plus a verdict-only twin filter) was tried first and the kernel refuses the twin: two flower filters with the same keys at one priority fail with `EEXIST`. The `acl-log` thread joins psample's `packets` generic-netlink group (hand-decoded in `nos-tc`, needs `CAP_NET_ADMIN`) and names each sample:
  - direction and device from psample's ifindexes: egress sets `out` to the device; ingress sets `in` to the device and `out` to 0 (checked in `nos-tc`'s kernel test, Linux 7.2);
  - the rule from the cookie (`PSAMPLE_ATTR_USER_COOKIE`, Linux 6.11+). The install checks the family knows that attribute (`CTRL_ATTR_MAXATTR`) after the filters are in, since installing `act_sample` loads `psample`; without it the install fails and the previous chain stays.
  - The data starts at the Ethernet header at both hooks; lines are rate-limited in the daemon (10/s, burst 10, per device, direction and rule).
- Counters (`show acl`, #543): an `RTM_GETTFILTER` dump of the live chain, read under the lock a pass takes. Each filter's `gact` row (found by kind, not position, so a second action does not shift it) is keyed by its cookie: the rule index, or `u32::MAX` for the default filters; a rule's counters are the sum over its filters and devices. A new chain starts at zero, so any edit resets them.
- Update: fill the idle chain, replace the entry (`NLM_F_REPLACE`, one RCU swap), flush the old chain. Atomic per (device, direction) only. `switch` writes chain 999 first and the entry last (the commit point), so a failed switch leaves the old chain live; a half-failed one is repointed at the old chain by the engine, and a failed first attach is detached (#698).
- Start: the first link snapshot is swept (a chain-0 dump per device and hook); a previous run's entries are adopted, then replaced or removed (fail closed across a crash).
- Clean stop (SIGINT): entry first, then both chains. A device that disappears takes its filters with it; one that is not there yet is applied when `nos-interfaced`'s link stream shows it.
- A bond is found through `LinkState.port_aggregate`, which `nos-interfaced` stamps on its `bond<id>`; `nos-acld` never derives the name.

## Flowspec rules (`nos-acld`, #561)

`nos-acld` also installs BGP Flow Specification rules on ingress, beside the ACL. A rule reaches it as a `FlowRule` (`nos_proto::acl`, a data-only mirror of `nos-bgp`'s decoded NLRI and actions), in a per-instance snapshot `FlowspecSet { instance, devices, rules }`.

- Layout (decision A, settled by the #563 spike): directly in chain 0, one priority per rule in the band 10..99 (`flowspec::PRIO_FIRST..=PRIO_LAST`), in snapshot order. Per device the instances stack in name order. A `goto chain` entry is not used, because a miss inside its target would end classification and skip the ACL at 100.
- One rule = one family = one priority. Its filters (the alternatives a numeric expression or a type-4 port expands to) share the priority and the actions. Each filter's first action carries the rule index as cookie, so a dump counts each filter once.
- Caps: 90 rules per device (the band; the rest are `unsupported: rule cap`), 64 filters per rule.
- Lowering (`acl/src/flowspec.rs`, pure): prefixes (IPv6 offset 0 only), protocol, ports (`!=`/`<`/`>` expanded to ranges; ports imply TCP or UDP), ICMP type/code, TCP flags when expressible as flags/mask, DSCP (`ip_tos`), fragment `IsF`/`FF` (flower's `is_fragment`/`firstfrag`). Refused, never approximated: packet length, flow label (no flower key on 7.2), fragment `DF`/`LF`, IPv6 prefix offset, redirects (sent as `FlowRuleAction::Unsupported`), an expression that matches nothing.
- Actions, in order: `sample` (psample group `0x465350`, nothing reads it yet; one packet in 100 like `log`, and the rule cookie sits on the next action so counters stay exact), DSCP `pedit` (IPv4 adds `csum`), then rate 0 `gact drop`, or rate > 0 `police` (bytes or packets per second, burst one second of rate, at least 16 KiB for bytes; the packet bucket starts empty), then the verdict.
- Verdict: the RFC 8955 T bit set means later rules also apply: `Verdict::Unspec`. Clear (the default): `goto chain 999` (`flowspec::EXIT_CHAIN`), whose one filter jumps to the live ACL chain, so a rate-limited or marked packet still meets the ACL. `Driver::switch` keeps that filter in step with the ACL entry; without an ACL the chain is empty and the packet passes.
- Update: per priority whose content changed, delete it (by `ip` then `ipv6`: the kernel refuses a delete with the wrong protocol) and add the new filters. Not atomic across priorities; unchanged rules keep their counters.
- Start: the first link snapshot also dumps each device's band; what a previous run left is rewritten or cleared by the next pass. Clean stop clears every band priority.
- Log lines: `flowspec rules received instance= rules= installable= devices=`, `flowspec applied interface= rules=`, `flowspec rule unsupported instance= flow= reason=` (once per instance, flow and reason), `flowspec pending interface= reason="absent"`.
- Read back: `GET /v1/flowspec` and the end of `show acl` list every rule with `unsupported` (the reason, `not attached` when no device holds it, or empty when installed) and packets/bytes summed over its devices. `nos-bgpd` reads the same rows for `show bgp flowspec`'s `dataplane`.

### Feed rules by hand (test hook)

- `nos-acld --flowspec-file <path>` (hidden; through the watchdog: `--acld-arg=--flowspec-file=<path>`) reads a JSON `FlowspecSet` every second and applies it when the content changes. A missing file clears what it applied.
- Example, drop TCP from 10.50.0.3:

```json
{"instance": "e2e", "devices": ["eth0"], "rules": [
  {"flow": "src 10.50.0.3/32 proto =6", "ipv6": false,
   "components": [{"Source": {"prefix": "10.50.0.3/32", "offset": 0}},
                  {"Protocol": [{"and": false, "lt": false, "gt": false, "eq": true, "value": 6}]}],
   "actions": [{"RateBytes": 0.0}]}]}
```

- Production pushes come from `nos-bgpd` as `AclRequest::PushFlowspec` (`Role::Bgpd` only, #562) with `devices` empty: `nos-acld` adds, per instance, the devices of its own plan (`plan::flowspec_devices`: every `flowspec` interface, subinterface or port aggregate whose routing table that instance owns, an aggregate resolved through its bond like an ACL). A config change re-attaches; a rule no device holds shows `unsupported: not attached`.
