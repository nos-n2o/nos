# nos-e2e phases

Developer reference for the `nos-e2e` harness (`tools/e2e`): every phase, what it needs and what it proves against real containers. The registry is `tools/e2e/src/phases/mod.rs`; a unit test (`cargo test -p nos-e2e`) fails when this table and `phases::ALL`/`phases::group` disagree.

- Run one phase, a group or everything: `cargo run -p nos-e2e -- <phase|group|all>`. Also `logs [n]` (last n log lines of every running router, via REST) and `down` (tear down containers, volumes and the network).
- `all` runs every row below in table order and leaves the containers up for inspection (`logs`).
- A group (`base`, `drivers`, `rpl`, `ospf-suite`, `multi`, `pki-suite`, `pki-crl`, `logd-memory-lab`, `config-memory-lab`) is self-contained: it starts its own routers, runs its members in table order and tears down on exit (pass or fail) unless `VERIFY_E2E_KEEP=1`. `.github/workflows/verify-e2e.yml` runs the first seven as parallel CI jobs; `logd-memory-lab` and `config-memory-lab` are manual only (minutes of runtime, memory thresholds are the flakiest class). The `Groups` column lists membership; groups are not restated elsewhere.
- `Requires`: `self-contained` phases start their own routers; a list of phases must already have run in the same lab (earlier in table order); `-` needs only the lab that `up` and `established` leave behind.
- How the harness provisions and asserts: root `CLAUDE.md`, "Two-router end-to-end verification".
- Adding a phase: root `CLAUDE.md`, "New features require an end-to-end Docker verification phase". Add its row here, in `phases::ALL` order.

## BGP

Topology: router-a (AS 65001) and router-b (AS 65002) on one docker network, peered in `rt1`. Self-contained phases add ExaBGP (`router-g`, scripted speakers, `asn4 disable`, API-fed paths), StayRTR, FRR (`router-f`) or a third nos router. `nos-e2e` sets `connect-retry-time` to 3s on every peer-group (the default 120s would stall "established" waits). Phases that change config take a baseline first and wait for a new session rather than a stale log line.

- `up`: start both routers (config seeded, REST pinned), configured as peers
- `established`: wait until both routers' `GET /v1/bgp/summary` shows an Established peer (graceful-restart / extended-message capabilities still checked from the log)
- `reconnect`: kill one side's nos-bgpd, confirm the other detects it and both re-establish
- `collision`: restart both nos-bgpd processes at once, check for/report a collision event
- `shutdown`: shut router-a's peer-group, then its peer alone, with an RFC 9003 message: router-b logs the Cease/Administrative Shutdown text (an RFC 8538 Hard Reset wrapping it, graceful restart being on) and the session stays down until cleared; removing the peer sends Cease/Peer De-configured
- `redistribute`: a static route configured on one router actually being redistributed into BGP, advertised over a real UPDATE message, learned into the other router's Adj-RIB-In/Loc-RIB, and — the BGP→RIB leg — pushed by that other router's own `nos-bgpd` to its `nos-ribd` and installed as a real kernel route in its own routing table — and that a soft-in's identical re-announcement of it is not a new best path (#160)
- `bgp-routes-paging`: provisions 25 `10.89.<i>.0/24` statics with `--redistribute` on router-a, then walks `GET /v1/bgp/routes?instance=r1&limit=10` over `pagination.next` on router-a (local routes) and router-b (learned paths), asserting each prefix appears once in ascending order; checks the first page, the 400s (pagination without `?instance=`, malformed `after`) and the 404 for an unknown instance; then removes the statics
- `bgp-graceful-restart`: RFC 4724/RFC 8538 graceful restart on by default between the two nos routers: the capability with N and an End-of-RIB each way with no config (`established` checks the capability too), router-a's `nos-bgpd` killed while its `nos-ribd` holds a prefix router-b redistributes: the respawned process restarts gracefully (`forwarding state preserved, deferring route selection`, R and F set in its OPEN, `route selection deferral ended reason=end-of-rib`), router-b keeps router-a's route until router-a's End-of-RIB (`count=0`), and neither kernel removes the other's route, a Cease/Other Configuration Change kept graceful by N (kept until router-a's End-of-RIB, never removed from router-b's kernel), `clear` going out as a Hard Reset (flushed and re-learned), and router-a with `graceful-restart disable` (flushed as no-capability on return, a kill a hard flap, no End-of-RIB sent to it), then back to the default
- `ribd-crash-hold`: router-b redistributes a static, router-a's `nos-ribd` is SIGKILLed (no teardown): the respawn logs `startup hold: keeping existing kernel routes`, then `startup hold released` once `nos-bgpd`'s `Full` is applied, and router-a never logs `removed route` for router-b's prefix; the session stays up
- `auth`: checks that a matching RFC 2385 TCP MD5 password configured on both routers' peer-groups still establishes while a mismatched password on either side does not (verified against the real kernel's `TCP_MD5SIG` enforcement, not simulated)
- `ao`: checks that a matching RFC 5925 TCP-AO key configured on both routers' peer-groups still establishes while a mismatched `exclude-options` (RFC 5925 §5.2, `TCP_AO_KEYF_EXCLUDE_OPT`) on either side does not (verified against the real kernel's TCP-AO enforcement), that the resulting `getsockopt(TCP_AO_INFO)` readback surfaces the live current/rnext key id in `show bgp brief`/REST, and that a real RFC 5925 §7.5 key-rollover sequence (add a second key as rnext, promote it to current, remove the old one) is hitless (#83): applied to the live socket in place, the kernel advancing both sides' current key on the peer's RNextKeyID, no session ended or re-established, while removing the key the peer still signs with (`EBUSY`) falls back to a reset
- `gtsm`: set max-hops 1 (RFC 5082 GTSM) on both routers' peer-groups, confirm the session still establishes with TTL 255 / min-TTL 255
- `policy`: checks that a real RPL import policy on one router actually rejects a specific redistributed prefix and that reverting to `accept-all` lets it back in; with `soft-reconfiguration-inbound` the same tighten/loosen is applied in place from the retained routes (no session restart, no route refresh), including enabling it on a live session (a route refresh) and disabling it (#859)

## Drivers

These need the kernel modules checked by `make e2e-preflight`. `lacp` and `lldp` use direct veth pairs between the two containers (`World::link_veths`), not docker networks: a Linux bridge never forwards the slow-protocols multicast or LLDP's `01:80:C2:00:00:0E`. `port-aggregate` needs two real links (`eth1`/`eth2`, own docker networks). `syslog` runs a syslog-ng container as an independent parser; `rest` also covers authentication and uses a throwaway `router-r` for the checks that sever REST itself.

- `loopback`: checks that a loopback interface (named `loopback-<table>` — the name alone marks it as a loopback, no separate config field) actually gets a real dummy kernel device created (named from its routing table's allocated kernel table id, e.g. `lo100`), enslaved into that table's VRF, and addressed — with no `routing-table` set, its address still listed as a `connected` route in `GET /v1/routes/rt1` — then deleted again on removal
- `routes-paging`: provisions 25 `10.88.<i>.0/24` statics on router-a and walks `GET /v1/routes/rt1?limit=10` over `pagination.next` (three pages), asserting each prefix appears once in ascending order; checks the first page holds 10 items with a `next`, that `after=` past the last prefix yields an empty page with `next: null`, and that a malformed `after` is 400; then removes the statics
- `mtu`: checks that a non-default MTU configured directly on an `Interface` (a link-layer property, not per-subinterface) actually gets applied to the real kernel link by `nos-interfaced`'s Linux driver and reported by `GET /v1/interfaces/eth0`, and that clearing it puts the link back to the enforced 1500; then (#843) with a VLAN sub-link `eth0.300` created at 1500, raising the link to 9000 gives it `applied sub-interface mtu ... mtu=9000`, a `--subinterface-mtu 1400` override wins, clearing it returns to 9000, and clearing the link's MTU returns it to 1500, each checked in `GET /v1/interfaces/eth0` subinterface `mtu`
- `port-aggregate`: checks that a `PortAggregate` (a static Linux bonding device — `Xor` mode, every member enslaved unconditionally) actually gets a real kernel bond device created and two real dedicated member interfaces (`eth1`/`eth2`, on their own docker networks — bonding needs at least two real distinct links, unlike every other phase's shared `eth0`) actually enslaved into it via `Interface.port_aggregate`, an address on the bond's tag-0 subinterface listed as a `connected` route in `rt1`, then torn down again
- `lacp`: checks that the actor port numbers are the allocated 1 and 2 (not ifindexes) and that a `Lacp`-mode `PortAggregate` running `lacp-rate fast` actually drives a real, from-scratch IEEE 802.1AX LACPDU exchange (see `docs/internals/lacp.md`) over real raw `AF_PACKET` sockets between both routers' own `eth1`/`eth2` (direct veth pairs between the two containers, not docker networks — a Linux bridge never forwards the slow-protocols multicast address, so no LACPDU could cross one), converging both sides' Receive/Mux state machines to `Distributing` and only then getting `nos-interfaced` to actually enslave each negotiated member into the same kind of real kernel bond device — proving the enslavement is genuinely negotiation-gated, not just config-driven like `Xor` — and that router-a answers a real injected Marker PDU (§6.5) with a byte-correct Marker Response, that an injected version-2 LACPDU (extra TLVs, over 110 bytes) reaches its Receive machine while a version-3 one only bumps the port's `unsupported_version_pdus` in `GET /v1/lacp`, and that withdrawing one member from the partner's aggregate (so it goes silent on that link) gets `nos-lacpd` to detect the loss via its real Receive Machine timeout (within 30s — far under the 90s Long timer, so the fast rate is provably in effect) and `nos-interfaced` to release it from the bond again, before the aggregate itself is torn down
- `micro-bfd`: checks RFC 7130 micro-BFD (`bfd`/`bfd-peer` on a `Xor` `PortAggregate`, `bfd-profile fast` 100 ms x 3) on the `lacp` phase's veth pairs: each router's `nos-bfdd` runs one session per member on the member itself (UDP 6784, IP packets to the dedicated multicast MAC), both reach Up on `eth1` and `eth2`, and only then `nos-interfaced` enslaves them (`PushBfdMembers`); the sessions stay Up while the members are enslaved, which proves frames still reach a member-bound packet socket behind the bond's `rx_handler`; a `tc` filter dropping UDP 6784 on router-a's `eth2` ingress takes that session Down within the detection time and releases `eth2` from the bond while `eth1` stays, and lifting it re-enables `eth2`; `GET /v1/bfd/sessions` lists the sessions with `key.aggregate` and the member as `key.interface`; deleting the aggregate stops them
- `lldp`: checks that `lldp transmit`/`lldp receive` on both routers' `eth1` (the same direct veth pairs as `lacp` — a Linux bridge never forwards LLDP's `01:80:C2:00:00:0E` either) actually drives a real IEEE 802.1AB LLDPDU exchange over real raw `AF_PACKET` sockets (see `docs/internals/lldp.md`), each `nos-lldpd` learning the other's System Name and port id, that a tuned `tx-interval`×`tx-hold` (5×3 → a learned TTL of 15) and several Management Address TLVs in one LLDPDU really reach the neighbor (one carrying the real ifIndex of the sender's `eth0`, resolved in its netns, one on no interface falling back to the "unknown" numbering, and the second removed again), that router-a's IEEE 802.1/802.3 org TLVs reach router-b (a switching-profile port's Bridge bit, VLAN Name and jumbo Maximum Frame Size on `eth1`, a bond member's Link Aggregation with the bond's ifIndex on `eth2`), that `GET /v1/lldp/statistics` reports real 802.1AB frame counters on both (sent and received, no errors, no unrecognized TLVs), that a `SIGSTOP`ped `nos-lldpd` (no shutdown frame) is aged out on that 15s TTL alone and counted in `ageouts`, that both routers on the `customer-bridge` destination group (`01:80:C2:00:00:00`) still hear each other while a mismatched pair never does, that turning transmit off on one side makes it send a real TTL-0 shutdown LLDPDU the other side acts on within seconds (not after the 120s TTL), that transmit coming back is learned again, and that dropping receive restarts the link transmit-only
- `l2-socket-race`: checks that `nos-l2-socket` creates its `AF_PACKET` socket with protocol 0, attaches the kernel filter and only then binds with the ethertype (a socket created with a protocol is hooked on every device until bound, and a later bind or filter does not flush what was queued); on the `lacp` veth pairs router-b floods `eth2` with LLDPDUs (port id `race-eth2`) from a helper container for 40 s while 30 tx-interval changes make router-a's `nos-lldpd` reopen its `eth1` socket, and router-a must log no `lldp neighbor learned interface=eth1 ... port_id=race-eth2`

## OSPFv2

`ospf` stands up the base lab: the point-to-point `eth0.0` and a `BroadcastDomain` bridge (dot1q sub-interface of `eth0`), the same profile on both, so one lab covers point-to-point and broadcast. Later phases reuse it, hence their `Requires`; a third router (`ospf-dr`) stays for `ospf-lfa` and the three `ospf-*` phases after it. Self-contained phases launch their own routers (`ospf-aging` with `--lsa-age-multiplier`, `ospf-dbd-pagination` with `--dbd-max-headers=1`). `ospf-opaque` runs FRR on router-a's `eth1`; `ospf-remote-lfa` uses five routers in a veth ring.

- `ospf`: checks that declaring a basic `OspfInstance` (name, router-id, routing-table association, see `docs/protocols/ospf-internals.md`), a nested `OspfArea` (dotted-quad area id) and `OspfProfile` under it, and attaching that profile to both routers' own eth0 tag-0 subinterface (`ospf <profile-name>`, requiring a `routing-table` on the same attach point — the same subinterface already carrying their BGP session's own address) actually gets `nos-watchdogd` to dynamically spawn a real `nos-ospfd` process for each instance, which itself resolves its own instance's router-id/routing-table/areas/profiles and every interface attached to each profile over a real IPC round trip to `nos-configd`, and actually exchanges real RFC 2328 Hello packets over a real VRF-scoped raw protocol-89 socket between the two containers, reaching neighbor state 2-Way on both sides, then completes a real RFC 2328 §10.6-10.8 DBD/LSR/LSU/LSAck exchange reaching `Full`, with a real self-originated Router-LSA actually flooded and installed into the other side's per-area LSDB (landing with RFC 2328 §13.3's `InfTransDelay` added to its age — never at age 0) — and, by attaching the same profile a second time to each router's own `BroadcastDomain` bridge (trunked from `eth0` via a dot1q sub-interface, so the bridge is reachable over the same docker network as a real multi-access segment), that the identical Hello exchange also reaches 2-Way there and runs a real RFC 2328 §9.4 DR/BDR election, converging deterministically on the higher-router-id side as DR and the other as Backup, and that adjacency there too reaches `Full`

- `ospf-external-flood`: RFC 2328 §3.6 external flooding across areas: router-a in the backbone only, router-b the ABR (eth0.0 in area 0, the bridge in a normal area 1) and router-c on the bridge redistributing a static; router-b copies router-c's Type-5 into the backbone (`ospf external lsa copied across areas`), router-a's `GET /v1/ospf/database` holds it with `external_metric` 20 and its route is installed, and clearing the rule makes router-b carry the MaxAge copy across too (`maxage=true`) so router-a removes the route
- `ospf-virtual-link`: an RFC 2328 §15 virtual link b<->c through area 1: §16.7 brings it up from area 1's SPF (`ospf virtual link up`), the virtual adjacency reaches `Full` over real VRF-bound raw sockets (unicast, Area-ID/source demux from the bridge link sharing its addresses), router-a's `GET /v1/ospf/database` shows both area-0 Router-LSAs with the type-4 link (`virtual_links`) and router-c's area-2 Type-3 carried into the backbone over it, router-b/router-c see each other's area-1 V bit (`router_flags`), router-a installs router-c's loopback through router-b (`gateway=<router-b>`, the type-4 edge of RFC 2328 §16.1) and router-b through router-c's bridge address (§16.7's transit next hop), and router-c clearing its end takes router-b's virtual neighbor down within the dead interval and both routes with it, while router-c's area-1 summary stays at router-b (§16.2: a backbone ABR ignores it)
- `ospf-opaque`: RFC 5250 opaque LSAs against a real FRR router (`router-f`, `quay.io/frrouting/frr`, on its own docker network with router-a's eth1 only): FRR reaches `Full` with router-a and — only because router-a's DBDs carry the O-bit — originates a type-10 (segment routing's Extended Link) and a type-11 (Router Information, AS scope) opaque LSA, which router-a installs and floods on to router-b over eth0.0 and lists in `GET /v1/ospf/database`, router-a's own RFC 7770 Router Information LSA (type 10, GR-helper capability) installed by router-b and accepted by FRR (which decodes an RI body only in its own `router-info` scope, AS), then — RFC 6987, router-a `max-metric router-lsa administrative` with router-b's loopback in OSPF — FRR's own SPF reaches that loopback through router-a at a cost of at least 65535 while router-a's eth0.0 subnet (a stub, which keeps its cost) stays below it, then — router-a made an ASBR (a redistributed static) and an ABR (a loopback in area 1) — FRR lists router-a as an `ABR, ASBR` border router and installs both the external and the inter-area prefix, which it does only because router-a's Router-LSA carries the RFC 2328 A.4.2 E and B bits (#34) — plus the overlapping `/26` router-a sends at a host-bits link state id (RFC 2328 Appendix E) — and FRR's own redistributed overlapping pair (`198.18.100.0/24` and `/25`, one at a host-bits link state id) becomes two routes with the right prefixes on router-a, an FRR static whose next hop is an unused address on the shared subnet reaches router-a with that address as the forwarding address and is routed via it, not via FRR (RFC 2328 §16.4 step 3, #215), then a type-9 Grace-LSA (`graceful-restart prepare ip ospf`) that router-a installs on eth1 and helps (RFC 3623) but router-b never receives (link-local scope)
- `ospf-remote-lfa`: RFC 7490 remote LFA on a real five-router ring (router-a…router-e, direct veth pairs, `remote-lfa` on all): every `nos-ribd` builds its `rlfa100` IP-in-IP device, router-a installs a backup for router-b's loopback that tunnels to router-d's loopback (the one PQ node; `backup_tunnel` in `GET /v1/routes/rt1`), and cutting router-a's link to router-b carries a ping from its VRF as IP-in-IP through router-d (`tcpdump` there) until SPF moves the primary to router-e; the link back restores both with no daemon restart, and turning `remote-lfa` off on router-d deletes its device. The cut logs `ospf link kernel interface down … reason=absent` within 5s and the primary moves within 15s; a `nos-interfaced` kill on router-a plus an in-place config change keeps every link and adjacency (`keeping running link`, no `ospf link stopped`, no neighbor down); `ip link set eth2 down` on router-b is seen as `admin-down` there and `no-carrier` on router-a within 5s with no dead timer expiring, and `up` brings `Full` back (#277)

## OSPFv3

Same lab as OSPFv2, with `ospfv3 <profile>` on the same attach points (no conflict between the protocols; a domain carries independent `ospf_profile`/`ospfv3_profile`). `ospfv3-dr` reuses `ospf-dr`'s third router. `ospfv3-auth` and `ospfv3-instance-id` reset their settings so `ospfv3-dr` can reuse the profile with a keyless router-c.

- `ospfv3`: checks that declaring a basic `Ospfv3Instance`/`Ospfv3Area`/`Ospfv3Profile` (RFC 5340, IPv6 OSPF — see `docs/protocols/ospfv3-internals.md`, if present, or the OSPFv3 Phase 1 plan) and attaching that profile to both routers' own eth0 tag-0 subinterface (`ospfv3 <profile-name>`, the same subinterface already carrying OSPFv2's `ospf <profile-name>` and the BGP session's own address, no conflict between the three) actually gets `nos-watchdogd` to dynamically spawn a real `nos-ospfv3d` process for each instance, which itself resolves its own instance/area/profile config over a real IPC round trip to `nos-configd`, exchanges real RFC 5340 Hello/DBD/LSR/LSU/LSAck packets over a real VRF-scoped raw IPv6 protocol-89 socket between the two containers, reaching neighbor state `Full` on both sides, and that attaching the same profile to one router's own loopback interface (a destination with no neighbor of its own) gets the other router's own real RFC 5340 §4.8/§16 SPF computation (the loopback /128 is originated with the LA prefix option, #49) to derive the correct IPv6 next-hop purely from the LSDB's Link-LSAs (never a live neighbor table) and push the computed route to its own `nos-ribd` for real kernel installation, then that switching both to RFC 8362 extended LSAs gets each to originate the E-LSAs the peer installs and to prematurely age (RFC 2328 §14.1) its legacy set, which the peer flushes until no legacy LSA from it is left (#149); then (#276) a second link `eth1.0` over a direct veth pair reaches `Full`, a `nos-interfaced` kill on router-a plus an in-place config change keeps every link and adjacency (`ospfv3 link resolution failed, keeping running link`, no `ospfv3 link stopped`, no neighbor down), `ip link set eth1 down` on router-b is seen as `admin-down` there and `no-carrier` on router-a within 5s with no dead timer expiring, `up` brings `Full` back, and deleting the veth logs `reason=absent` within 5s
- `ospfv3-asbr`: checks that one routing table redistributes into OSPF and OSPFv3 at once (#222: an IPv4 static with `redistribute ospf`, an IPv6 static with `redistribute ospfv3` on router-a) so it originates a Type-5 and a real RFC 5340 AS-External-LSA (or its RFC 8362 form), router-b installs both and two real kernel routes, and removing the OSPFv3 rule prematurely ages only its LSA (the Type-5 and its route stay), then removing the OSPF rule flushes the Type-5 within seconds, and that router-b's OSPFv3 acks are delayed and batched (RFC 2328 §13.5: some `ospfv3 lsack sent` batch was held a second or more)
- `ospfv3-abr`: checks that router-b's IPv6 loopback in a second `Ospfv3Area` makes it a real ABR originating an Inter-Area-Prefix-LSA router-a installs and routes to over a real kernel route, flushed with the route within seconds once the loopback leaves
- `ospfv3-lsinfinity`: self-contained; a control run installs router-b's ABR loopback and redistributed static on router-a, then a run with `nos-ospfv3d --originate-lsinfinity` (hidden, test-only) shows router-a holding both LSAs at metric `0xFFFFFF` while neither route is installed
- `ospfv3-lsinfinity-asbr`: self-contained, three routers on two docker networks (router-b is the only ABR, router-c an ASBR attached to router-b's area-1 link only); the flag goes to router-b alone because router-c originating an infinite AS-External would prove the wrong skip; mutation check: dropping `&& r.metric < LS_INFINITY` in `asbr_distance` must make the infinity run fail
- `ospfv3-graceful-restart`: RFC 5187 graceful restart: with `graceful-restart grace-period 120` on router-a, a SIGTERM to its `nos-ospfv3d` sends a real Grace-LSA before exiting, router-b enters helper mode, holds the adjacency (no teardown logged) and router-a's loopback route (no kernel removal) through the whole restart, and resynchronizes to `Full` with the respawned process
- `ospfv3-auth`: checks that a matching RFC 7166 HMAC-SHA-256 authentication-trailer key (SA ID 300 — above OSPFv2's one-octet classic key-id range, proving the 16-bit field is real) configured on both routers' shared point-to-point `Ospfv3Profile` reaches/stays `Full` with real per-packet trailer verification (AT-bit set, checksum omitted per RFC 7166 §4.2, digest bound to the IPv6 source), that a mismatched key on either side produces a real logged digest-verification failure and blocks any new `Full` adjacency, and that reverting to a matching key lets a fresh `Full` adjacency form again with no anti-replay drops — then clears the key on both so `ospfv3-dr` can reuse the profile with a keyless router-c
- `ospfv3-mtu-mismatch`: the same over ospfv3: dbd rejected, no full; mtu-ignore reaches full; both cleared
- `ospfv3-instance-id`: RFC 5340 §A.3.1 Instance ID enforcement: `instance-id 1` on router-a's `Ospfv3Profile` alone gets router-b to drop its packets (`ospfv3 packet instance id mismatch, dropping … received=1 expected=0`) with no new `Full`, `instance-id 1` on both reaches `Full` again, and both are reset to 0 for `ospfv3-dr`'s router-c
- `ospfv3-p2p-rid-change`: #957: router-b's router-id changes `9.9.9.10` -> `9.9.9.11` from the same link-local address; router-a logs `ospfv3 neighbor evicted, same address new router id … neighbor=<old>`, `ospfv3 neighbor reached full … neighbor=<new>`, `ospfv3 neighbor entry removed … neighbor=<old>` (one dead interval later) and `added route` for router-b's loopback; then the original id is restored the same way so `ospfv3-bfd`/`-dr`/`-lfa` keep their constants. Mutation check: re-adding a shared p2p deadline or dropping the `Down` removal makes it fail.
- `ospfv3-bfd`: the same over `nos-ospfv3d` (`killing ospfv3 neighbor`, peer `fe80::...`, `ipv6` filter); router-b's loopback is `OSPFV3_LFA_LOOPBACK_ADDRESS`.
- `ospfv3-dr`: checks that attaching the same `Ospfv3Profile` a second time to the same `BroadcastDomain` bridge `ospf`/`ospf-dr` already stood up (a domain carries independent `ospf_profile`/`ospfv3_profile` fields, so both protocols' Hello/election/adjacency run over the identical real Linux bridge with no conflict) reaches the identical real RFC 2328 §9.4 DR/BDR election outcome and §8 DrOther-Full-adjacency restriction over the new address family too — and, since router-a/b each run a second OSPFv3 link (`eth0.0`) in the same area while router-c is on the bridge only, that router-c's `GET /v1/ospfv3/database` (checked right at `Full` and again after a periodic full resend) holds router-a's/router-b's Link-LSAs tagged with the bridge link only, never `eth0.0`'s: RFC 5340 §4.5.1 link-local flooding scope (#46); and (#879) the same flood-destination logs and loopback-LSA delivery proof over `ff02::6`/`ff02::5`
- `ospfv3-lfa`: router-a gets a loop-free alternate via router-c for router-b's ospfv3 loopback; nos-ribd installs the link-local backup with its own interface at a metric above the primary's, then removes both
- `ospfv3-flush`: RFC 2328 §13.4/§14.1 withdrawal of LSAs a router no longer originates: router-a and router-c leave the bridge, so router-b — its DR — loses its last `Full` neighbor there and prematurely ages its (E-)Network-LSA, which router-a, still adjacent over `eth0.0`, flushes within seconds rather than at `MaxAge` an hour later Then (#731, §13.4) a SIGKILLed router-b restarts with an empty LSDB, gets its own Router-LSA back from router-a with a newer sequence number and re-originates above it (`ospfv3 self-originated lsa received with newer sequence`, then `ospfv3 lsa originated ... reflected=true`).
- `ospfv3-mtu-pagination`: an ospfv3-profile mtu override (200, no dbd-max-headers flag) drives a real multi-packet ospfv3 dbd exchange; router-a redistributes 20 statics, logs `ospfv3 lsu split packets=<n>` (LSU/LSR/LSAck cut to `mtu - 40 - 16 - 4 - trailer`, #807) and router-b learns the last prefix
- `ospfv3-router-lsa-split`: self-contained; router-a/b are Full over `eth0.0` and the bridge (two Router-LSA links on router-a, no router-c); the daemon flag caps links per fragment at 1, so router-a logs `ospfv3 router-lsa split`, `GET /v1/ospfv3/database` lists Router (0x2001) or E-Router (0xA021) LSAs with IDs router-id and `0.0.0.1`, and router-b logs installing fragment `0.0.0.1`; which link sits in which fragment is not asserted (HashMap order)

## PKI

`pki` runs on the standard lab; `pki-rotation` restarts the routers with `--pki-leaf-lifetime=20 --pki-rotate-every=6`. Details of the PKI itself: `pki/CLAUDE.md`.

- `pki`: checks that the watchdog and four daemons (`nos-configd`, `nos-logd`, `nos-bgpd`, `nos-ribd`) each run as their own uid (`starting ... uid=` and `/proc`), that the `nos-bgpd` uid cannot `rm` `nos-logd`'s socket (sticky `/run/nos`) and that the socket is `0660 nos-logd:nos`, every daemon holds the certificate identity `nos-watchdogd` minted for it (`nos://configd/`, `ribd/rt1`, `bgpd/<instance>` in each daemon's own startup log line), that every IPC handshake negotiated the hybrid `X25519MLKEM768` key exchange with ML-DSA-65 certificates and none anything else, that `nos-provision` — the image's scriptable client, which logs in like `nos` does — is refused with a wrong password (the watchdog logs `login rejected`) and, with the right one, receives a certificate on a key it generated and commits a transaction as that user (`login accepted`), that revocation reaches every daemon — a throwaway user's saved certificate (`nos-provision --pki-cert-out`/`--pki-cert-in`) opens `nos-configd` until the user's password changes, is refused after it (`certificates revoked role=user`, `nos-configd` logging a revoked-certificate handshake failure) while a login with the new password works, and is refused again once the user is deleted, that the same user's REST certificate is refused with 401 after the password change while a fresh REST login works, and that a burst of 200 concurrent REST logins on distinct usernames (#381) is answered with only 401/429 (the per-address limit of 20 failures in 60s kicks in, even a right password gets 429 until the window ends), `nos-watchdogd` does not restart and a good login works again afterwards, that killing `nos-ribd` revokes its certificate (`certificates revoked role=ribd name=rt1`, `ipc crl updated`) while the restarted one still answers a REST route query, and (#718) with no route change `nos-bgpd` notices the closed push connection itself, re-sends `sent initial bgp route snapshot to nos-ribd` and the learned route is `added route` again in the kernel
- `pki-crl`: router-a only, a dedicated `crl-user` (created, then deleted). `nos-provision --login-burst 30000` logs in 4 at a time on fresh connections and keys (the broker verifies 2 passwords at once and answers `LOGIN_BUSY` after 5s, which the tool retries); a password change then revokes all 30,000 serials in one CRL (~1.17 MB, over the old 1 MiB frame cap, which silently stopped rotation in every child). The phase waits for `certificates revoked ... serials=30000` and `ipc crl updated entries=3xxxx`, asserts no `identity pipe broke` for 60s and that BGP and a REST read still work. The burst has a 45 min deadline; the 8 h user-certificate lifetime keeps entries from expiring first.
- `pki-rotation`: checks that hot rotation really keeps long-lived daemons connectable: after waiting out a whole lifetime, `nos-ribd` is killed and the watchdog restarts it with a fresh identity, router-b has advertised a prefix beforehand, and router-a's *long-lived* `nos-bgpd` — which can only handshake with the new `nos-ribd` using a rotated certificate, its original one having expired — reconnects its route push on its own (no new route needed, #718) and gets the prefix installed as a real kernel route, rotation frames carry no CRL (`identity pushed … crl_bytes=0`) while the revocation from the kill is pushed once (`crl_bytes=[1-9]`, #858), all with REST (a per-request client of `nos-configd`) provisioning on rotated identities; and the IPC session cap (#637): a `nos-provision` login renews (`--renew-probe`) inside `--pki-ipc-session-max`, and past it the renewal is refused (`renewal refused, ipc certificate unknown or past the session cap`) while a fresh password login works

Per-daemon RSS and the container cgroup (`memory.current` vs `memory.max`) are logged at each sample; `LOGD_MEM_ROUTER=b cargo run -p nos-e2e -- logd-mem` prints the same on router-b.
