# REST daemon internals

How `nos-rest` is built, moved from `rest/CLAUDE.md` (#264) so the always-loaded file keeps only rules and pitfalls. The rules to respect when editing the crate are in [`rest/CLAUDE.md`](../../rest/CLAUDE.md).

## Authentication (`auth.rs`, `login.rs`)

Mutual TLS replaces per-request credentials: the password crosses the network once, at login, and every later request carries only the client certificate.

- **Getting a certificate.** `POST /v1/login {user, password, csr}` — the only route reachable without one — sends the password and a base64 DER PKCS#10 request for an ECDSA P-256 key the client generated (`openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout key.pem -outform DER | base64 -w0`). `nos-restd` forwards it to the watchdog (`WatchdogRequest::RestLogin`, allowed for `restd` only), which verifies it exactly as it does for `nos` (`nos_password::verify_or_dummy`) and returns a `user/<name>` certificate from the **REST CA** for the public key in the CSR — the client's private key never leaves it. `POST /v1/renew {csr}` trades the certificate the connection presented for a fresh one (`RestRenew`; refused once the user is deleted, the certificate is revoked, or the login is older than `--pki-rest-session-max`, 7 days: the renewed certificate inherits the password login's start time); lifetime is `--pki-user-lifetime`, renew at half of the `lifetime_secs` in the reply. Clients trust the REST CA from `rest-ca.crt` in the watchdog's `--pki-dir` (`/run/nos/pki`) — distribute it out of band; it is never served over the network, because fetching a trust anchor over an unauthenticated connection would let whoever intercepts that fetch also capture the login password.
- **Revocation.** The REST CA has no CRL. The watchdog keeps an allowlist of live REST certificates by hex serial (`Pki::rest_session`), and `client_auth` asks it per request (`RestCertCheck { user, serial }`, `restd` only; `Ok` or `Denied("session expired")` is 401). A password change or deletion drops the user's entries, the same trigger as the IPC CRL; a watchdog restart empties the list along with the CA. `Accepted.serial` (`nos_pki::rest`) carries the serial from the handshake into `PeerUser`.
- **Failed logins.** One attempt at a time *per username* (`LoginGate`), and a failed one costs 1s before the next may start — however many streams or connections the guesses arrive on. The broker's own per-connection throttle only covers a direct `Login`: `RestLogin` arrives over `nos-restd`'s shared connection, so the delay has to be here. Many usernames in parallel are bounded elsewhere (below). After 5 failures within 60s (counted from the first; a success resets it) further attempts on that username *from the same source address* get `429` with `Retry-After` (RFC 6585) straight away — no watchdog call, no delay, even with the right password. The lockout is keyed `(source address, user)` (#635), so an attacker elsewhere cannot block the real user's login; one sharing the user's NAT address still can (accepted). It never blocks `renew` or certificates already issued. Without a peer address (tests only) all requests share one key.
- **Login flood (#381).** Per source address, 20 failures within 60s (all usernames; a success does not reset it; at most 4096 addresses tracked) give `429` before any work; the limit is above the per-user one because NAT puts many users behind one address. Plus two global bounds, whatever the usernames or addresses: `LoginGate` allows 8 logins in flight (more get `429`, `Retry-After: 1`, before any IPC), and `nos-watchdogd` runs at most 2 argon2 verifications at once (64 MiB x 4 threads each), queueing others up to 5s, then `Denied("login busy")`, which REST maps to `429` too. A busy refusal is not `invalid credentials`: it counts toward no lockout.
- **Every other route** (`client_auth`, the **last** `.layer(..)` in `api::router`, so it wraps the merged Swagger UI, `/openapi.json` and the SSE stream too): the TLS layer has already verified the certificate against the REST CA and `listen.rs` has attached the user its URI SAN names to every request of that connection (`PeerUser`, a request extension). Here the user must also **still exist in the running config** — one cheap `Request::UserExists { name }` to `nos-configd` per request (#755; the server scans the users under the read lock, no config clone or transfer) — so deleting a user locks their (still-valid) certificate out on the very next request, even on a connection that is already open. No verified user is `401` (with `WWW-Authenticate: Mutual realm="nos", login="/v1/login"` — a custom scheme name, since a client certificate has no registered one; it names the flow that gets one), an unreachable `nos-configd` is `503` (fail closed). An open SSE stream is authenticated at connect time only. ponytail: one pooled `UserExists` round trip per request, no cache (a cache would break "locked out on the very next request").
- `ApiDoc` declares the `mtls` security scheme (`MutualTlsScheme`, `SecurityScheme::MutualTls`) and a global requirement; `login` is `security(())`. Browsers can present a REST certificate (it is ECDSA P-256 on purpose), so Swagger UI works once one is imported; `curl` needs `--cert/--key/--cacert` and a curl/OpenSSL new enough to offer `X25519MLKEM768`.
- Users appear in the generated config tree like any section (`/v1/transactions/{tx}/user/{name}`); a clear `password` in a `PUT` is hashed by `nos-configd`, and `GET /config` returns the hashes (behind auth).

## Transport (`listen.rs`, `tls.rs`, `ipc.rs`)

- **Listener.** After the VRF bind, `tls::start` asks the watchdog for a server certificate for the bound address (`IssueRestServerCert`, on a key generated here, IP SAN from the config — never from the CSR) and renews it at half its life. Each accepted connection gets its own task: TLS handshake (`nos_pki::rest::RestServer::accept`, 5s timeout — a slow peer never stalls accept), then hyper-util's `auto::Builder` (HTTP/1.1 + HTTP/2; 128 concurrent streams, 30s h2 keep-alive, 10s header-read timeout) with `Extension(PeerUser)` on every request. Shutdown is graceful, capped at 2s by `stop()` so a keep-alive client can't hold a rebind hostage. A client that offers only classical key exchange, or a certificate from another CA, never gets a request through.
- **One connection, many requests.** HTTP/2 multiplexes concurrent requests over one TLS handshake; a client should reuse its connection pool.
- **Behind it, IPC connections are pooled** (`Daemons::call` in `ipc.rs`). Every IPC connection is a mutual-TLS handshake, and a request used to cost three (the config check for auth, the broker to resolve, the daemon itself). Now a finished call parks its connection (up to 8 idle per daemon, discarded after 5 minutes) and the next call to that daemon reuses it, and broker answers are cached (socket paths are fixed per daemon name; a failed call drops the entry, and a "not running" answer is never cached). The one rule this leans on: **a plain request gets exactly one event back, and the server keeps reading requests on the same connection** — true of every daemon's server; streaming replies (`LogRequest::Tail`) use `open_stream` and a connection of their own. A parked connection whose daemon restarted shows up as "dead before any reply" and is retried once on a fresh connection; only that case is retried, so a request the daemon received is never sent twice.

- **Limits (what a client sees).**
  - 256 open connections (`listen::MAX_CONNECTIONS`, handshaking or serving): the 257th is closed straight after `accept`, before any ML-KEM work; the client sees a reset/EOF. Logged as a rate-limited `warn!`.
  - 30s per request (`api::REQUEST_TIMEOUT`), covering the handler and the request body read: `408` problem document. A streamed reply (`GET /v1/logs/follow`) only has to start within it.
  - 20s per daemon call (`ipc::IPC_TIMEOUT`, send and reply each): `504` "a backend daemon did not answer in time". The connection is dropped, not parked or retried.
  - Failed TLS handshakes are `warn!` lines rate-limited per peer IP (`ratelimit::LogLimiter`: burst 3, one more per 10s, `suppressed=N` on the next line, 1024 peers tracked). No per-peer refusal; the connection cap bounds the CPU cost.
  - All four are constants, not config.

## Listening (`listen.rs`)

Every 1s tick — and immediately on a routing-table config diff — `Listener` compares what config *wants* (this table's `rest_api`, read with the cheap `Request::GetRestApi { table }`, not a full-config fetch, #759/#758) with what is *bound* and converges:

- the VRF name comes from the owning `nos-ribd` (`ServiceRef::RibTable` + `RibRequest::GetVrfName`), exactly like `nos-bgpd`; `None` means "not created yet" and is retried;
- the socket is bound to `address:port` (no wildcard) with `SO_BINDTODEVICE=<vrf>` (a per-crate copy of `nos-bgpd`'s `tcp::bind_listener`);
- an address that isn't configured on an interface in the VRF yet (`EADDRNOTAVAIL`) is a transient state, retried each tick and logged once per change (`rest api not listening yet: …`);
- a changed address/port, or a VRF that was deleted and recreated under the same name (its `nos-ribd` restarted — detected by the device's `ifindex` changing, since `SO_BINDTODEVICE` resolves the name once), drops and rebinds the listener;
- a `nos-configd` read failure keeps the current listener rather than tearing it down.

Log lines the e2e phase greps: `rest api listening table=… vrf=… address=… port=…`, `rest api stopped listening`, `rest api not listening yet: …`.

## Endpoints (`/v1`, see `api.rs`)

Auth (POST): `/login` (no certificate needed), `/renew`. Show (GET, the daemon's own reply payload as JSON): `/config`, `/fdb/{domain}` (a broadcast domain's `nos-fdbd` forwarding database), `/routes/{table}[/{addr}]`, `/interfaces[/{name}]`, `/port-aggregates[/{name}]`, `/lacp[/{name}]`, `/lldp/neighbors`, `/logs?source=&limit=`, `/logs/follow?source=&limit=` (`show log --follow` as Server-Sent Events: the backlog — trimmed to `limit` — then each new entry as an `event: log` whose data is the JSON `LogEntry`, until the client disconnects; the daemon-side `Tail` connection's write half is held open for the stream's lifetime), `/bgp/summary`, `/ospf/{neighbors,database}`, `/ospfv3/{neighbors,database}`. The router-wide ones (`bgp`/`ospf`/`ospfv3`) iterate the instances in the running config (names only, via `Request::ListBgpInstances`/`ListOspfInstances`/`ListOspfv3Instances`, #759 — only `GET /v1/config` still uses `Request::Get`) and report a per-instance `"not running"` instead of failing, like `nos-cli`. A daemon that isn't reachable is `503`. **Actions** (`clear.rs`, `POST`, change live state never config): `/bgp/{instance}/peer/{peer}/soft-in` = `clear bgp <instance> <peer> soft-in` — asks the live session for an RFC 2918 ROUTE-REFRESH (`route_refresh: "sent"`), or, for a peer-group with soft reconfiguration inbound, `route_refresh: "none"` plus `reevaluated` (per-family counts; a superseded pass is `503`); 404 if the peer isn't configured or has no `Established` session (the daemon doesn't distinguish the two), 503 if that instance's `nos-bgpd` isn't running. `/bgp/{instance}/peer/{peer}/clear` = `clear bgp <instance> <peer>` — releases a maximum-prefix hold and resets an Established session (`BgpRequest::ClearPeer`); 404 only if the peer isn't configured.

**Transactions — the config tree is the URL tree:**

| | |
|---|---|
| `POST /transactions/<tx>?base=blank\|current` | open or resume (201 / 200) |
| `GET` / `PUT` / `DELETE /transactions/<tx>` | whole in-progress config / set the whole config / discard |
| `GET` / `PUT` / `DELETE /transactions/<tx>/<path>` | read / set / remove one subsection |
| `GET /transactions/<tx>/diff`, `POST …/commit` | diff vs running; validate + commit (422 on a validation error, transaction kept; `ConfigError`s whose message starts `validation failed` also map to 422: no users left, bad syslog trust anchor, masked secret with nothing to keep, too many clear passwords, #675) |
| `POST /config/save` | `Request::Save` — persist the running config (the CLI's `save`), 204; a failed write is 502 (`tx::save` remaps `from_config`'s 400, the client did nothing wrong). Never implied by a commit |
| `ETag` / `If-Match` / `If-None-Match` | every transaction reply is tagged with its generation; `PUT`/`DELETE`/commit/`GET` with a stale or weak `If-Match`, or any `If-Match` on a missing transaction → 412; `GET` with a matching `If-None-Match` → 304 (see below) |

**Optimistic concurrency (RFC 9110 §8.8, §13.1).** Every reply that describes a transaction — `POST` (open/resume), `GET` (whole or subsection), a successful `PUT`, a subsection `DELETE`'s 204 — carries a strong `ETag`: the transaction's `generation` (`TransactionSnapshot.generation`, a per-transaction counter `nos-configd` bumps on every `ApplyOp`/`EditTransactionPath`) as a quoted decimal, `"17"`. It is per *transaction*, not per subsection, on purpose: the store serializes on one mutex entry per transaction, so that is the real conflict domain, and two clients editing disjoint paths of the same transaction still conflict. `PUT`, `DELETE` and `POST …/commit` honour an optional `If-Match` (`*`, or a comma list of entity-tags, strong comparison so a weak tag never matches; an opaque or non-numeric tag is valid and never matches; only malformed syntax is 400): it travels as `if_match: Option<Vec<u64>>` (strong numeric tags only; empty = never matches) on `EditTransactionPath`/`DiscardTransaction`/`CommitTransaction` and is checked by `nos-configd` under the same transactions lock as the edit (a real compare-and-set), a mismatch being `ConfigError::PreconditionFailed` → **412** with nothing changed (a refused commit keeps the transaction open, like a 422). `*` maps to no store-side precondition; `tx.rs`'s `missing_tx` turns the store's "no transaction named" 404 into **412** whenever an `If-Match` was sent (RFC 9110 §13.1.1: no current representation), while a missing config path stays 404. `GET` evaluates `If-Match` first against the snapshot it read (412), then `If-None-Match` (`*` or a list, weak comparison) and answers **304** with the `ETag` and no body when it matches. Both are opt-in: a caller that sends neither (`nos-cli`'s `ApplyOp`, `nos-provision`) keeps last-write-wins. `nos-e2e`'s `Router::edit` sends `If-Match` on its `PUT` and commit, so every provisioning phase exercises the matching path; the `rest` phase (`rest_etag`) proves the 412/304 paths against the real daemon. The tags are `tx.rs`'s `etag`/`Condition`; a discarded transaction's 204 carries none.

`<path>` is e.g. `hostname`, `routing-table/rt1`, `bgp-instance/r1/peer-group/pg1`, `ospf-instance/o1/area/0.0.0.0/profile/p1`, `static-routing-instance/s1/route/10.1.0.0%2F16`. The grammar lives in `nos_proto::config_path` (segment = kebab-case field name, a list field is followed by the element's key; a `PUT` to a list element that doesn't exist appends it; the body's key must match the URL). `diff` and `commit` are static routes and therefore reserved first segments. The handlers split the **raw** URI path before percent-decoding, so a key containing `/` stays one segment. The server-side edit is one `nos-configd` request, `Request::EditTransactionPath` (its reply carries only the edited subsection, which `tx.rs` masks with `nos_proto::redact_at`, #774) — atomic under the transactions lock, all-or-nothing (the edited JSON must still deserialize as a `Config`), and, like every op, unvalidated until commit.

## OpenAPI (`openapi.rs`)

`GET /openapi.json`, browsable at `/swagger-ui/` (`utoipa-swagger-ui` with the `vendored` feature: assets are embedded in the binary, so there is no CDN dependency at runtime or GitHub download at build; it is pointed at the `/openapi.json` route rather than given a `utoipa` struct, so it shows the generated config-tree paths too). Show and transaction-root operations are `#[utoipa::path]`-annotated and registered with `routes!`, so the router and the spec can't disagree. The config-tree paths are **generated** by walking the `Config` schema (the router serves them all with one `{*path}` route) using `config_path::{field_segment, key_field}` — the same naming and key rules the server resolves paths with; the walker debug-asserts `field_matches` for every path it emits and tests check every parameter is declared and every `$ref` resolves. `nos-proto`'s `openapi` feature adds `ToSchema` derives (off unless `nos-rest` is built); `IpAddr`/`IpNet` fields carry `schema(value_type = String)`, and the recursive `SectionDiff.subsections` needs `schema(no_recursion)`. Adding a config section needs no OpenAPI work; adding a *show* endpoint needs a `#[utoipa::path]` and a `routes!` line. Any change to the document fails `tests/openapi_snapshot.rs` until `make docs-fix` rewrites the checked-in copy, `docs/openapi.json`, which the user docs (`docs/api.md`) link to.

## Errors and response headers (`error.rs`)

- 502 and 503 carry a fixed `detail` (`a backend daemon returned an unexpected reply` / `a backend daemon is unavailable`); the specific string (socket path, daemon reply variant) is logged with `warn!` to nos-logd only.
- A per-instance `show` report entry that failed carries `daemon error`, not the error's `Debug`.
- `security_headers` (outermost layer) adds `X-Content-Type-Options: nosniff` to every response and a `Content-Security-Policy` to `/swagger-ui*` only.
