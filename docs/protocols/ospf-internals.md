# nos-ospf internals

How `nos-ospf` implements OSPFv2: functions, data structures, log lines to grep for, `ponytail:` ceilings and the not-done lists. For configuration and behaviour see [OSPF](ospf.md); the rules to respect when editing the crate are in [`ospf/CLAUDE.md`](../../ospf/CLAUDE.md). OSPFv3 is in [OSPFv3 internals](ospfv3-internals.md). Which `nos-e2e` phase covers what is in [`docs/e2e-phases.md`](../e2e-phases.md).

## Scope

`nos-ospfd` resolves its own configured instance/areas/profiles from `nos-configd`, and runs a real RFC 2328 Hello protocol on every `Subinterface.ospf_profile` (point-to-point) and `BroadcastDomain.ospf_profile` (multi-access, with RFC 2328 §9.4 DR/BDR election) attach point — a real raw protocol-89 socket, VRF-scoped, joined to the AllSPFRouters (224.0.0.5) multicast group (and, only while DR/Backup, AllDRouters 224.0.0.6). Adjacency formation now reaches real `Full` state with real LSAs, matching how `nos-bgp` grew from OPEN/KEEPALIVE-only into real route exchange:

- **Neighbor FSM depth**: `Down` → `Init` → `TwoWay` → `ExStart` → `Exchange` → `Loading` → `Full` (`ospf::neighbor::NeighborState`), on both network types — the full RFC 2328 §10.5 ladder. `TwoWay` only advances to `ExStart` once RFC 2328 §7.5/§10.4's adjacency-eligibility rule holds (`link::should_form_adjacency`): unconditionally true on point-to-point; on a broadcast link, only for a DR/BDR-involving pair (a `DrOther`-`DrOther` pair stays at `TwoWay` forever). From `ExStart` onward, `ospf::exchange` drives RFC 2328 §10.6-10.8's DBD master/slave negotiation and summary-list exchange, then real LSR/LSU/LSAck against a per-area `ospf::lsdb::Lsdb` (see below) — now with real RFC 2328 §16.1/§16.2 SPF route computation over what lands in it (`ospf::spf`, see "SPF and route installation" below).
- **Network type**: `Subinterface.ospf_profile` attach points (a VLAN sub-interface modeling one link to one peer) run point-to-point — at most one neighbor, no election, `link::InterfaceState` fixed at `PointToPoint`. `BroadcastDomain.ospf_profile` (multi-access SVI) attach points run broadcast — potentially many neighbors keyed by router-id, a `Waiting` interface state on start (wait-timer = dead-interval), then a real DR/BDR election (`ospf::election::elect`) settling into `Dr`/`Backup`/`DrOther`. **Point-to-multipoint** (RFC 2328 §9.5, `OspfProfile.network_type = PointToMultipoint`, never a default): Hello stays multicast and has no DR/BDR/mask check, `InterfaceState` is `PointToPoint`, and every discovered neighbor forms an adjacency (`should_form_adjacency` is unconditional). Dead timers run on the broadcast 1s `sweep_dead_neighbors`, not the single p2p deadline. `router_lsa_links` follows §12.4.1.4: a type-1 link per `Full` (or grace-held) neighbor plus one type-3 stub for our own address with mask 255.255.255.255 (not the subnet's; omitted under prefix suppression); SPF is unchanged. `neighbor_summaries` is one row per known neighbor, none while empty. OSPFv3 rejects it at commit (`valid_profile_timers`); NBMA, static neighbor lists and unicast Hello are not built. Verified by `nos-e2e ospf-p2mp`. A loopback (`Interface.ospf_profile`) attach point still has no peer to Hello with and stays **log-only**, resolved purely from the already-fetched `Config` (`reconcile::attach_points_for`). Hello stays multicast 224.0.0.5 on both real network types (RFC 2328 has no unicast Hello); DBD/LSR and retransmitted LSUs are unicast to the specific neighbor's IP (captured from the source address of its last Hello). On broadcast links the periodic LSU flood and the delayed LSAck are multicast instead (#879, RFC 2328 §13.3 step 5/§13.5): a DR or Backup sends to 224.0.0.5, any other router to 224.0.0.6, via `OspfSocket::send_all_drouters` and `LinkSocket::send_flood`; point-to-point, point-to-multipoint, virtual links and the Grace-LSA stay unicast.
- `OspfProfile.network_type: Option<NetworkType>` overrides the type an attach point gets when set; left `None`, it defaults per attach-point kind (`Subinterface` → `PointToPoint`, `BroadcastDomain` → `Broadcast`) — resolved in `reconcile.rs`, not the schema, since one profile can be referenced by attach points of different kinds at once. Never validated against the attach point's actual kind (real OSPF allows forcing either behavior on either kind of link).

`OspfProfile` carries `hello_interval`/`dead_interval`/`priority: Option<u16|u8>` (`None` defaults to `HELLO_INTERVAL_DEFAULT`/`DEAD_INTERVAL_DEFAULT`/`PRIORITY_DEFAULT` — 10s/40s/1, RFC 2328 Appendix C.3), `hello_interval`/`dead_interval` validated (`dead_interval` must exceed `hello_interval` when both are set) the same way `BgpPeerGroup.hold_time`/`keepalive_interval` are, one level up on `OspfArea.profiles` (`ospf_profile::valid_profile_timers`). `priority` governs DR/BDR election eligibility on a `Broadcast` link (`0` means "never eligible") and is sent on the wire (functionally inert) on a `PointToPoint` one too. `cost: Option<u16>` (range `1..=65535`, `None` defaults to `1`) is a real RFC 2328 §16 SPF metric: `link::originate::router_lsa_links`/`originate_router_lsas` use it as this link's (or loopback stub's) Router-LSA link metric, summed along the Dijkstra path by `ospf::spf::compute`. All five fields plus `auth` (see "Authentication" below) are `nos-cli`-editable (`set hello-interval|dead-interval|cost|priority|network-type|simple-password|crypto-key ...` while navigated into an `OspfProfile`, or the fully-qualified form from anywhere — mirrors `BgpPeerGroup.hold_time`'s exact CLI precedent). RFC 2328 Appendix C.3's `RxmtInterval` (how often an unacknowledged LSR/LSU is resent) is a fixed 5s constant (`link::RXMT_INTERVAL`), not yet a sixth `OspfProfile` field — see `link.rs`'s own `ponytail:` note on why.

### Authentication

`OspfProfile.auth: Option<OspfAuth>` is RFC 2328 Appendix D authentication, mirroring `BgpPeerGroup.auth: Option<BgpAuth>`'s exact shape (`OspfAuth::Simple { key }` / `OspfAuth::Crypto { keys: Vec<OspfCryptoKey> }`, `None` == AuType 0/Null) — `key` is the label of an admin keystore entry (#509), never the secret; `nos-ospfd` resolves it with `Config::key` (a dangling label skips the link, fail-closed) and subscribes to `DiffScope::Admin`, so rotating a secret restarts the link. `OspfCryptoKey.algorithm: OspfCryptoAlgorithm` covers both RFC 2328 Appendix D.3's original plain-MD5 scheme (`Md5`, `MD5(packet || key)`, 16-byte digest, no real HMAC construction) and RFC 5709's HMAC-SHA extension (`HmacSha1`/`HmacSha256`/`HmacSha384`/`HmacSha512`, real HMAC per RFC 2104, 20/32/48/64-byte digests) — the wire's AuType is `2` for all five; there's no separate algorithm field on the wire, so a packet's Key ID alone must unambiguously determine which algorithm a receiver uses, exactly like `BgpAoKey`'s key-rotation model (`is_current` marks the key that signs outgoing packets; every configured key is still accepted on receive, looked up by the wire's own Key ID — this is what allows graceful key rollover with no dropped adjacency).

`ospf::packet` (see the Modules table) owns the wire-level mechanics, kept dependency-free of `nos-proto` like the rest of that "pure, no I/O" module — `packet::CryptoAlgorithm` is its own mirror of `nos_proto::OspfCryptoAlgorithm`, converted at the config boundary in `link::LinkAuthConfig` (`reconcile.rs`'s `resolve_auth`). `packet::checksum` now correctly excludes the 8-byte Authentication field (bytes 16..24) from its RFC 1071 sum for Null/Simple auth — a no-op for Null (those bytes are already zero) but load-bearing for Simple, whose password occupies that field on the wire; Crypto auth skips the checksum entirely (RFC 2328 D.4.3: not calculated for that AuType) and instead appends a real digest (`CryptoAlgorithm::digest`, using the `md-5`/`sha1`/`sha2`/`hmac` crates) after the packet, outside the packet's own `length` field's count — `verify_auth` is the shared decode-side counterpart, rejecting an AuType that doesn't match the link's configured policy (`PacketError::AuthTypeMismatch`) or a bad password/digest/unknown Key ID (`PacketError::AuthFailed`).

RFC 2328 D.4.3's anti-replay crypto sequence number is deliberately **not** tracked in `packet.rs` (which stays fully stateless) — `link.rs` owns it instead, since it already owns all other per-neighbor state: `NeighborInfo.last_crypto_seq` records the last-accepted value per neighbor, checked/updated once in `run()`'s single inbound decode call site (`accept_crypto_sequence`, generic across all five packet types via `packet::router_id`) before any `handle_*` dispatch — a non-increasing sequence number is silently dropped and logged (`"ospf packet crypto sequence number not increasing, dropping"`), never treated as a fatal error. The outgoing counter (`next_crypto_seq`, threaded as `&mut u64` through every send path) is seeded from wall-clock unix-seconds at link startup (`crypto_seq_floor`) and bumped by one per packet sent — floored at the current wall-clock value on every bump, so it never regresses even across a link restart (an auth/key change is just another `LinkConfig` field change, so it restarts the link task exactly like any other — the peer rejects the new auth until it's updated too, which is the desired match/mismatch behavior; auth failures log distinctly as `"ospf packet authentication failed"` so `nos-e2e ospf-auth` can assert on them).

**RFC 7474 extended sequence numbers** (`OspfProfile.extended_sequence_numbers`, `set … profile <p> extended-sequence-numbers enable|disable`, provision `--ospf-extended-seq`): `AuType` 3 — 32-bit Key ID, a 64-bit (boot count : counter) number in the 8 octets after the packet (outside the OSPF length, covered by the digest) and `Apad` = IP source address + `0x878FE1F3…` (`packet::ext_digest_input`; the packet's source is threaded in via `OutgoingAuth::Crypto.extended`/`AuthPolicy::Crypto.extended`). It does **not** use an LLS block (issue #43 said so; RFC 7474 doesn't) — RFC 5613 LLS is still unimplemented. Commit-time validation (`valid_profile_timers`) requires crypto auth with HMAC-SHA keys only. The boot count comes from `boot::BootCounter` (`--state-dir`, default `/var/lib/nos/ospfd`, file `<instance>.boot`, atomic write) and is taken fresh on **every link (re)start**, not just process start, so a config-driven link restart can't send a lower sequence than before; the low 32 bits carry into it on wrap. Replay check is per neighbor **per packet type** (`NeighborInfo.last_crypto_seq: HashMap<u8, u64>`; the classic `AuType` 2 keeps its single slot). Types 2 and 3 don't interoperate (`AuthTypeMismatch`, logged as an auth failure). Verified by `nos-e2e ospf-auth` (mismatch, both-ends Full, `nos-ospfd` kill/restart with no replay drops). The classic `AuType` 2 HMAC-SHA digests are `HMAC(K, packet || Apad)` per RFC 5709 §3.3 (`packet::classic_digest`/`apad`, pinned by a test that recomputes the HMAC independently; #82) — plain MD5 is `MD5(packet || key)` with the key zero-padded/truncated to 16 bytes (RFC 2328 D.4.3 (a)).

**Key ID width**: `nos_proto::OspfCryptoKey.key_id` is `u16` (shared with `Ospfv3Profile.auth`, where it is RFC 7166's 16-bit SA ID). The classic `AuType` 2 wire field is one octet, so `valid_profile_timers` rejects a key-id above 255 unless `extended_sequence_numbers` is on (RFC 7474's field is 32 bits); `packet::encode_packet`'s classic arm relies on that cap.

Only MD5 and the RFC 5709 HMAC-SHA family are implemented — no other cryptographic algorithm, and (like the rest of this crate) no multi-area/ABR scope creep alongside it.

### LSA exchange and the LSDB

Once a neighbor reaches `ExStart`, `ospf::exchange` (pure, no I/O, mirroring `bgp::fsm::step`'s transition-returns-actions shape) drives the steps below. The DBD half (negotiation, pagination, `Loading`/`Full` DBDs, the delayed-ack queue, `LSAck` handling) is `nos_ospf_common::exchange`, shared with `nos-ospfv3` (#430); `ospf::exchange` passes it v2's closures (`lsa::in_area_scope`, `lsa::is_opaque`) and `Params` (`dbd_options(stub)`, the peer's O-bit) and keeps the LSR/LSU handlers:

- **`ExStart`**: RFC 2328 §10.6 master/slave negotiation — the higher router-id wins master. The two sides' Hello-driven `ExStart` entry is never synchronized (each side reaches it independently, off its own Hello timing), so `on_dbd_in_exstart` accepts *either* a genuine negotiation attempt (I=1,M=1,MS=1) *or* the other side's one reply/poll as the trigger, on **both** sides of the negotiation (would-be master accepting the slave's reply, and would-be slave accepting the master's poll — the latter's own detection no longer requires `more: false`, since a paginated first poll can legitimately still have data left) — a real, common case (on either side) where a peer's original attempt was sent, and lost, before the local side even had adjacency data to receive it into (`handle_dbd` drops a DBD for a neighbor with no adjacency yet), so the only packet ever seen back is that peer's reply/poll to our own (later) attempt. Since that packet is also the only copy of the peer's summary either side will ever see for that specific chunk (a peer already past its own `ExStart` never resends the original attempt), receiving it this way processes that chunk's content immediately too (only `NegotiationDone` fires here, though — never `ExchangeDone`, since with pagination a single chunk is never assumed to be the whole summary; termination is always decided in `Exchange`, see below). The slave-side half of this (accepting the master's poll, not just its attempt) was only added once a real three-router Docker scenario (`ospf-dr`, see root `CLAUDE.md`) exposed it — a newly-joining router's own attempt to a segment's already-converged DR/BDR would otherwise be the only exchange either side ever completed, leaving the third router's other adjacency permanently stuck at `ExStart`.
- **`Exchange`**: real RFC 2328 §10.8 pagination — each side's local LSDB summary (`AdjacencyData.summary_remaining`, seeded once at `ExStart` exit) is chunked into `max_headers`-sized pieces (`exchange::pop_chunk`; the per-process budget is `link::LinkManager`'s `dbd_max_headers`, defaulting to `exchange::DEFAULT_DBD_MAX_HEADERS` — see `main.rs`'s `--dbd-max-headers`), one chunk per DD sequence number: the master increments the sequence number and polls again as long as either side still has data (even sending an empty chunk purely to let the slave keep replying), the slave always replies at the master's latest sequence number with its own next chunk, and the request list accumulates across every chunk from both sides (`compute_request_list`, extended not overwritten). The exchange terminates once both sides have declared `more: false` in the same round. `ponytail:` `max_headers` is a fixed conservative constant sized off a generic Ethernet MTU assumption (`exchange.rs`'s own doc comment), not derived from a live query of the link's real interface MTU — `DbdPacket.interface_mtu` is checked on receive in `ExStart`/`Exchange` (`exchange::mtu_acceptable`, called from `link::rx::handle_dbd`): a larger neighbor MTU is dropped with `ospf dbd rejected` and the neighbor stays in `ExStart`; `OspfProfile.mtu_ignore` (`LinkConfig.mtu_ignore`) skips it. Verified by `nos-e2e ospf-mtu-mismatch`. Empty request list goes straight to `Full`, non-empty goes to `Loading`. A negotiation-shaped duplicate arriving here (the peer's own view hasn't caught up to the fact that negotiation already succeeded) is silently ignored, not treated as a restart signal — treating it as `SeqNumberMismatch` would force both sides to keep re-picking fresh random sequence numbers and restarting in lockstep, an unrecoverable live ping-pong.
- **DBDs in `Loading`/`Full`** (RFC 2328 §10.6, `exchange::on_dbd_in_loading_or_full`, #146):
  - An Init DBD raises `SeqNumberMismatch` (back to `ExStart`). This recovers a peer that restarted negotiation on its own side (BadLSReq, an out-of-sequence DBD) while its Hellos still list us — Hello alone only catches a peer whose link restarted.
  - The slave answers the master's duplicate final poll (same sequence number, MS set) by resending its last DBD, which `finish_neighbor_event` keeps for that purpose (the master clears its own). `ponytail:` kept until the next `ExStart`, not the RFC's `RouterDeadInterval`.
  - `retransmit_pending` resends a DBD only in `ExStart`/`Exchange`, so the slave's kept reply goes out only on that duplicate.
  - Any other non-Init DBD is ignored; the `Exchange`-state duplicate rule above is unchanged.
- **`Loading`**: LSR/LSU/LSAck against the neighbor, via `nos_ospf_common::lsdb::Lsdb<Lsa>` (shared with `nos-ospfv3`; `ospf::lsdb::Lsdb` is the alias) — one per OSPF area (`LinkManager` holds `HashMap<Ipv4Addr, Arc<Mutex<Lsdb>>>`, never a single flat map, since `OspfArea` is already multi-valued in this schema and a flat LSDB would leak LSAs across areas). `Lsdb::install` only accepts a strictly-newer instance (RFC 2328 §13.1: sequence number, then checksum, then `MaxAge`-is-always-newer). An unrequestable LSA (`BadLSReq`) or an out-of-sequence packet at any point restarts negotiation from `ExStart` (`SeqNumberMismatch`). Acknowledgments are **delayed** (RFC 2328 §13.5): `on_lsu_received` queues each received LSA's header on `AdjacencyData.pending_acks` instead of answering every LSU with its own `LSAck`, and each link's `RXMT_INTERVAL` sweep (`link::flush_pending_acks`, via `exchange::take_pending_acks`) sends a neighbor's whole queue as one packet (on a broadcast link every neighbor's queue is merged and deduplicated by `exchange::take_all_pending_acks` into one multicast set), logging `"ospf lsack sent"` with `acked` (headers in it) and `delayed_ms` (how long the batch was held). **Multicast flooding (#879)**: `flood_full_neighbors` sends each LSU chunk once to the group chosen by `nos_ospf_common::drouters::flood_dest` (multicast LSUs are signed once; Crypto anti-replay is per neighbor). Opaque LSAs go to the group only if every `Full` neighbor is opaque-capable; otherwise they are unicast to the capable ones. A failed group send logs `failed to multicast ospf lsu` (or `lsack`) and that pass falls back to per-neighbor unicast. `ospf lsu flood destination changed link=.. dest=unicast|all-spf-routers|all-drouters` is logged only when the destination changes. `ponytail:` every ack is delayed — the RFC's direct-ack cases key off "was this LSA flooded back out in response", which the periodic-resend flooding model has no equivalent of; the 5s sweep is the RFC's own `RxmtInterval` ceiling for the delay, at the cost of the sender's `retransmit_pending` sometimes resending an LSU whose ack is still queued.
- **Self-origination** (`LinkManager::originate_router_lsas`, on a 2s tick, independent of the 10s config-reapply tick): recomputes and reinstalls this router's own Router-LSA per area (one link entry per currently-known link with a neighbor/resolved DR) and a Network-LSA on any broadcast link where this router is DR with ≥1 `Full` neighbor — reinstalling (and bumping the sequence number) either when the content changed, or when the held instance's age has reached RFC 2328 §14's `LSRefreshTime` (1800s) even with unchanged content (see "Aging/refresh/flush" below).
- **Own LSA flooded back newer** (RFC 2328 §13.4, #731): `handle_lsu` finds installed headers whose advertising router is this router (`nos_ospf_common::lsa::reflected_self_lsas`), `Lsdb::mark_reflected`s them and wakes `LinkManager::reoriginate`; `origination_pass` runs at once and `install_self_originated` re-originates at the received sequence + 1 even with an unchanged body, skipping `MinLSInterval`. A mark no pass took (a type no longer originated) is flushed at the end of the pass. A Network-LSA with a foreign advertising router and this link's address as Link State ID (a previous incarnation as DR under another router-id) is flushed by `origination_pass` (`flush_stale_network_lsas`, any link's address; `ospf stale network lsa flushed`).
- **Aging/refresh/flush** (RFC 2328 §14): a second per-process background tick in `LinkManager::new` (`AGE_TICK_INTERVAL`, real 1s, independent of `ORIGINATION_INTERVAL`) ages every installed LSA in every area's `Lsdb` by one second — scaled by `age_multiplier` (`LinkManager::new`'s argument, wired from `nos-ospfd`'s `--lsa-age-multiplier`, default `1` — test/debug only, reachable purely via `nos-watchdogd`'s `--ospfd-arg` pass-through, never `OspfProfile`/`nos-cli`) — and evicts (`Lsdb::age_and_evict`) anything that has sat at `MAX_AGE` (3600s) for `nos_ospf_common::lsdb::MAX_AGE_HOLD_TICKS` (7) ticks, logging `"ospf lsa maxage flushed"`. A self-originated LSA is held with its real wire checksum (`lsa::fill_checksum`) so a neighbor's echo of it in the periodic resend ties with the held instance instead of superseding it (a zero local checksum used to lose to every echo — harmless until the flush below, which it would undo). That hold is what makes **premature aging** (RFC 2328 §14.1) work on top of the periodic-resend flooding model: `link::originate::withdraw_self_originated` flushes one of this router's own LSAs by reinstalling it at `MAX_AGE` with its sequence number *unchanged* (`is_newer`'s MaxAge tie-break makes every neighbor accept it — the body, hence the checksum, is untouched), logging `"ospf lsa prematurely aged"`, and the hold keeps it in the LSDB long enough for each link's `RXMT_INTERVAL` resend to carry it out; a neighbor installs the MaxAge copy (SPF ignores it at once — `spf::live_lsas`, §16.1 step 2), holds it the same way so *its* resend propagates it further, then flushes it. `exchange::on_lsu_received` implements §13 step 4 — a MaxAge instance of an LSA with no held copy (and not on this adjacency's request list) is acked and discarded, never installed — without which two routers each holding the flushed copy for its hold window would reinstall each other's echo forever. Every origination pass (`originate_router_lsas`/`originate_as_external_lsas`/`originate_summary_lsas`) ends with `withdraw_undesired`, the inverse of its install loop: a Router-/Network-LSA in an area this router has left (no link, no stub) or a link it's no longer DR on, a Type-5 for a prefix no longer redistributed, a Type-3/4 no longer intra-area to some other area — all flushed in seconds rather than after an hour. **Graceful shutdown** (`LinkManager::shutdown`, on SIGINT/SIGTERM): flushes every self-originated LSA in every area, logs `"ospf flushing self-originated lsas before shutdown"`, kicks the flushed copies out at once (`LinkManager::flood_now`, see "Flooding"), keeps the link tasks alive for `PREMATURE_AGE_FLOOD_WINDOW` (6s — one more `RXMT_INTERVAL` retransmission — inside `nos-watchdogd`'s 10s kill budget beside RFC 6987's on-shutdown hold, which runs first; a `const` assertion pins the sum at ≤ 9s) with the origination tick gated off (`shutting_down`), then aborts them. **Sequence-number wraparound** (§12.1.6, issue #32): `install_self_originated` at `lsa::MAX_SEQUENCE_NUMBER` withdraws instead of incrementing (a wrapping add would produce the reserved `0x8000_0000`), and once the MaxAge hold has evicted the flushed copy the next tick re-originates at `INITIAL_SEQUENCE_NUMBER`. **Pacing** (RFC 2328 §13 step 5a / Appendix B): `MinLSInterval` (`lsa::MIN_LS_INTERVAL`, 5s) — `install_self_originated` holds back changed content until the held instance's `age` (the local clock since origination, never overwritten by an echo thanks to `fill_checksum`) reaches it, and the next 2s origination tick retries; `MinLSArrival` (`lsdb::MIN_LS_ARRIVAL`, 1s) — `Lsdb::install_received`, the flooding-side `install` that `on_lsu_received` uses, records when each key's instance was last accepted and returns `InstallOutcome::TooSoon` for a newer one arriving inside that window, which is then neither installed nor acknowledged nor treated as answering a request (the sender's `RxmtInterval` retransmission brings it back). Self-originated installs and withdrawals never go through `install_received`, so they're never paced against a received copy. `CheckAge` stays out of scope: every LSA's checksum is already verified once on wire admission.
- **Flooding**: every LSA leaves in an LSU with `packet::INF_TRANS_DELAY` (1s, RFC 2328 §13.3 / Appendix C.3 `InfTransDelay`) added to its age on the wire copy only (`packet::encode_lsu`, saturating at `MaxAge`; the LSA checksum excludes the age, so it's unaffected), so an age keeps advancing across hops between age ticks — the receiver's `"ospf lsa installed"` line logs the age it landed with. Otherwise `ponytail:` no real RFC 2328 §13 event-driven flooding (on origination, or on receipt, reaching every adjacent link) — instead, each link periodically (every `RXMT_INTERVAL`) resends its *entire* local-area LSDB to every `Full` neighbor on that link (`link::flood::flood_full_neighbors`). The one exception is the shutdown path: `LinkCommand::FloodNow` (sent by `LinkManager::flood_now` over each link's command channel, beside `LinkCommand::Grace`) runs that same resend at once, for RFC 6987's on-shutdown Router-LSA and the §14.1 flush. Safe (a non-newer duplicate is cheaply rejected and still acked) and simple, at the cost of up to one `RXMT_INTERVAL` of propagation delay and a little wasted bandwidth on a lab-scale LSDB; it does mean an LSA can validly be first observed as "installed" via either of a router's links when it has more than one in the same area. This remains the permanent design even now that SPF exists (see below): `rib_push_client` recomputes on each LSDB change (#190) but propagation between routers is still bounded by `RXMT_INTERVAL`, so real event-driven flooding still isn't worth the complexity of threading a fan-out channel through every link task. See `lsa.rs` for what Router/Network-LSA bodies this NOS parses/originates and what's deliberately deferred (AS-external/Summary LSAs, multi-area ABR behavior, authentication).
- **Reporting**: `nos_proto::OspfNeighborState`/`NeighborSummary` (`show ospf neigh`) report the full `Down`/`Init`/`TwoWay`/`ExStart`/`Exchange`/`Loading`/`Full` ladder 1:1 (`link::to_neighbor_state`). `show ospf database` (`OspfRequest::GetDatabase`/`OspfEvent::Database`, `LinkManager::database_summaries`) reports every installed LSA's header — type, link-state-id, advertising router, sequence number, age, checksum — across every area, never the full LSA body (SPF reads bodies internally; there's just no operator-facing rendering of one yet).

### SPF and route installation

`ospf::spf::compute(root, lsas)` is a pure RFC 2328 §16.1/§16.2 Dijkstra over one area's LSDB snapshot: vertices are routers (keyed by router-id) and transit networks (keyed by a Network-LSA's `link_state_id`), edges come from Router-LSA type-1/type-2 links (type-3 stub links are leaves, handled in a post-pass) and Network-LSA `attached_routers` (cost 0, per RFC). Next-hop derivation is entirely LSDB-based — no live neighbor-table dependency: a point-to-point/transit-network link's `link_data` is always the *originating* router's own address on that link (RFC 2328 §12.4.1.1), so a neighbor `w`'s address is learned by reading *`w`'s own* LSA for its link back to us, not ours. Every vertex beyond the first hop simply inherits its parent's next-hop set unchanged. Equal-cost paths are all kept (RFC 2328 §16.1 step 2(d)): an equal-distance relaxation unions the new parent's next hops into the vertex's set (a transit network pops before a router at equal distance, so its zero-cost edges can still add to it), and an equal-metric tie between two collected routes to one prefix unions their sets (`spf::merge_equal`, also used by `compute_routes`' cross-area merge). `RouteEntry.next_hops` is sorted and deduped, and `rib_push_client` pushes the whole set (`OspfRoute.next_hops`), which `nos-ribd` installs as one `RTA_MULTIPATH` kernel route (see `docs/internals/rib.md`'s "Equal-cost multipath"). Verified by `nos-e2e ospf-spf` (`next_hops=2`: router-a reaches router-b over both the p2p link and the bridge). Destinations directly attached to the root (root's own stub links, or a transit network root itself sits on) are filtered out by `(link_id, link_data)` key, not by reachability — necessary because a point-to-point link's *far end* independently advertises the identical subnet (see below), which Dijkstra will otherwise happily reach through the neighbor.

To give SPF real destination prefixes to compute against — the LSDB otherwise carries pure router-to-router/transit-network topology, zero leaf prefixes — `link::originate::router_lsa_links` now emits a type-3 stub-network link for every point-to-point link's own subnet *unconditionally* (RFC 2328 §12.4.1.1: independent of neighbor state), and `originate_router_lsas` fills in a real `NetworkLsaBody.network_mask` (previously always `UNSPECIFIED`) for a broadcast link's Network-LSA. A loopback (`Interface.ospf_profile`) attach point stays log-only for Hello/adjacency purposes (see above) but now feeds `LinkManager.stub_networks: HashMap<area, Vec<(subnet, cost)>>` (populated by `reconcile.rs`'s `loopback_attach_points`/`resolve_loopback_prefix`), so its own subnet is still advertised as a type-3 stub — the cleanest destination with zero neighbors, and what `nos-e2e ospf-spf` exercises end to end. `LinkConfig` carries the real `local_prefix_len`/`cost` needed for all of this (`OspfProfile.cost`, `None` → `1`).

`LinkManager::compute_routes` runs `spf::compute` per area and merges into one route set — a router attached to 2+ areas (an ABR, see "ABR and Summary-LSA origination" below) can legitimately compute the same prefix from more than one area's own LSDB, so the merge keeps whichever is cheaper rather than a plain overwrite. `rib_push_client.rs` (mirroring `bgp::rib_push_client`'s shape, but event-driven (#190): `Lsdb` owns an optional `Notify` fired in `install`/`remove`/`age_and_evict`, shared by every area's and link-local LSDB and exposed as `LinkManager::route_changed`, so one choke point covers all ~29 `lock()` sites; a 50ms hold-down coalesces an LSU burst into one SPF and the 2s poll stays as a `ponytail:` safety net for non-LSDB inputs, neighbor state and area reconcile) pushes the result to the owning `nos-ribd` instance over `RibRequest::PushOspfRoutes` (`Full` on connect, diffed `Add`/`Remove` after each LSDB change or 2s fallback tick), landing as `RouteSource::Ospf` (admin-distance-style preference `110` — Cisco-convention, beaten by `Static`/`Bgp`) in `nos-rib`'s multi-source `Rib`.

### Loop-free alternates (backup routes)

`spf::compute` also fills `RouteEntry.backup_next_hop` with an RFC 5286 basic loop-free alternate. `spf::alternates` runs one extra `run_dijkstra` rooted at each router adjacent to root (p2p neighbor, or another router on a transit network root sits on); `pick_backup` accepts a candidate whose address is none of the primary next hops and that satisfies `dist(N,E) < dist(N,root) + dist(root,E)` for the route's *egress vertex* `E` (`RouteEntry.egress`, the router/network the metric was built from — the leaf/summary/external metric cancels out of the inequality), choosing the cheapest, ties by address. `ospf::rib_push_client` carries it in `OspfRoute.backup_next_hop`; `nos-ribd` installs it as a second kernel route at `BACKUP_METRIC` (see `docs/internals/rib.md`), so failover needs no netlink call. RFC 5286 §3.5: `alternates` drops a candidate whose forward cost (root's link) or reverse cost (the neighbor's own link back to root, or to the shared network — `spf::own_link`) is `lsa::MAX_LINK_METRIC`, so an RFC 6987 stub router at either end is never an alternate. `ponytail:` link protection only (no node protection), one Dijkstra per neighbor per area on every SPF run; `nos-ospfv3d` has its own port (see [OSPFv3 internals](ospfv3-internals.md)). Verified by `nos-e2e ospf-lfa` and `ospf-stub-router`.

**Remote LFA** (RFC 7490, #187), opt-in per instance (`OspfInstance.remote_lfa`, `LinkManager::set_remote_lfa`, an atomic read into `spf::Context.remote_lfa` by `compute_routes`; provision `--ospf-remote-lfa true|false`):

- `spf::remote_lfas` runs after `pick_backup`, for routes with one next hop over a root p2p link and no basic LFA. P-space of root for the link to E: routers whose next-hop set lacks E's address on it (no extra Dijkstra). Q-space of E: `dist(Q,E) < dist(Q,root) + cost(root,E)`, from `reverse_distances` (Dijkstra over reversed edges, because costs can be asymmetric). A PQ node must have a /32 stub (`host_stub`, the tunnel destination) and not be an RFC 8770 host router; per route, a PQ whose own path to the egress vertex doesn't come back through root, cheapest `dist(root,PQ) + dist(PQ,E')`, ties by address. Fills `RouteEntry.backup_tunnel`; `merge_equal` clears it once a route is ECMP, `apply_transit` on replacement.
- `rib_push_client` sends it as `OspfRoute.backup_tunnel` (`backup_next_hop` stays `None`); `nos-ribd` installs it through its `rlfa<table-id>` device (see `docs/internals/rib.md`'s "Tunnel backups").
- `ponytail:`s: plain P-space only (an extended P-space PQ must be reached through a given neighbor, which the tunnel route can't pin); link protection over p2p links only; one reverse Dijkstra to root plus one per protected neighbor plus one forward per PQ candidate on every SPF run (RFC 7490 §4.4's incremental computation is the upgrade); SPF can't tell whether the PQ node runs `remote-lfa` (decaps), hence "on every router"; IPv4 only (`nos-ospfv3d` not done).
- Tests: `spf::tests::five_node_ring_gets_a_remote_lfa_to_the_pq_node`, `a_basic_lfa_needs_no_tunnel`, `q_space_uses_reverse_distances`, `a_pq_node_without_a_loopback_is_skipped`, `an_ecmp_route_gets_no_tunnel`; `nos-e2e ospf-remote-lfa`.

### ASBR and AS-external-LSA origination

`RoutingTable.redistribute` (a list of rules keyed by `to`, one per target: `Bgp`, `Ospf`, `Ospfv3`, so one table can feed all three) accepts `to: Ospf` — `redistribute ospf` makes this router a real RFC 2328 ASBR. The mechanism mirrors BGP's own redistribution exactly, mirrored end to end: `nos-ribd`'s `ospf_client.rs` (a near line-for-line copy of `bgp_client.rs`) pushes this table's `RouteSource::Static` entries to the owning `nos-ospfd` instance over a persistent connection (`OspfRequest::RedistributeRoutes(RedistributeUpdate)`, fire-and-forget, `Full` on connect then diffed `Add`/`Remove`); `link.rs`'s `LinkManager` holds the raw set (`redistribute_raw`) and a policy-filtered set (`redistribute_filtered`, re-derived by `set_redistribute_policy` on every `reconcile.rs` resync — no `PolicyCache` unlike BGP's, since `OspfInstance.redistribute_policy` is exactly one policy per instance, so compiling fresh every resync tick needs no cache-invalidation logic); `originate_as_external_lsas` (run from the same 2s tick as `originate_router_lsas`) installs a real Type-5 AS-external-LSA (`lsa::AsExternalLsaBody`, RFC 2328 Appendix A.4.5) per redistributed prefix.

**Cross-area flooding**: since a real AS-external-LSA is domain-wide, `originate_as_external_lsas` installs each of this router's own redistributed prefixes' Type-5 into *every* area it is attached to, and `flood_external_lsas_across_areas` (same 2s tick, ABR only) copies every non-self Type-5 — live or MaxAge, so a flush propagates — from each area's `Lsdb` into every other area where `lsa::in_area_scope` allows it (never a stub area/NSSA) and no equal-or-newer instance is held (`Lsdb::install`; a MaxAge copy with nothing held is skipped). Logs `ospf external lsa copied across areas`. `ponytail:` a copy ages on its own area's clock; one AS-scope `Lsdb` (like `nos-ospfv3d`'s) is the upgrade path. No new flooding code: `flood_full_neighbors`'s periodic per-link resend picks up whatever lands in that area's `Lsdb`. Tests: `link::tests::an_abr_copies_a_foreign_type5_*`, `an_abr_never_copies_a_type5_*`, `a_non_abr_and_a_flush_*`; `nos-e2e ospf-external-flood`.

`ospf::spf::compute` gained a third destination-collection pass, `collect_external_routes`, parallel to the existing stub/network passes: for each installed AS-external-LSA, it looks up the advertising ASBR's already-computed intra-area distance/next-hop and adds the LSA's own metric to it (or resolves the forwarding address, see below); `spf::insert_best` ranks it against stub/network routes with `prefer` (an external never beats an intra-area route). A guard skips `advertising_router == root` — this router's own Type-5, once installed into its own area, would otherwise compute a spurious route to its own prefix via itself.

Deliberate simplifications (all `ponytail:`-flagged at their point in the code), scoped to keep this a real, correct, appropriately-sized ASBR without pulling in NSSA/ABR work:
- **Redistribution source**: `Static` only, mirroring BGP's own redistribution (which also only supports `Static` today). BGP→OSPF redistribution is unimplemented.
- **Metric semantics** (#215): the E bit is carried verbatim (`AsExternalLsaBody.e_type2`, kept on Type-7→Type-5 translation) so a foreign Type-2 LSA is flooded unchanged (RFC 2328 §13); nos originates the rule's `redistribute ... metric`/`metric-type` (default 20, Type 1; #216): mirrored by `nos-proto`'s `derive.rs` into `OspfInstance.redistribute_metric`/`redistribute_metric_type` (read-only, the `redistribute_policy` pattern), set on `LinkManager` every resync by `set_redistribute_metric` and used for both Type-5 and own Type-7 in `originate_as_external_lsas` (`spf::DEFAULT_EXTERNAL_METRIC` when unset); a change re-originates (sequence bump, MinLSInterval-paced). `LsaSummary` carries `external_metric`/`external_type2` for `GET /v1/ospf/database`. SPF ranks per RFC 2328 §16.4 step 6: `spf::prefer` over `RouteEntry.class` (`PathClass`: Internal < External1 < External2), Type 2 by LSA metric then distance X (`metric - ext`); `RouteEntry.metric` is X+ext for both. `insert_best` and `LinkManager::compute_routes`' cross-area merge both use `prefer`. LSInfinity (0xFFFFFF) LSAs are skipped. `ponytail:` no §16.4.1 area preference, no RFC 1583 mode.
- **Forwarding address**: `forwarding_address` is always `0.0.0.0` on origination. On receipt SPF honours a non-zero one (RFC 2328 §16.4 step 3, `spf::resolve_forwarding_address`): longest match among the Internal routes of `out` and root's own attached prefixes (`root_attached_prefixes`, which `out` omits; next hop = the FA itself); unresolved = LSA skipped. External collection therefore runs after every Internal collector. This also applies to Type-7 LSAs inside an NSSA.
- **Router-LSA E-bit** (RFC 2328 A.4.2, #34): `originate_router_lsas` sets `lsa::ROUTER_FLAG_E` while `redistribute_filtered` is non-empty — the same set `originate_as_external_lsas` reads, so the bit and the Type-5s come and go in the same tick (a rule whose policy passes nothing leaves E clear), and cleared in a stub area. Our own SPF doesn't read it, but other vendors do: FRR resolves a Type-5's ASBR only through a Router-LSA with E or B (`nos-e2e ospf-opaque`). (The separate Hello-packet Options-byte E-bit is per area — clear in a stub area — and checked by `link::rx::handle_hello`, see "Stub areas" below.)
- **LSA withdrawal**: RFC 2328 §14.1 premature aging — when a redistributed prefix disappears (or the rule is removed), `originate_as_external_lsas`'s `withdraw_undesired` pass flushes its Type-5 (see "Aging/refresh/flush" above). The redistributed set is only re-filtered on `reconcile.rs`'s 10s resync, so the flush follows the removal by up to that plus one resend period.
- **Link State ID assignment** (RFC 2328 Appendix E, #183), shared by Type-3/5/7 (each its own ID space, per area):
  - `link::originate::assign_link_state_ids` sorts by mask length: the shortest mask gets the network address, a longer one sharing it gets the address with its host bits set (`192.0.2.128/25` → `.128`, `/26` → `.191`).
  - Stateless and deterministic, recomputed every tick: the RFC's own end state. When a shorter prefix appears, the longer one moves to its host-bits ID at once; the old ID's content change can wait out `MinLSInterval`, so both IDs briefly carry it.
  - `ponytail:` when both IDs are taken (`10.0.0.0/16`, `/24`, then `10.0.0.255/32`), the later prefix is skipped with `ospf lsa link state id collision, not originating`.
  - On receive, `spf::net_from` truncates, so an ID with host bits (FRR's, or a Network-LSA's DR address) names the right prefix, and every collector keys its routes by that prefix: two LSAs for one prefix compete and merge.
  - Tests: `link::tests::assign_link_state_ids_follows_appendix_e`, `overlapping_*`, `spf::tests::host_bit_link_state_ids_truncate_and_merge`, `network_lsa_route_is_truncated_to_the_segment_prefix`; `nos-e2e asbr` and `ospf-opaque` (both directions against FRR).

`nos-e2e asbr` (requires `ospf` to have already run) exercises this end to end: a static route + `redistribute ospf` on router-a, confirming a real Type-5 origination, router-b installing it into its own LSDB over the real adjacency, and router-b's own SPF pushing a real kernel route for it via `nos-ribd` — then removing the rule (`--clear-redistribute-to-ospf`) and confirming router-a prematurely ages the Type-5, router-b flushes it and removes the kernel route, all within seconds.

### ABR and Summary-LSA origination

A router attached to 2+ `OspfArea`s at once (already fully supported by the config/reconcile layers — `LinkManager.lsdbs` is already keyed per area) is a real RFC 2328 Area Border Router by this NOS's purely-derived definition: `LinkManager::originate_summary_lsas` checks `self.lsdbs.keys().len() >= 2` on every 2s origination tick, no config flag, mirroring how this crate already derives DR-ness/ASBR-ness from live state rather than a schema field. When true, it computes each area's own **intra-area-only** view (`spf::intra_area_routes` — Dijkstra plus only the stub/network collector passes, explicitly excluding external/summary-derived routes: RFC 2328 forbids re-summarizing an already inter-area or already-external route, which is what prevents trivial two-area routing loops) and, for every *other* area the router touches, installs a fresh Type-3 network-summary LSA (`lsa::SummaryLsaBody`, RFC 2328 Appendix A.4.4) per intra-area prefix and a Type-4 ASBR-summary LSA per genuinely-in-that-area ASBR (any router-id with an installed Type-5 that's actually reachable via that area's own Dijkstra) — both freshly self-originated (advertising router is always this router's own id), not a raw copy of another router's LSA. No new flooding code was needed, exactly like Type-5 needed none: `flood_full_neighbors`'s existing periodic per-link full-area-LSDB resend already picks up whatever lands in that area's `Lsdb`.

The Router-LSA's B-bit (`lsa::ROUTER_FLAG_B`, #34) is set in every area while this router has a link or loopback stub in 2+ areas — not `lsdbs.len()`, which never shrinks after leaving an area. FRR needs it to accept our Type-3s (`nos-e2e ospf-opaque`). A configured virtual link counts as a backbone area here (see "Virtual links"); V is set in a virtual link's transit area.

`ospf::spf::compute` gained a fourth destination-collection pass, `collect_summary_routes`, parallel to `collect_external_routes`: for each installed Type-3 in this area, it looks up the advertising ABR's already-computed intra-area distance/next-hop and adds the summary's own metric — `insert_best` competes it against stub/network routes with `prefer` (intra and inter-area share a class and compare raw metric; externals rank below both). `collect_external_routes` itself gained a Type-4 proxy fallback (`spf::asbr_distance`): if an AS-external-LSA's advertising ASBR has no direct intra-area Router-LSA vertex in this area (it's genuinely attached in another area), it falls back to an installed Type-4 for that ASBR in this area — distance is that Type-4's advertising ABR's own intra-area distance plus the Type-4's metric, next-hop is the ABR's own next-hop (packets to a foreign ASBR go via the ABR proxying reachability to it); multiple Type-4s for the same ASBR take the cheapest. A guard skips `advertising_router == root` in `collect_summary_routes`, mirroring `collect_external_routes`'s own `asbr == root` guard — this router's own self-installed Type-3 must never route to its own summarized prefix via itself.

Deliberate simplifications (all `ponytail:`-flagged at their point in the code), scoped the same way the ASBR feature was — a real, correct, appropriately-sized 2-area ABR mechanism without pulling in NSSA/full-mesh-loop-prevention work:
- **Virtual links** are below ("Virtual links"), as are stub areas, area ranges and NSSAs.
- **No RFC 2328 up/down-bit loop-prevention machinery** — correct for the 2-area topology this is designed/tested against (one non-backbone area behind a single ABR); a 3+-area topology with multiple ABRs could in theory re-summarize an already-inter-area route back across a third area, since `intra_area_routes` only excludes *this router's own* external/summary-derived routes, not another ABR's.
- **`intra_area_routes` doesn't summarize root's own directly-attached transit networks** (only stub networks) — a router won't advertise reachability to a broadcast segment it's itself sitting on into its other areas. This NOS's concrete ABR scenarios (a loopback stub, a redistributed prefix) never need it.
- Path types rank RFC 2328 §11 style (`spf::PathClass`: intra-area < inter-area < Type 1 < Type 2): an intra-area route always beats an inter-area one to the same prefix, whatever the metric, within an area (`insert_best`) and across areas (`compute_routes`' merge).
- **§16.2** (#226): an ABR attached to the backbone (`LinkManager::is_backbone_abr`; a configured virtual link counts, #37 D5) examines only the backbone's Type-3/4 (`spf::Context.skip_summaries` for its other areas). An ABR with no backbone attachment still reads every area's summaries (RFC 3509-like, unchanged).
- **Link State IDs**: Type-3s use RFC 2328 Appendix E, like Type-5 (see "Link State ID assignment" above). A prefix intra-area in two source areas is one Type-3, at the lower metric.
- **LSA withdrawal** is RFC 2328 §14.1 premature aging, like Type-5: when a prefix/ASBR stops being intra-area to some other area, `originate_summary_lsas`'s `withdraw_undesired` pass flushes the Type-3/Type-4 (see "Aging/refresh/flush" above). A router that leaves an area entirely (no link, no stub left) also flushes its Router-LSA there, which is what empties that area's intra-area view in the first place.

`nos-e2e abr` (requires `ospf-spf` to have already run — it reassigns that scenario's own loopback into a second area, at a distinct address, since `nos-ribd`'s route diffing needs a genuinely new prefix to log a fresh kernel-install event) exercises this end to end: router-b's loopback moves from the backbone into a real second area, making router-b a genuine ABR; router-b originates a real Type-3 for it; router-a (backbone-only) learns and installs that Type-3 into its own LSDB over the real adjacency; and router-a's own SPF computes and pushes a real kernel route for a prefix that isn't in its own area at all, purely via router-b's summary — then the loopback leaves area 1 again and router-b prematurely ages the Type-3, router-a flushes it and removes the kernel route, within seconds.

### Stub areas, area ranges and discard routes (RFC 2328 §3.5, §3.6, #35)

- **Config**: `OspfArea.area_type` (`Normal`/`Stub`/`TotallyStubby`), `stub_default_cost` and `ranges` (`OspfAreaRange { cidr, not_advertise }`), resolved by `reconcile::area_settings` into `link::AreaSettings` and handed over with `LinkManager::set_area_settings` on every resync. `LinkConfig.stub` is per link, so changing an area's type restarts its links (both ends must agree).
- **Stub link**: `send_hello` clears `OPTION_E` and `handle_hello` drops a Hello whose E-bit differs (`dropping ospf hello with mismatched e-bit`); DBDs use `exchange::dbd_options(adj.stub)`; the DBD summary (the `in_scope` closure) and `flood_full_neighbors` leave AS-scope LSAs (`lsa::is_as_scope`: Type-5/11) out; `on_dbd_received` answers a DBD listing one with `SeqNumberMismatch`; `on_lsu_received` drops one unacked.
- **Origination**: `originate_as_external_lsas` installs nothing into a stub area (so a just-turned-stub area's Type-5s are flushed); `originate_router_lsas` clears `ROUTER_FLAG_E` there; `compute_routes` ignores a Type-5 still held in one. As an ABR (`lsdbs.len() >= 2`, `ponytail:` no backbone check), `originate_summary_lsas` originates the default Type-3 (`0.0.0.0`, mask `0.0.0.0`, `default_cost`) into a stub area, no Type-4, and no other Type-3 when totally stubby.
- **Ranges**: `spf::apply_ranges` turns one source area's intra-area routes into what to summarize (uncovered prefixes plus each advertised range with a component, at the *largest* component cost — RFC 2328, not RFC 1583) and the active ranges. They land in `LinkManager.active_ranges`, which `compute_routes` turns into `spf::RouteEntry::discard` entries (no next hop) unless SPF has a route for exactly that prefix. `rib_push_client` pushes them as `OspfRoute { discard: true }` — `nos-ribd` installs a blackhole (see `docs/internals/rib.md`'s "Discard routes"). The existing `withdraw_undesired` passes flush what a range or totally-stubby now suppresses.
- `ponytail:` the E-bit in the header of self-originated LSAs stays 0 (RFC 2328 §12.1.2 wants it set outside stub areas; nobody tested checks it).
- Tests: `link::tests::stub_area_gets_a_default_and_ranges_summarize` (in-memory wire), `exchange::tests::stub_link_keeps_as_scope_lsas_out`, `spf::tests::apply_ranges_*`; `nos-e2e ospf-stub`.

### NSSA (RFC 3101, #36)

- **Config**: `OspfAreaType::Nssa`/`NssaNoSummary` (`is_stub()` is true for both, `is_nssa()`, `import_summaries()`), `OspfArea.nssa_translate_always`/`nssa_default_originate` (NSSA only). `reconcile::area_settings` fills `AreaSettings.nssa`/`nssa_translate_always`/`nssa_default_originate` (`stub` is set too), and `LinkConfig.nssa` (with `stub`).
- **Wire**: `link::hello_options` sends N (`packet::OPTION_N`) and no E in an NSSA; `handle_hello` drops a mismatched N (`dropping ospf hello with mismatched n-bit`). DBDs use the stub options (O only). `lsa::in_area_scope(type, stub, nssa)` is the one scope rule: `on_dbd_received` (restarts the exchange, and filters the summary), `on_lsu_received` (drops unacked), `flood_full_neighbors` and `compute_routes` keep a Type-5/11 out of a stub area/NSSA and a Type-7 out of anything but an NSSA.
- **Origination** (`originate_as_external_lsas`, one pass per area): a normal area gets a Type-5 per redistributed prefix plus per translated one (one `HashMap` keyed by prefix, so one `withdraw_undesired` flushes both kinds); an NSSA gets a Type-7 per redistributed prefix — P-bit (`install_self_originated_with_options`) unless this router is an ABR, forwarding address `nssa_forwarding_address` (lowest link address in the area, else a loopback stub's) — plus, as an ABR with `nssa_default_originate`, a P-clear `0.0.0.0/0` Type-7 at `default_cost`; a stub area gets nothing. `originate_router_lsas` keeps E in an NSSA and sets `ROUTER_FLAG_NT` there with `nssa_translate_always` on an ABR. `originate_summary_lsas` sends the default Type-3 into an NSSA only when no-summary, and never a Type-4.
- **Translation**: per NSSA, as an ABR (`is_area_border_router`), `spf::nssa_translator` (§3.1: `always`, else no reachable B-bit router with Nt or a higher router-id) and `spf::nssa_translations` (§3.2: live P-bit Type-7s with a non-zero forwarding address from a reachable ASBR). Role changes log `ospf nssa translator role changed area=… translating=…`.
- **SPF**: a Type-7 decodes into `LsaBody::AsExternal`, so `spf::compute`'s external pass already routes on it inside the NSSA (the ASBR is always intra-area).
- Type-7 Link State IDs use RFC 2328 Appendix E (RFC 3101 §2.4), in their own ID space (see "Link State ID assignment" above).
- `ponytail:`s: no `TranslatorStabilityInterval`; a translated Type-5 has forwarding address 0 (traffic goes through the translator); §3.2's preference between two Type-7s for one prefix isn't applied; the translator's Router-LSA E-bit in the backbone follows only its own redistribution (B is set anyway). nos-provision has `--ospf-area-type nssa|nssa-no-summary` only — the two NSSA options are CLI/REST.
- Tests: `link::tests::nssa_type7_is_translated_into_the_backbone` (in-memory wire, three routers), `link::tests::handle_hello_matches_the_n_bit_to_the_nssa_flag`, `exchange::tests::type7_only_in_an_nssa_and_type5_never_there`, `spf::tests::type7_routes_and_translations`/`nssa_translator_election`, `lsa::tests::nssa_external_lsa_round_trips_with_its_p_bit`; `nos-e2e ospf-nssa`.

### Virtual links (RFC 2328 §15, #225)

- **Config**: `OspfArea.virtual_links` on the transit area (#224), handed over every resync as `link::VirtualLinkConfig` (`reconcile::virtual_links`, Appendix C.3 timer defaults, auth through the same `resolve_auth` as a profile, never RFC 7474) with `LinkManager::set_virtual_links`.
- **§16.7 resolution** (`LinkManager::resolve_virtual_links`, first step of the 2s origination tick): per link, `spf::virtual_link_endpoint` runs the transit area's Dijkstra; reachable gives cost (path distance), first hop and the endpoint's address (`link_data` of its first type-1/2 link, `ponytail:`). `resolve_virtual_link` (pure) turns that into a `LinkConfig` named `vlink-<transit>-<router-id>`, area 0, `PointToPoint`, mask 0 (`local_prefix_len` 0), `local_addr` our transit link toward the first hop, `kernel_interface` = the VRF, `mtu_ignore`, `virtual_link: Some(VirtualLinkEnd)`. Logs `ospf virtual link up link=… neighbor=… local=… cost=…` / `ospf virtual link down link=…`.
- **Links**: `reconcile` stores the attach-point links in `physical`; `apply_links` diffs `physical` + `resolved_virtual` against the running tasks. `diff_links` ignores `cost` (`same_but_cost`; the running entry's cost is updated in place), so an SPF cost change (or a profile cost change) doesn't restart an adjacency; a new endpoint address does.
- **Socket**: `OspfSocket::open_virtual` (the `new` opener picks it on `virtual_link`) — VRF-bound, bound to `local_addr`, no multicast join, default TTL. `send_hello` unicasts to the endpoint. The kernel still hands it the transit link's unicast traffic from the same neighbor, and the transit link's socket the virtual link's: `accepts_packet` (RFC 2328 §8.2, on the raw Area ID before decoding, `packet::area_id`) keeps a virtual link to backbone packets from its endpoint and drops backbone packets on a non-backbone link (other area mismatches still reach `handle_hello`'s warning).
- **Router-LSA**: `router_lsa_links` gives a virtual link one type-4 link (`lsa::LINK_TYPE_VIRTUAL`, `link_id` endpoint, `link_data` our address, cost) while the neighbor is `Full`, never a stub; `originate_router_lsas_with` sets V (`lsa::ROUTER_FLAG_V`) in the transit area's Router-LSA then. #37 D5: a configured virtual link creates the area-0 `Lsdb` and counts as backbone for `is_area_border_router` (B bit), so a router whose only backbone presence is the virtual link summarizes into area 0 and is flooded over it.
- **Reporting**: `show ospf neigh` lists the link by name; `LsaSummary.router_flags`/`virtual_links` (type-4 link ids) expose the V bit and the links in `GET /v1/ospf/database`.
- **SPF across the link** (§16.1, #226): `spf::compute_in` takes a `spf::Context` per area. In the backbone a type-4 link is an edge at its metric when the endpoint's area-0 Router-LSA has one back (`neighbors`); out of root its next hops are §16.7's first hops in the transit area (`Context.virtual_links`, `LinkManager::virtual_next_hops`, recomputed from the transit LSDB on every `compute_routes`), further out they are inherited as usual. The endpoint's stubs, Type-3s and Type-5s (§16.4, through the direct vertex) route through it. `originate_summary_lsas` passes the same context to `intra_area_routes`, so the far end summarizes the backbone into its own areas.
- **§16.3 transit summaries**: for each non-backbone area of a backbone ABR that is transit-capable (a reachable Router-LSA with V), `spf::transit_summaries` gives one candidate per Type-3 from an ABR reachable there; `spf::apply_transit` lets a strictly cheaper one replace a backbone route's cost and next hops and an equal one add its next hops. It never adds a route nor touches an external. `ponytail:` Type-4s are not examined, and a replaced route gets no LFA.
- **Not done**: DoNotAge (RFC 1793, #37 D6); DBD Interface MTU 0 (A.3.3, `ponytail:` the transit link's is sent and the check skipped); RFC 2328 §12.4.3's split horizon toward a transit area (harmless: §16.2 keeps the ABRs off those summaries and §16.3 only takes strictly cheaper paths); stub areas or NSSAs as transit areas (refused by #224's validation); OSPFv3.
- Tests: `link::tests::virtual_link_reaches_full_and_joins_the_backbone` (in-memory wire, three routers), `diff_ignores_cost_but_not_the_virtual_neighbor`, `accepts_packet_demuxes_virtual_link_traffic_by_area_and_source`, `resolve_virtual_link_up_down_and_address`, `router_lsa_links_virtual_link_only_when_full`, `spf::tests::virtual_link_endpoint_follows_the_transit_area_path`, `virtual_link_is_a_backbone_edge_with_transit_next_hops`, `virtual_link_beyond_the_first_hop_inherits_the_next_hop`, `skip_summaries_ignores_type3_and_type4`, `transit_summaries_improve_backbone_routes`, `lsa::tests::virtual_link_router_lsa_round_trips`; `nos-e2e ospf-virtual-link` (also the kernel routes on both sides and their removal with the link).

### Graceful restart (RFC 3623)

A port of `nos-ospfv3d`'s RFC 5187 work ([OSPFv3 internals](ospfv3-internals.md)), nos↔nos only:

- **Grace-LSA** is a native body, `LsaBody::Grace` (`lsa::LSA_TYPE_OPAQUE_LINK` 9, Link State ID `3.0.0.0` — opaque type `OPAQUE_TYPE_GRACE` 3): RFC 3623 Appendix A's Grace Period, Restart Reason and IP Interface Address TLVs. Every other opaque type is `LsaBody::Opaque` (see "Opaque LSAs" below); the DBD O-bit makes other vendors send theirs (FRR's, in `nos-e2e ospf-opaque`). SPF ignores it.
- **Restarting side**: `OspfInstance.graceful_restart_grace_period` (`LinkManager::set_graceful_restart`). Only SIGTERM (`main::wait_for_shutdown_signal` returns `planned_restart`) announces: `LinkManager::announce_graceful_restart` asks every link task (`LinkEntry.grace_tx`) to unicast a Grace-LSA to each `Full` neighbor, twice, 500ms apart (`GRACE_SEND_WINDOW`), and sets `restarting`, which makes `shutdown` skip `withdraw_all_self_originated` and its flood window (RFC 3623 §2). SIGINT (watchdog stop, instance removal) still flushes. The restarted process resyncs cold — no RFC 3623 restart mode (originating before adjacencies are `Full` again).
- **Helper side**, always on: `handle_lsu` removes a newly installed Grace-LSA from the link's type-9 store under the same lock (never held, so never offered back to the restarted router) and calls `on_grace_lsa`, which sets `NeighborInfo.grace_deadline` for a `Full` neighbor (idempotent: the second copy only resets the deadline). While in grace: `apply_dead_timer`/`sweep_dead_neighbors` skip the neighbor, a Hello that doesn't list us keeps its state, `Lsdb::age_and_evict` (`LinkManager::age_lsdbs`' hold set) keeps its LSAs below `MaxAge` (a copy already at `MaxAge` is evicted as usual), and a DR keeps it in its Network-LSA. The restarted neighbor's Init DBD resyncs through the "DBDs in `Loading`/`Full`" rule above. Grace ends on `Full` again (`ospf helper: neighbor reformed, exiting grace early`), a `MaxAge` Grace-LSA, or the deadline (`expire_grace`, 1s tick on both network types). `ponytail:` no §3.2 (c) strict LSA checking.
- Routes need nothing: `nos-ribd` keeps a disconnected push client's OSPF routes.
- **Marker file** (skips RFC 6987 on-startup after a planned restart, #42): `main.rs` writes `<state-dir>/<instance>.gr` (the grace deadline in unix seconds, atomic write — `boot::write_grace_marker`) before `announce_graceful_restart`, only with a grace period configured (`ospf graceful restart marker written`; a write failure only warns, so the respawn applies on-startup — the safe side). The next process reads and **deletes** it once at start (`boot::take_grace_marker`) — valid only while `now < deadline <= now + u16::MAX`, so a respawn after the grace period (the helpers gave up), a clock jump or a corrupt file applies on-startup — and hands the result to `LinkManager::set_after_graceful_restart`.
- Tests: `link::tests::graceful_restart_is_helped_through_a_real_restart` (in-memory wire), `boot::tests::grace_marker_is_consumed_once_and_checked`; `nos-e2e ospf-graceful-restart` (also: on-shutdown not applied, marker written, on-startup skipped).

### Prefix suppression (RFC 6860, #184)

- **Knob**: `OspfInstance.prefix_suppression` (`set ospf instance <i> prefix-suppression`, `delete …` turns it off; provision `--ospf-prefix-suppression true|false`). Instance-wide, handed over with `LinkManager::set_prefix_suppression` (an atomic, so a toggle re-originates on the next tick without restarting links).
- **Router-LSA** (§2.1): `router_lsa_links` leaves out every p2p link's type-3 stub; the type-1 link stays. Loopback stubs are never hidden.
- **Network-LSA** (§2.2.2.1): as DR, `network_lsa_mask` gives it `255.255.255.255`; the LS-ID stays the DR's address.
- **SPF** (§2.2.2.2, always on, whatever the local setting): `collect_network_routes` skips a /32 Network-LSA. The vertex stays in Dijkstra, so transit, next hops and LFAs are unchanged, and `intra_area_routes` doesn't summarize it into other areas. A router without RFC 6860 installs a /32 host route to the DR instead.
- **NSSA forwarding address** (§4.1): `nssa_forwarding_address` uses only a loopback stub's address, else `0.0.0.0`.
- Not done: OSPFv3 (RFC 6860 §3).
- Tests: `link::tests::prefix_suppression_hides_the_p2p_stub_and_the_network_mask`, `spf::tests::hidden_transit_network_carries_transit_but_yields_no_route`; `nos-e2e ospf-prefix-suppression`.

### Stub router (RFC 6987, #42)

- **Knobs** (flat `OspfInstance` fields, handed to `LinkManager::set_max_metric` every resync; provision `--ospf-max-metric-on-startup <secs>`/`--ospf-max-metric-on-shutdown <secs>` (`0` clears) and `--ospf-max-metric-administrative true|false`):
  - `max_metric_on_startup: Option<u32>` (5-86400, `max-metric router-lsa on-startup`).
  - `max_metric_on_shutdown: Option<u8>` (1-3, `max-metric router-lsa on-shutdown`).
  - `max_metric_administrative: bool` (`max-metric router-lsa administrative`).
- **Router-LSA** (§2): `router_lsa_links(.., max_metric)` gives type-1 and type-2 links `lsa::MAX_LINK_METRIC` (0xFFFF, §3); type-3 stubs (and loopback stubs) keep their cost. Nothing else changes: no Type-3/4/5 metric raising (vendors' `summary-lsa`/`external-lsa`, outside the RFC).
- **State** (`MaxMetric` behind a `std` mutex): `max_metric_active()` = administrative, or inside the on-startup period — the one predicate RFC 8770's H-bit (#186 PR B) can OR into, beside `router_lsa_links`' `max_metric` input. The 2s origination tick reads it once (`max_metric_tick`), logging `ospf stub router max-metric changed active=… reason="administrative|on-startup|expired|cleared"` on a change; the period ends at most one tick late.
- **On-startup**: the first `set_max_metric` (the first config resolution after start) arms the deadline (tokio `Instant`); later calls never re-arm it (a new value takes effect on the next start, as on Cisco/FRR), `None` ends it. Skipped after a graceful restart (`ospf stub router on-startup skipped after graceful restart`, see "Graceful restart"'s marker file).
- **On-shutdown** (`LinkManager::max_metric_on_shutdown`, the first step of `shutdown` when no grace period was announced): re-originates the Router-LSAs with `max_metric` (`originate_router_lsas_with`, which reports whether any was installed), logs `reason="on-shutdown"`, kicks them out (`flood_now`), sleeps the configured seconds, then the usual flush. Skipped — `ospf stub router on-shutdown skipped, router-lsa unchanged or changed too recently` — when `MinLSInterval` holds the Router-LSA back (changed under 5s ago) or nothing would change; also skipped while max-metric is already active. Never under a grace period (RFC 3623 §3.2 (c): the restarter's LSAs must not change). The 1-3s range is what fits `nos-watchdogd`'s 10s SIGINT budget beside the 6s flush window; `docker-compose.yml`'s `stop_grace_period: 15s` covers a whole-container `docker stop`.
- **Receive side**: nothing (§4) — SPF already sums 0xFFFF as an ordinary metric, so a stub router still carries transit when it is the only path. The RFC 5286 §3.5 LFA guard is in "Loop-free alternates".
- **Not done**: OSPFv3's R/V6-bits (`nos-ospfv3d`), an operational "max-metric active" field in `show` (the log line is it).
- Tests: `link::tests::router_lsa_links_max_metric_raises_transit_links_only`, `on_startup_max_metric_lasts_its_period`, `on_startup_is_armed_once_cleared_by_none_and_skipped_after_graceful_restart`, `on_shutdown_advertises_max_metric_before_the_flush`, `on_shutdown_is_skipped_when_the_router_lsa_just_changed` (in-memory wire), `spf::tests::stub_router_*`; `nos-e2e ospf-stub-router` (administrative, on-shutdown and on-startup over a real restart, the LFA guard), `ospf-opaque` (FRR routes through a max-metric router-a at ≥ 65535, its stub subnet below), `ospf-graceful-restart` (the marker skip).

### Host router (RFC 8770, #186)

- **Knob**: `OspfInstance.host_router: bool` (`set ospf instance <i> host-router`; provision `--ospf-host-router true|false`), an atomic handed over with `LinkManager::set_host_router` every resync — no link restart.
- **Origination** (§3): `originate_router_lsas_with` sets `lsa::ROUTER_FLAG_H` (0x80) in every area and forces RFC 6987's `max_metric` on (transit links at 0xFFFF, stubs keep their cost). `max_metric_active()` includes it, so on-shutdown is skipped (nothing would change).
- **ASBR rule** (§3): commit refuses `redistribute … to ospf` on a table whose instance has `host_router` (`routing_table::valid_redistribute_rules`). nos has no Type-2 metric to set to LSInfinity, so refusing is the explicit choice.
- **Receive side** (§4/§5, `spf.rs`): `host_bit_honoured` — every live Router-LSA's originator has an RI (type 10 or 11) with bit 7; `host_routers` — the H routers when honoured, else none. `run_dijkstra` doesn't expand a host router unless it is root (a leaf: its stubs and Type-3/5s still route), which covers `compute`, `intra_area_routes`, the NSSA passes and every Dijkstra inside `alternates`; `alternates` also drops a host-router candidate (its own Dijkstra is rooted at it). Not honoured: nothing changes, the max-metric links steer traffic.
- **Log**: `compute_routes` logs `ospf host-bit state changed area=… honoured=… host_routers=…` (H routers seen, honoured or not) per area on a change.
- **Not done**: OSPFv3 (RFC 8770 is OSPFv2 only; OSPFv3 has the R-bit).
- Tests: `spf::tests::host_router_*`, `host_bit_support_counts_a_type_11_router_info`, `lsa::tests::router_info_capabilities_decodes_type_10_and_11`, `link::tests::host_router_sets_the_h_bit_in_every_area`, `routing_table::tests::redistribute_to_ospf_with_ospf_instance_passes`; `nos-e2e ospf-host-router` (router-c, all nos: honoured, router-a drops its LFA via c, back on clear) and `ospf-opaque` (FRR lacks bit 7: router-b doesn't honour router-a's H-bit, FRR routes via it at ≥ 65535).

### Hello prioritisation and liveness (RFC 4222, #185)

- **Recommendation 1** (Hellos and LSAcks first): `run()`'s `tokio::select!` is `biased;`, ordered hello ticker, `recv_packet`, p2p dead deadline, `dead_sweep`, `wait_deadline`, `grace_rx`, `rxmt_sweep` — a due Hello never loses a draw to the 5s full-LSDB resend, and a queued packet is read before a dead timer that became ready in the same poll. A received LSAck is already handled inline (`handle_lsack`, no lock, no await). `ponytail:` ceiling on the select: bias doesn't preempt a running arm (a handler waiting on the LSDB lock still delays the next Hello), and a sustained inbound queue runs the timer arms late; upgrade to a separate Hello task or a high/low receive queue if a large LSDB shows Hello starvation. No deterministic test (the starvation is a race).
- **Recommendation 2** (any packet proves liveness): `NeighborInfo.last_heard` drives the inactivity timer (`sweep_dead_neighbors`, `expire_grace`'s restart); `last_hello_received` is reported only (`last_hello_secs`). `note_alive`, called at the single decode site after the `accept_crypto_sequence` guard for every non-Hello packet, sets `last_heard` (and on p2p pushes `p2p_dead_deadline`) only for a neighbor at `ExStart` or later — the RFC's "over that adjacency". Hellos keep their own refresh in `handle_hello`, after its validity checks, so a dropped Hello never keeps a neighbor alive. `ponytail:` any destination counts, not only unicast / AllSPFRouters on p2p as the RFC words it (`recv_packet` returns no destination; that needs `IP_PKTINFO`).
- **Not done**: recommendations 3 (exponential retransmission back-off — `RXMT_INTERVAL` stays 5s), 4 (congestion-detection send gaps) and 5 (limit on simultaneous adjacency bring-up); pacing comes from `RXMT_INTERVAL`, `MinLSArrival` and `MinLSInterval` at the scale nos targets.
- Same in `nos-ospfv3d` (`ospfv3/src/link.rs`).
- Tests: `link::tests::note_alive_only_refreshes_an_adjacency`, `link::tests::{point_to_point,broadcast}_adjacency_survives_lost_hellos` (in-memory wire with `Wire::drop_hellos`), in both crates. No e2e phase: scheduling and timer bookkeeping only, nothing new on the wire, in the kernel or over IPC; the existing `ospf*`/`ospfv3*` phases cover adjacency and dead detection.

### Receive hardening (#394)

- **Source address** (RFC 2328 §8.2): `link::source_on_link` drops, with a `debug!` only (an off-link flood must not become log amplification), any packet whose source is outside the link's subnet. Exempt: point-to-point links (unnumbered / `/32` peers share no subnet) and virtual links (already pinned to the endpoint by `accepts_packet`).
- **Neighbor cap**: `nos_ospf_common::ratelimit::MAX_NEIGHBORS_PER_LINK` (64, a constant, `ponytail:`). `handle_hello` refuses a Hello from an unknown router-id once the link holds that many neighbors; known neighbors keep refreshing. Log: `ospf neighbor limit reached, dropping hello`.
- **Warning limit**: every `warn!` a bad Hello can trigger in `handle_hello` goes through one `WarnLimiter` per link run loop (burst 5, one more per second). The next allowed line is preceded by `ospf hello warnings were rate limited suppressed=N`.
- Same in `nos-ospfv3d`, except the source check is "must be link-local" (RFC 5340 §4.2.2) and applies to every packet type.
- Tests: `link::tests::{handle_hello_caps_neighbors_but_keeps_refreshing_known_ones,source_on_link_exempts_p2p_and_virtual_links_only}` (v3: the first only), `ratelimit::tests`. No new e2e phase (drops only); `ospf-suite` and `ospfv3` cover the exemptions.

### Link state from `nos-interfaced` (#277)

- **Stream**: `link_client::run` resolves `ServiceRef::Interfaces`, sends `InterfaceRequest::SubscribeLinks` and folds `LinkSnapshot`/`LinkChanged`/`LinkRemoved` into a `watch<LinkTable>`; `send_if_modified` wakes nobody for an event that changes nothing. On loss the table is kept (`connected = false`) and the client retries every 1s; a fresh snapshot replaces the whole table.
- **Gate**: `link_client::gate(table, kernel_device)` is `Ungated` (never connected, or `observed = false` i.e. the noop driver), `Up(ifindex)` or `Down(absent | admin-down | no-carrier)`. Only `reconcile::resync` gates, per physical and broadcast attach point (never inside `link::run`; loopback stubs and virtual links are not gated). A `Down` link is left out of `desired_links`, so `apply_links` aborts it (RFC 2328 §9.3 InterfaceDown, §10.3 KillNbr; logs `ospf link stopped`).
- **Recreated devices**: `LinkConfig.ifindex` is part of the config, so a device that came back with a new ifindex restarts the link with a fresh raw socket. A link that was ungated (ifindex 0) restarts once when the first snapshot arrives.
- **Trigger**: `run()` selects on the table; after `LINK_DEBOUNCE` (200ms) it resyncs only if the gates of the watched devices (every device resolved by the last resync, before gating) differ from the last resync's. The 10s tick stays the safety net. Logs only on transitions.
- **Keep the running link**: a failed VRF, address or bridge lookup (`nos-ribd`/`nos-interfaced` restarting) falls back to the running link's value (`merge_running`, `LinkManager::running_config`), logging `ospf link resolution failed, keeping running link link=… missing=vrf|address|bridge` once. Config, not the lookup, decides whether the link is still wanted: an attach point whose config has no IPv4 address (`has_address`) or no routing table gets no fallback and is dropped. Profile changes (cost, timers, auth) still apply meanwhile.
- Tests: `link_client::tests`, `reconcile::tests::{merge_running_table,signature_only_covers_watched_devices,attach_points_know_whether_the_config_has_an_address}`, `link::tests::{running_config_follows_the_task,ifindex_change_restarts_but_cost_does_not}`; `nos-e2e ospf-remote-lfa` (nos-interfaced kill, veth delete, carrier loss).

### Opaque LSAs (RFC 5250)

- **Bodies**: types 9/10/11 decode to `LsaBody::Opaque(Vec<u8>)`, the body bytes kept as received so a re-encode keeps the originator's checksum; the Grace-LSA (type 9, opaque type 3) stays `LsaBody::Grace`. SPF ignores both. `lsa::is_opaque`/`is_link_local_scope`/`opaque_type`.
- **O-bit**: every DBD sends `exchange::DBD_OPTIONS` (E|O); Hellos stay E only (RFC 5250 §3). `nos_ospf_common::exchange` records the peer's O-bit (`Params::peer_opaque_capable`, from `exchange::peer_opaque_capable`) in `AdjacencyData.opaque_capable` at `ExStart` and leaves opaque headers out of a non-capable peer's summary; `flood_full_neighbors` builds one LSU per group (capable or not). FRR originates no opaque LSA until a neighbor's DBD has the O-bit.
- **Scopes**: type 9 lives in a per-link `Lsdb` (`LinkEntry.link_local_lsdb`, created with the link task, dropped with it), never the area's: `on_lsu_received` picks the store by type, `on_lsr_received` looks in the area store then the link's, `handle_dbd`'s summary and `flood_full_neighbors` add the link's headers/LSAs, `age_lsdbs` ages it and `database_summaries` lists it under the link's area (no link column). Type 10 is the area store. Type 11 goes into the area it arrived in, like a received Type-5 — `ponytail:` an ABR doesn't flood it on to its other areas.
- **Unknown types**: `packet::decode_lsu` skips an `UnknownLsaType` LSA by its header length (RFC 2328 §13 step 2) and keeps the rest of the LSU — no ack for it, so the sender retransmits it.
- nos originates two opaque LSAs: its Grace-LSA (sent to every `Full` neighbor, O-bit or not, as before #40) and the RFC 7770 Router Information LSA below.
- **Router Information LSA** (RFC 7770, #186):
  - Type 10, opaque type 4, Link State ID `4.0.0.0` (`lsa::ROUTER_INFO_LINK_STATE_ID`), one per attached area — area scope so stub areas and NSSAs carry it too.
  - Body: the Informational Capabilities TLV only (`lsa::encode_router_info`), kept as `LsaBody::Opaque`. Bits: GR helper (`RI_CAP_GR_HELPER`, always — helping is always on), stub router support (`RI_CAP_STUB_ROUTER`, bit 2, always — RFC 6987 is implemented), GR capable (`RI_CAP_GR_CAPABLE`) while `graceful_restart_grace_period` is set.
  - Originated by `originate_router_lsas` beside the Router-LSA, so it shares its pacing, refresh, flush on leaving an area, and shutdown flush.
  - Also host router support (`RI_CAP_HOST_ROUTER`, bit 7, always — RFC 8770 is implemented). A received RI's capabilities are read by `lsa::router_info_capabilities` (type 10 or 11), for the H-bit check below; its body stays `LsaBody::Opaque`.
- Tests: `lsa::tests::opaque_lsas_round_trip_as_raw_bytes`, `packet::tests::lsu_skips_an_unknown_lsa_type_and_keeps_the_rest`, `exchange::tests::opaque_*`, `link::tests::opaque_lsas_are_flooded_by_scope` (in-memory wire), `lsa::tests::router_info_body_is_one_capabilities_tlv`, `link::tests::originate_router_lsas_originates_router_info_per_area`; `nos-e2e ospf-opaque` (FRR, which also accepts router-a's RI LSA).

### Not applicable RFCs (#45)

- **RFC 1793 (demand circuits)**: nos never sets the DC option, so DC-capable neighbours never send it DoNotAge LSAs; nothing to implement.
- **RFC 4577 (DN-bit)**: only matters on a PE, and nos has no BGP L3VPN (VPNv4) address family. Revisit when that exists.

## Testing without raw sockets

`link::LinkSocket` is either the real `OspfSocket` or, under `#[cfg(test)]`, a port on an in-memory wire (`link::tests::wire`); `LinkManager::with_opener` picks which one every link opens (`new` = the real socket). The `link::tests` scenarios run whole `LinkManager`s over that wire with `#[tokio::test(start_paused = true)]`, so Hello/dead/wait/retransmit timers pass instantly: p2p `Full` plus SPF and a Type-5, a 4-router DR/BDR election, crypto/simple auth match and mismatch, and DBD pagination (#131). `socket.rs` itself stays excluded from coverage — `nos-e2e` is its test.

## Watchdog/broker wiring

`nos-watchdogd` gives every `nos-ospfd` instance a real `--listen-socket` (`/run/nos/ospf-<name>.sock`) and registers it in `EndpointRegistry` under `EndpointKind::OspfInstance` — the `ServiceRef`/registry plumbing that already existed generically (see `docs/architecture/endpoint-broker.md`) is now actually wired up, not just present.
