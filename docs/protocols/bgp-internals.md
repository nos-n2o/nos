# nos-bgp internals

How `nos-bgp` implements BGP: functions, data structures, log lines to grep for, and `ponytail:` ceilings. For configuration and behaviour see [BGP](bgp.md) and [EVPN and VXLAN](evpn-vxlan.md); the rules to respect when editing the crate are in [`bgp/CLAUDE.md`](../../bgp/CLAUDE.md). Which `nos-e2e` phase covers what is in [`docs/e2e-phases.md`](../e2e-phases.md).

## Scope

`nos-bgpd` resolves its own configured peers and VRF from `nos-configd`, opens/accepts VRF-scoped TCP connections to/from those peers (see "Raw TCP session model" below), and runs a real BGP-4 finite state machine (RFC 4271) over each connection: OPEN/KEEPALIVE exchange up through the `Established` state, with hold-timer/keepalive-timer maintenance and real RFC 4271 §6.8 collision resolution. Once `Established`, route exchange (UPDATE messages, full RIB integration — see `rib.rs`) and RFC 2918 ROUTE_REFRESH are both supported. See "BGP finite state machine" and "Route refresh (RFC 2918)" below.

### VRF resolution

A `BgpInstance` carries a reflexive, read-only `routing_table: Option<String>` field (`nos-proto`'s `derive::sync_routing_table_refs`, mirrored from the owning `RoutingTable.bgp_instance` on every config load/commit — see [Schema reference](../schema-reference.md)). `nos-bgpd` reads this directly instead of scanning every `RoutingTable`, then resolves the named table's real Linux VRF interface name the same way `nos-interfaced` does: `ServiceRef::RibTable(name)` via the watchdog broker, then `RibRequest::GetVrfName` directly against that `nos-ribd` instance (`rib_client::get_vrf_name`).

This resolves to one of three states (`session::VrfRequirement`):
- **`Invalid`** — no owning routing table at all. Treated as a config error, **not** a "run unscoped in the default VRF" fallback — BGP always belongs to a VRF in this system. Logged as an error every resync; no session or listener is ever opened while in this state.
- **`Pending`** — an owning table exists but its VRF isn't allocated/known yet (the table's `nos-ribd` instance isn't up, or hasn't created its VRF yet). A normal, transient condition, logged at `debug`, retried by the periodic re-apply tick.
- **`Resolved(name)`** — the VRF's real Linux interface name. Only in this state does `nos-bgpd` open anything.

### Raw TCP session model

Once resolved, `session::SessionManager` maintains, per configured peer, both sides of a TCP session, scoped into the VRF via `SO_BINDTODEVICE` (`tcp.rs`, `socket2::SockRef` over a `tokio::net::TcpSocket` — a socket-level equivalent of `nos-ribd`/`nos-interfaced`'s `rtnetlink`-based VRF enslavement, since no interface or route is being programmed here):
- **Active**: a per-peer retry loop attempts an outbound connect (`fsm::CONNECT_RETRY_TIME`, RFC 4271's own suggested `ConnectRetryTimer` default) to the peer's `remote_address:179`, optionally bound to its peer-group's `source_address` — but skips dialing out entirely whenever `PeerSlot::is_established` is already true (in either role), so a session held open by the passive side doesn't see a redundant, pointless outbound attempt (and the collision it would otherwise trigger) every `CONNECT_RETRY_TIME`. Found via real two-container verification — see "Verification" below.
- **Retry timing** (#158): the sleep between attempts is jittered to `[0.75, 1.0] × connect_retry_time` (RFC 4271 §10, `session::jittered`, std-only randomness) — a §6.8 collision closes both routers' connections at the same instant, and an unjittered fixed sleep redials them in lockstep so they collide again every cycle. Each `tcp::connect` is also bounded by `connect_retry_time` (§8.2.2: ConnectRetryTimer expiring in Connect drops the attempt), so an unanswered SYN (`SYN_SENT`) no longer holds the Active role for the kernel's ~2min SYN-retry budget. That was the real e2e flake: `nos-bgpd` resolves the VRF as soon as `nos-ribd` creates it, up to one 10s `nos-interfaced` tick before eth0 is enslaved, so the first dial leaves the empty VRF with source `0.0.0.0` and is never answered — both routers sat in `SYN_SENT` with their listeners idle.
- **Passive**: one shared listener (`0.0.0.0:179` + `[::]:179`) accepts inbound connections, matching the remote IP against the configured peer set; an unconfigured remote is rejected.

**Both roles must be stopped when a peer is reconciled away or respawned.** `SessionManager::peer_tasks` owns only the *active*-connect loop; a passive session is spawned per accepted connection by `handle_inbound`, so it is tracked on its `collision::PeerSlot` (`set_passive_task`/`stop_passive`) — otherwise `reconcile_peers` has nothing to abort and an established passive session keeps serving the `ResolvedPeer` it was accepted with (stale policies, auth and timers) for as long as it stays up, while the active side restarts normally. Which side that is depends on who won the collision, so the symptom is non-deterministic. Because both stops are `abort()`s, the cancelled tasks never reach `fsm::run`'s own exit path, so `reconcile_peers` also calls `BgpRib::peer_disconnected` itself — without it the peer's `adj_rib_in`/`peer_outbox` outlive the sessions that owned them and its routes stay in the Loc-RIB.

Once a `TcpStream` exists (either side), `fsm::run` takes over — see "BGP finite state machine" below.

### Session authentication

A `BgpPeerGroup`'s optional `auth` (`nos_proto::BgpAuth`) is either a single RFC 2385 TCP MD5 password, or one or more RFC 5925 TCP-AO keys (`HMAC-SHA-1-96`/`AES-128-CMAC-96`, with `send_id`/`recv_id`-based rotation via `is_current`/`is_rnext`, and `exclude_options` — RFC 5925 §5.2, `TCP_AO_KEYF_EXCLUDE_OPT` — excluding TCP options from the key's MAC coverage; both peers must agree on it or authentication fails) — the two mechanisms are mutually exclusive, matching the kernel (a socket accepts only one). `BgpAuth` holds admin key labels (`key_ref`), never secrets (#508): `reconcile::resync` resolves it with `session::ResolvedAuth::resolve(&BgpAuth, &Config)` (a `bgp`-local mirror using `nos_tcp_auth`'s wire-level types, looking each label up with `Config::key`; an unknown label yields `None` and a `warn!` naming only the label, so the peer has no auth and its session fails loudly). RPKI caches go through `rpki::resolve_auths`, whose result is part of what the RTR client was started with. `nos-bgpd` subscribes to `DiffScope::Admin`, so a rotated secret under the same label makes the resolved peers differ and the usual restart-on-change applies. `ResolvedAuth` carries the raw secret, so its `Debug` is redacted; `session::ResolvedPeer`'s `PartialEq`-based restart-on-any-change (`diff_peers`) covers an auth change like a changed `remote_as` — except a TCP-AO change `session::ao_delta` can express (keys added/removed, `is_current`/`is_rnext` moved, nothing else different on the peer), which is applied in place (#83, below).

`session::to_peer_summary` also reports a TCP-AO peer's live kernel state (RFC 5925 §7.2/§7.5) in `PeerSummary`: the KeyID currently signing outgoing segments, the RecvID of our own rnext key (the RNextKeyID *we* ask the peer to send with — `TCP_AO_INFO`'s `rnext` is not the peer's request; the peer's request shows up as the KeyID moving), and per-connection good/bad/key-not-found packet counters, from an on-demand `getsockopt(TCP_AO_INFO)` (`nos_tcp_auth::get_ao_info`) against the `Established` connection's fd — captured by `fsm::run` (alongside its existing `local_addr` capture, right before `into_split()`) into `status::PeerStatus.fd`, the one channel already carrying FSM-owned state out to the query boundary. `None` for an MD5/no-auth peer, a non-`Established` peer, or a readback racing session teardown (harmless — indistinguishable from "no AO auth", `ponytail:`-flagged rather than engineered around). Verified by `nos-e2e ao`.

**Hitless rollover (#83).** `nos-bgpd` never writes `is_current` back to config: the *kernel* already does RFC 5925 §7.5.2 per connection (`tcp_inbound_ao_hash`: a verified segment whose RNextKeyID differs from `current_key`'s SendID and matches an installed key's SendID makes that key current; the peer puts its RecvID there, which is our SendID for the same MKT), so config `is_current` only seeds *new* connections. What used to break a rollover was the restart on every key change; `ao_delta` now turns an AO-only `ResolvedAuth` change into an `AoDelta` (add, remove, rnext RecvID) and `diff_peers` returns it in a third list, `to_update`:

- the listener fds get adds/deletes (`tcp::apply_ao_delta`, `live = false`: a listener has no current/rnext), `applied_auth` follows;
- `PeerSlot::auth()`/`set_auth()` (the slot's `peer.auth` is immutable, so a mutex copy) hold the keys every *new* connection (`active_connect_loop`, `handle_inbound`, `to_peer_summary`) starts from;
- an `Established` session gets `FsmCommand::UpdateAo`, handled in `fsm::run`'s command arm (which owns the fd, so there is no stale-fd risk): adds, then `set_ao_rnext`, then deletes. Any error (expected: `EBUSY` for a key the peer still signs with or advertises) logs `failed to update tcp-ao keys in place, resetting session` and leaves through the Cease/Other Configuration Change path; the reconnect uses `slot.auth()`. Success logs `bgp tcp-ao keys updated in place`.

`ao_delta` returns `None` (restart) for MD5 on either side, a kept key whose RecvID/algorithm/secret/`exclude_options` changed (an MKT is immutable for a connection), and an added key reusing the RecvID of a key being removed (the kernel's `EEXIST` on RecvID overlap, RFC 5925 §3.1, which `valid_auth` now also rejects at commit; adds run before deletes). Without a flagged rnext, the advertised RNextKeyID is the `is_current` key's RecvID (`session::ao_rnext`): on connect (`apply_auth` sets `set_rnext` on it) and on in-place updates — and on **accept** (`handle_inbound` calls `nos_tcp_auth::set_ao_rnext`), because an accepted socket otherwise advertises whatever KeyID the peer's SYN used. Only rnext is ever pushed to a live socket, never `set_current`: forcing it would break a session whose peer doesn't have that key yet.

Authentication is entirely socket-level and never reaches `fsm.rs` — by the time a `TcpStream` exists, the kernel has already verified (or the handshake never completed):
- **Active**: `tcp::connect` applies the peer's `ResolvedAuth` (via `tcp::apply_auth`, `nos_tcp_auth::{set_md5_key, add_ao_key}`) to the outbound socket before `.connect()`.
- **Passive**: since one shared listener serves every configured peer, a key must be installed on the *listening* socket itself, scoped to the specific peer address — Linux allows adding `TCP_MD5SIG`/TCP-AO keys to an already-listening socket at any time; they apply to future SYNs, not retroactively. `session::SessionManager` tracks each `Listeners`' raw v4/v6 fds (the `TcpListener`s themselves are moved into `accept_loop`'s spawned task) plus which peer currently has which key installed (`applied_auth`). `spawn_listeners` primes every desired peer's key on a fresh bind (needed even when the peer set is unchanged, e.g. a VRF flap); `reconcile_peers`' existing `to_stop`/`to_spawn` diff doubles as exactly the "remove key" / "install key" list for `sync_listener_auth` on every later change. `tcp::apply_auth`'s `on_listener: bool` param strips a TCP-AO key's `set_current`/`set_rnext` bits before installing on this socket — found by running `nos-e2e ao` against a real kernel: `TCP_AO_ADD_KEY` returns `EINVAL` for either bit on a socket in `LISTEN` state (a listener has no single connection for "the currently signing key" to mean anything on; the kernel matches an accepted connection's key from the wire's KeyID/RNextKeyID against every key installed here regardless of the flag). The active side still sets them for real, since an outbound socket needs a key to sign its own initial SYN with before any wire data exists to match against.

`nos_tcp_auth::add_ao_key`/`delete_ao_key` set `ifindex = 0`, not `-1` — `TCP_AO_ADD_KEY`'s `ifindex` field is only meaningful with `TCP_AO_KEYF_IFINDEX` set (never done here, since VRF scoping is already applied via `SO_BINDTODEVICE`), and the kernel rejects any other value with `EINVAL`. Also found by `nos-e2e ao`: this bug blocked *every* TCP-AO key install, active or passive, so TCP-AO had never actually worked end to end before that phase existed (only RFC 2385 MD5 had e2e coverage — see `auth`).

Secrets are stored **clear-text** end-to-end (config, transaction diffs, `nos-cli` rendering) — this system has no encryption-at-rest anywhere, so there's no established masking convention to be consistent with. The raw `setsockopt(TCP_MD5SIG)`/`setsockopt(TCP_AO_ADD_KEY/DEL_KEY)` calls live in `nos-tcp-auth` (`tcp-auth/`, see root `CLAUDE.md`), not here — `nos-bgp` only ever calls its safe wrapper functions.

### GTSM / `max-hops` (RFC 5082)

A `BgpPeerGroup`'s `max_hops` (1..=254, CLI `set max-hops <n>`, `--max-hops` on `nos-provision`) sets TTL/hop-limit 255 and `IP_MINTTL`/`IPV6_MINHOPCOUNT` = `256 - n` via `nos_tcp_auth::set_max_hops`, applied by `tcp::apply_max_hops` on the outbound socket before `connect()` and on the accepted stream in `handle_inbound` (the minimum is per socket, so it can't live on the shared listener). `tcp::bind_listener` always sets the listener TTL to 255 so the SYN-ACK and accepted sockets pass a GTSM peer's check (found by `nos-e2e gtsm`: without it a GTSM active side drops the SYN-ACK). Consequence: enabling it on one side only still yields a session via that side's active connect. Not implemented: the default TTL 1 for directly connected eBGP (issue #10's last point). Verified by `nos-e2e gtsm`.

### BGP finite state machine

`fsm.rs` implements the RFC 4271 states that need message exchange — `OpenSent`, `OpenConfirm`, `Established` — layered on top of the raw TCP connectivity above (Idle/Connect/Active remain `session.rs`'s retry-loop behavior; `fsm::run` is spawned only once a stream already exists, replacing what used to be `hold_until_closed`). `fsm::step` is the pure transition core (state + event -> next state + actions), unit-tested directly; `fsm::run` is the async orchestrator that owns the `BgpCodec`-framed socket and the hold/keepalive timers.

OPEN validation (`fsm::handle_open`) checks, in order: BGP version (must be 4), the peer's real ASN against the configured `BgpPeerGroup.remote_as` (see "Four-octet AS numbers" below), the BGP Identifier's validity (`message::is_valid_bgp_identifier` — rejects `0.0.0.0`, multicast, broadcast), and the proposed hold time (`0`, or `>= 3` per RFC 4271 §6.2 — `1`/`2` are invalid). Any failure sends the matching RFC 4271 §6 `NOTIFICATION` (Error Code `OpenMessage`, the specific subcode) and closes; a hold-timer expiry at any state sends `NOTIFICATION(HoldTimerExpired)`. The negotiated hold time is `min(local, remote)`, where "local" is the owning `BgpPeerGroup`'s configured `hold_time` (`nos_proto::HOLD_TIME_DEFAULT`, 90s, when unset); keepalive interval defaults to `negotiated_hold / 3` but can be overridden by the peer-group's `keepalive_interval`, itself falling back to the `/3` derivation whenever the override doesn't fit under what was actually negotiated (config-time validation only checks the override against the locally-configured hold-time, not the post-negotiation one); a negotiated hold time of `0` disables both timers entirely regardless of any override, per RFC 4271. A peer-group's `connect_retry_time` (`nos_proto::CONNECT_RETRY_TIME_DEFAULT_SECS`/`fsm::CONNECT_RETRY_TIME`, 120s, when unset) governs `session.rs`'s outbound retry interval the same way. A peer-group's `mrai` (seconds, unset/0 = unpaced) is RFC 4271 §9.2.1.1's `MinRouteAdvertisementInterval`, applied in `fsm::run`'s outbound arm by `mrai::Mrai` per peer per prefix (and ADD-PATH id): a first advertisement is sent at once (so a session's initial dump is not delayed), a changed one within the interval is held and collapses to the latest, withdrawals are never held; EVPN routes are not paced. Verified by the `mrai` e2e phase. All three timer constants/defaults live in `nos_proto` (alongside the `BgpPeerGroup` fields themselves) rather than `nos-bgp`, since `nos-config`'s commit-time validation needs the same floor/ratio rules `fsm.rs` applies at runtime.

Every well-formed inbound message (not just KEEPALIVE) resets the hold timer, per RFC 4271 §4.4 — handled centrally in `fsm::run`'s read branch rather than per-message-type. UPDATE and ROUTE_REFRESH both bypass `step()`'s OpenSent/OpenConfirm/Established transition table entirely — they're short-circuited directly in `fsm::run`'s read branch, meaningful only once `Established` (silently logged and ignored otherwise, same as before that state). `Unhandled` now covers only genuinely unrecognized message types.

### Extended optional parameters (RFC 9072)

`message::parse_open` accepts the extended OPEN form (`opt_param_len == 255` then a `255` type octet, a 2-byte length, and 2-byte per-parameter lengths); `encode_open` emits it only when the capabilities exceed 255 bytes, otherwise the classic form byte-for-byte. Unit-tested only (nothing here generates that many capabilities yet).

### Four-octet AS numbers (RFC 6793)

`BgpInstance.asn`/`BgpPeerGroup.remote_as` are `u32`, wider than OPEN's plain 2-byte "My Autonomous System" field, so `message::build_open` always advertises the four-octet AS number capability (code 65) and uses `AS_TRANS` (23456) as the 2-byte field's placeholder whenever the real ASN doesn't fit. `message::effective_remote_asn` reads the real value back out — preferring the capability when present, falling back to the plain field for interop with peers that never send it. An `AS_TRANS` value with no backing capability is treated as a malformed/bad-peer-AS OPEN, since it's otherwise meaningless.

A peer that never sent the capability (`fsm::RemoteInfo.four_octet_as == false`) gets RFC 6793's transition encoding, switched on at `Established` via `BgpCodec::two_octet_as` (set on both halves next to `add_path_afis`): outbound `AS_PATH` is 2-byte with `AS_TRANS` for any ASN > 65535, plus an `AS4_PATH` carrying the real path only when some ASN was squashed (§4.2.2); inbound `AS_PATH` is read as 2-byte and its trailing AS numbers are replaced by `AS4_PATH` (§4.2.3, `AsPath::merge_as4`: counted the RFC 4271 way — an `AS_SET` is one, confederation segments none and always kept — a longer `AS4_PATH` is ignored, and one from a four-octet peer is ignored too). `AS4_PATH` never carries confederation segments on send; a received one that does, or one that is malformed, is discarded and the route kept with the 2-octet path (RFC 6793 §6, RFC 7606 §7.11). `AGGREGATOR` follows the same rule (2-byte with `AS_TRANS` plus `AS4_AGGREGATOR` toward such a peer, merged back on receipt) — see "ATOMIC_AGGREGATE / AGGREGATOR" below.

### ATOMIC_AGGREGATE / AGGREGATOR

`ATOMIC_AGGREGATE` (type 6) and `AGGREGATOR` (type 7) are decoded into `PathAttributes.{atomic_aggregate, aggregator}`, stored on `RibRoute`, and re-advertised verbatim to every eligible peer (RFC 4271 §5.1.6/§5.1.7 — transitive, no eBGP/iBGP split, like communities). A malformed one (wrong length) is discarded on its own, not treat-as-withdraw (RFC 7606 §7.7/§7.8). Locally they're generated only for an aggregate (below). RPL cannot read them.

### Aggregation (RFC 4271 §9.2.2.2, #78)

`BgpInstance.aggregates` (`nos_proto::BgpAggregate { prefix, as_set, summary_only }`, keyed by prefix; `set bgp instance <i> aggregate-address <prefix> [as-set] [summary-only]`; validated by `valid_aggregates`: network-aligned, not a host route, unique) reaches the RIB as `BgpRib::set_aggregates`, called by `reconcile::resync` after `SessionManager::reconcile` (so the local ASN/router-id are set). All of it lives in `rib/aggregate.rs`.

- **Contributors**: the Loc-RIB prefixes strictly more specific than the aggregate (`AggregateState.contributors`). `recompute_and_propagate` calls `update_aggregates_for(prefix)` after its Loc-RIB insert/remove and **before** the per-peer fan-out (`fan_out`, split out of it), so a `summary-only` aggregate activated by a prefix already suppresses that prefix. `set_aggregates` seeds a changed config with one Loc-RIB scan, withdraws aggregates that went away, and re-fans every prefix covered by an old or new `summary-only` aggregate. An unchanged config is a no-op.
- **The route**: an active aggregate is a local candidate in `BgpRib.aggregated`, beside `redistributed` (`origin: Local`, `next_hop: None` — next-hop-self, never pushed to `nos-ribd`, so no discard route is installed). A changed aggregate re-runs `recompute_and_propagate` on its own, strictly shorter prefix, which terminates the recursion and handles nested aggregates. Attributes: `ORIGIN` the worst of the contributors'; `AS_PATH` empty, or with `as-set` the contributors' common leading `AS_SEQUENCE` plus one sorted `AS_SET` of every other ASN (RFC 4271 Appendix F.6, confederation segments dropped, `as_set_path`); `ATOMIC_AGGREGATE` when a contributor carries it, or without `as-set` when some contributor's path is non-empty; `AGGREGATOR` = member `asn` + router-id (the codec already does `AS_TRANS` + `AS4_AGGREGATOR`); no MED, communities or non-default `LOCAL_PREF`. `received_at` is kept across rebuilds (it is part of `RibRoute`'s `PartialEq`).
- **`summary-only`**: `suppressed_by_aggregate(prefix)` (an active `summary_only` aggregate strictly covers it) makes `fan_out` withdraw/withhold the prefix, and `peer_established`/`resend_all` skip it. Activation or withdrawal of such an aggregate re-fans its contributors. Contributors are still pushed to `nos-ribd`. A route-server client's `propagate_add_path` view is deliberately untouched (RFC 7947 transparency).
- Logs: `bgp: aggregate activated|updated aggregate=… contributors=… as_set=…`, `bgp: aggregate withdrawn aggregate=…`, plus the usual `loc-rib best path for <agg> updated`.
- `ponytail:` ceilings: linear scan of the aggregates per Loc-RIB change (free with none), `as-set` rebuilt from all contributors per change, the RFC 4271 §9.2.2.2 "different MEDs are not aggregated" rule not enforced (FRR's `matching-MED-only` is opt-in too), an aggregate's validation state/AGGREGATOR not refreshed on a VRP or router-id change until a contributor changes. Not implemented: suppress/unsuppress/attribute maps, RPL access, a discard route.
- **Loop prevention is an implicit withdraw**: a received route dropped for our own ASN in `AS_PATH`, our cluster-id in `CLUSTER_LIST` or our router-id as `ORIGINATOR_ID` now also removes that peer's earlier route for the prefix (`withdraw_announced`, RFC 4271 §9.1.2: an unfeasible route replaces the previous one) — before, the stale route stayed in Adj-RIB-In.


### Malformed UPDATE handling (RFC 7606)

`message::parse_update` resets the session (`WireError::MalformedUpdate` → NOTIFICATION) only for *framing* errors: a truncated attribute header, an attribute length overrunning the list, a malformed `MP_REACH_NLRI`/`MP_UNREACH_NLRI`, or a bad withdrawn-routes/NLRI field. A malformed attribute *value* (ORIGIN, AS_PATH incl. AS 0 per RFC 7607 and an unknown or empty segment per §7.2, NEXT_HOP, LOCAL_PREF, MED, ORIGINATOR_ID, CLUSTER_LIST, the three community types) or a missing mandatory attribute is **treat-as-withdraw**: `parse_update` rewrites the message so its legacy NLRI land in `withdrawn_routes` and each `mp_reach` batch becomes an `mp_unreach` batch (ADD-PATH ids carried), with `attributes = None`, and logs `treating announced routes as withdrawn`; `BgpRib::handle_update` needs no special case. Covered end to end by `nos-e2e malformed-update` (ExaBGP sending a 3-byte COMMUNITY beside a good route: the good one is learned, the session isn't reset). Not implemented: AFI/SAFI-disable for MP errors.

**Next-hop validation (#393).** `BgpRib::handle_update` (`rib/adj_in.rs`), next to the loop/OTC/cluster checks, treats the whole UPDATE as a withdraw (`withdraw_announced`, log `treating bgp update as withdraw: invalid next hop`) when the legacy `NEXT_HOP` (only if it carries NLRI) or any `mp_reach` batch with NLRI/EVPN has `message::next_hop_is_martian` true: `0/8`, loopback, multicast, class E, `::`, `::1`, `ff00::/8`, IPv4-mapped, or equal to `PeerOutbox::local_addr`. Link-local IPv6 is valid; loopback is allowed when the peer itself is on loopback. `ponytail:` own-address is the session address only, not every interface address; no eBGP on-link requirement (third-party next hops stay legal). Covered by `nos-e2e malformed-update` (ExaBGP next hop `240.0.0.1`).

**Next-hop validation (#393).** `BgpRib::handle_update` (`rib/adj_in.rs`), next to the loop/OTC/cluster checks, treats the whole UPDATE as a withdraw (`withdraw_announced`, log `treating bgp update as withdraw: invalid next hop`) when the legacy `NEXT_HOP` (only if it carries NLRI) or any `mp_reach` batch with NLRI/EVPN has `message::next_hop_is_martian` true: `0/8`, loopback, multicast, class E, `::`, `::1`, `ff00::/8`, IPv4-mapped, or equal to `PeerOutbox::local_addr`. Link-local IPv6 is valid; loopback is allowed when the peer itself is on loopback. `ponytail:` own-address is the session address only, not every interface address; no eBGP on-link requirement (third-party next hops stay legal). Covered by `nos-e2e malformed-update` (ExaBGP next hop `240.0.0.1`).

**First-AS check (#392).** `BgpRib::handle_update` (`rib/adj_in.rs`), after the next-hop and stray-confederation-segment checks, treats the UPDATE as a withdraw (`withdraw_announced`, log `treating bgp update as withdraw: first AS of as_path is not the peer's AS`) when the peer is eBGP, not a confederation member, in `first_as_peers`, `peer_as != 0`, and the first segment is not an `AS_SEQUENCE` starting with `peer_as`. `fsm.rs` sets `first_as_peers` through `set_peer_enforce_first_as(peer, ResolvedPeer.enforce_first_as && !route_server_client)` before `peer_established`. The warning goes through `first_as_warn_due`: one per peer per 10s (`FIRST_AS_WARN_EVERY`) with the count `suppressed`, dropped on disconnect. Covered by `nos-e2e local-as` (ExaBGP announcing first AS 65777, then `--no-enforce-first-as`).

Per-attribute rules in `parse_path_attributes`:
- Flags (§3(c)): the Optional and Transitive bits must match `expected_flags(type)` (the same values the encoder emits, `OTC` included); a mismatch is treat-as-withdraw, or a session reset for `MP_REACH_NLRI`/`MP_UNREACH_NLRI` (Malformed Attribute List, subcode 1). Partial and Extended-Length are never checked; unknown types are never checked.
- Duplicates (§3(g)): a repeated `MP_REACH_NLRI`/`MP_UNREACH_NLRI` resets the session; any other repeat keeps the first occurrence and discards the rest (`debug` log), the UPDATE is processed.
- An UPDATE or End-of-RIB before `Established` is an FSM error (`Event::UnexpectedUpdate` -> NOTIFICATION 5/1 in OpenSent, 5/2 in OpenConfirm, RFC 4271 §8.2.2 / RFC 6608).

### Route flap damping (RFC 2439)

A `BgpPeerGroup`'s `damping` (`nos_proto::BgpDamping { half_life, reuse, suppress, max_suppress }`, seconds; CLI `set damping [half-life N] [reuse N] [suppress N] [max-suppress N]`, RFC 7196 defaults 900/750/6000/3600; eBGP groups only, checked in `bgp_instance::valid_route_reflection_and_server`) damps routes **received** from its peers. `damping::Damping` (pure, owned by `BgpRib`) keeps a decaying penalty per (peer, prefix): +1000 when a held route is withdrawn (or an import policy now rejects it), +500 when it is re-announced with different attributes (`learn_prefix` compares ignoring `received_at`), 0 for an identical re-announcement — which also keeps the stored `received_at`, so it is no change downstream (no re-propagation, no reset of the step-8 route age, #160); it halves every `half_life` and is capped at `reuse * 2^(max_suppress/half_life)`. At `>= suppress` the route is suppressed: it stays in Adj-RIB-In but `recompute_and_propagate`/`propagate_add_path` skip it as a candidate. A 5s task (`main.rs` → `SessionManager::damping_tick` → `BgpRib::damping_tick`) decays and releases (`< reuse`) and re-decides the prefix. Logs `route suppressed by flap damping` / `route released from flap damping`. `fsm::run` hands the group's value to the RIB after `peer_established` (`set_peer_damping`); a session reset clears the peer's state. Not implemented: EVPN/redistributed routes, keeping history across session resets, a `show` command. Verified by `nos-e2e damping`, which puts router-a on a reject redistribute policy for the phase: earlier phases leave it redistributing the prefix router-b flaps, and its own `Local` copy would otherwise outrank router-b's and keep the flaps out of its Loc-RIB.

### Collision resolution (RFC 4271 §6.8)

`collision::PeerSlot` (one per configured peer, shared between its active-connect task and the passive accept handler) implements real router-ID-based collision resolution — not a "first TCP connection wins" simplification. Both an active and a passive connection for the same peer are allowed to proceed through OPEN exchange; `PeerSlot::on_open` records each connection's BGP Identifier and, once both sides have one, resolves the winner:

- higher local BGP Identifier keeps the connection this system initiated (active); closes the accepted (passive) one; the reverse if the peer's ID is higher.
- a connection already `Established` always beats a later collision, regardless of ID comparison (RFC 4271 §6.8) — in practice, over real sockets, this is almost always which side actually decides the outcome, since one connection's OPEN/KEEPALIVE round trip typically completes well before the other side's OPEN is even processed. The pure ID-comparison path is exercised deterministically by `collision.rs`'s own unit tests (calling `PeerSlot::on_open` directly, no sockets), rather than by timing-dependent integration tests.
- a tie (duplicate/misconfigured router-id) keeps whichever connection registered first and logs a warning.

The loser is torn down with `NOTIFICATION(Cease, ConnectionCollisionResolution)` (RFC 4486 §7), signaled via a `tokio::sync::Notify` handle so its own `fsm::run` task sends the notification itself before closing — never a bare socket drop.

Because `BgpRib` is keyed by peer **address** rather than by connection, both connections for a peer share one set of RIB state, so `fsm::run` deregisters (`BgpRib::peer_disconnected`) on its way out **only if it registered** — i.e. only if it reached `Established` and ran `Action::ReportEstablished` (`fsm::run`'s own `registered` flag). A collision loser never registers, and tearing one down used to wipe the *winner's* `adj_rib_in` and, worse, its `peer_outbox` — leaving a session that stayed `Established` but could never advertise to that peer again, with no event that would ever restore it short of a session flap. Guarded by `handshake.rs`'s `collision_leaves_exactly_one_side_running`, which asserts the shared `BgpRib` still has the peer (`BgpRib::has_peer`) after the collision resolves.

### Administrative shutdown (RFC 4486 / RFC 9003)

`BgpPeerGroup.shutdown` and `BgpPeer.shutdown` (`Option<BgpShutdown { message }>`, ops `SetShutdown`/`ClearShutdown` on `BgpPeerGroupOp`/`BgpPeerOp`, CLI `set shutdown [<message>]` in a peer-group / `set peer <addr> shutdown [<message>]`) shut a whole group or one peer; the peer's own value wins over its group's (`reconcile::resync` resolves it into `ResolvedPeer.shutdown`). A shut peer keeps its `PeerSlot` (so it shows as `Idle (shutdown)` in `show bgp brief`) but gets no `active_connect_loop`, and `handle_inbound` drops its inbound connections.

Every session that `reconcile_peers` stops is told why first (`FsmCommand::Cease` on the slot's command channel, waited on for up to `CEASE_GRACE`, then aborted as before): subcode 2 Administrative Shutdown with the message as an RFC 9003 `len(1) || UTF-8` communication (≤255 bytes, cut on a char boundary) when the shutdown was just set, 3 Peer De-configured when the peer left the config, 6 Other Configuration Change for any other restart (`session::cease_reason`). A received NOTIFICATION is logged (`received notification peer=… code=… subcode=… shutdown_message=…`, the message decoded for Cease 2/4). Maximum Prefixes (1) and the reset verb are below. With graceful restart's N exchanged, subcodes 1–4 go out as an RFC 8538 Hard Reset (see "Graceful restart" below). Not implemented: Connection Rejected (5) toward a shut peer's inbound attempts. Verified by `nos-e2e shutdown`.

### Maximum prefixes (RFC 4486 §4)

A `BgpPeerGroup`'s `maximum_prefix` (`nos_proto::BgpMaximumPrefix`, one `Option<BgpPrefixLimit { limit, warning_only, restart_interval }>` per address family; CLI `set maximum-prefix ipv4|ipv6|l2vpn-evpn limit <n> [warning-only] [restart-interval <s>]`) caps the accepted prefixes per peer per family. A limit for a family the group doesn't negotiate is rejected at commit (`valid_peer_group_timers`). `limit 0` is valid and means explicitly uncapped (`check_max_prefix` skips it, the #501 commit warning accepts it); with nothing set there is no built-in cap.

- **Counting**: `BgpRib::accepted_prefixes(peer)` = `[v4, v6, evpn]`, post-import-policy (a rejected route is never stored; a damping-suppressed one is and counts), in **paths**: an RFC 7911 ADD-PATH peer's paths each count (a sender with no limit of its own can make us store any number). `path_counts` (`[v4, v6]` per peer) is kept in step by `put_path`/`take_path`, the only Adj-RIB-In mutators (`learn_prefix`, `remove_path`), so the check is O(1) per UPDATE; EVPN is `evpn_adj_rib_in[peer].len()`. `prefix_counters_match_a_recount_through_every_mutation` guards it.
- **Trip**: after each UPDATE `fsm::classify_inbound` calls `BgpRib::check_max_prefix`, which logs `maximum prefix limit exceeded peer=… family=… count=… limit=… warning_only=…` once per crossing and returns the first family over a hard limit. The FSM then sets the slot's hold (`PeerSlot::trip_max_prefix(restart_interval)`) and queues `FsmCommand::Cease { subcode: MaximumPrefixesReached, data }` (`AFI(2) SAFI(1) limit(4)`, `message::encode_max_prefix_data`) — once only, since a queued command outlives the session in the slot's channel. `FsmCommand::Cease` carries already-encoded `data`; `session::cease_reason` encodes the RFC 9003 text.
- **Hold**: while `PeerSlot::max_prefix_held()`, `active_connect_loop` doesn't dial and `handle_inbound` drops the connection (`rejecting inbound tcp connection from peer held by maximum prefix limit`). `restart_interval` 0 holds until released; `> 0` expires by itself. `show bgp brief` shows `Idle (max-prefix)` (`PeerSummary.max_prefix_held`) and, while Established, `prefixes v4 <n> …` (`accepted_prefixes`).
- **Release**: `BgpRequest::ClearPeer { peer }` (`clear bgp <instance> <peer>`, `POST /v1/bgp/{instance}/peer/{peer}/clear`; `user`/`restd`) → `SessionManager::clear_peer`, which clears the hold and, on an Established session, sends Cease/Administrative Reset (4); `PeerNotFound` if the peer isn't configured. A shut/no-shut or any limit change respawns the peer with a fresh `PeerSlot` (`diff_peers`), which drops the hold too. A released peer redials on its next connect-retry tick.


### Route refresh (RFC 2918)

`message::build_open` (via `fsm::run`) always advertises the Route Refresh capability (code 2, no payload) — unconditional, like every other capability this NOS sends, with no peer-group opt-out. Both directions are supported once `Established`:

- **Inbound**: a received `BgpMessage::RouteRefresh` is dispatched straight to `BgpRib::resend_all(peer, family)` (`rib/gr.rs`), which re-sends the current Loc-RIB to that peer for the requested address family only, reusing `build_advertisement`'s existing eligibility logic (split-horizon, negotiated-AF check, source-peer echo) — a family the peer never negotiated is silently a no-op.
- **Outbound**: `nos-cli`'s `clear bgp <instance> <peer> soft-in` reaches a peer's live `nos-bgpd` via `BgpRequest::SendRouteRefresh { peer }` (`server.rs`), which calls `SessionManager::send_command` to deliver an `FsmCommand::SendRouteRefresh` through `collision::PeerSlot`'s command channel. `fsm::run` sends a `RouteRefresh` message for every address family the session actually negotiated. On a peer-group with soft reconfiguration inbound `soft-in` re-evaluates locally instead (see below).


**Enhanced route refresh (RFC 7313)**: `Capability::EnhancedRouteRefresh` (code 70) is always advertised too; `RouteRefreshMessage.subtype` is the former reserved octet (0 request, 1 BoRR, 2 EoRR). When the peer echoes it (`RemoteInfo::enhanced_refresh`), an inbound request is answered `BoRR`, routes, `EoRR` (`BgpRib::resend_all(.., enhanced)` queues `OutboundUpdate::RefreshMarker`s in order with the routes; the FSM drains any MRAI-held announcements before sending `EoRR`). Inbound, `BoRR` marks every Adj-RIB-In prefix of that family stale (`BgpRib::stale`), any UPDATE mentioning a prefix clears its mark, and `EoRR` withdraws whatever is still stale. Markers from a peer that never negotiated it are ignored. RFC 7313 §4 stale timer: `fsm::run` keeps one deadline per family (`stale_until`, scoped to the session), armed by `BoRR` (a repeated one restarts it) and cancelled by `EoRR`; on expiry it purges exactly as `EoRR` would (`end_refresh_in`, logging `route refresh stale timer expired`). The duration is the peer-group's `route-refresh-stale-time` (`ROUTE_REFRESH_STALE_TIME_DEFAULT_SECS`, 360s; 0 disables it). Verified by `nos-e2e rest` and `route-refresh-stale`.
**Request throttle (#396)**: a peer-driven request resends the whole Loc-RIB, so `fsm::run` keeps a `refresh_limit::RefreshLimiter` per session (burst 2, one token per 10s, fixed) in `RefreshState`; a denied request skips `resend_all` and logs `route refresh rate-limited` at debug. Internal refreshes (RPKI, policy change) bypass it.

**Capability check (RFC 2918 §4)**: `RemoteInfo.route_refresh` records whether the peer's OPEN carried capability 2; `send_route_refresh` sends nothing (and logs `route refresh not sent: the peer did not advertise the route refresh capability`) without it — before #17 `soft-in` sent one regardless.

### Soft reconfiguration inbound (#859, #866)

- **Retention** (`rib/retain.rs`): `Retained { tables, counts, enabled, awaiting_eorr, evpn, flow, vpn }` per peer: the unicast tables reuse `put_path`/`take_path` (ADD-PATH ids included). `BgpRib::set_peer_soft_reconfig(peer, on)` is called by `fsm::report_established` from `PeerSlot::soft_reconfig()`; off calls `drop_peer`. `learn_prefix` stores a clone of the pre-policy candidate (after `validation_state` is set, before `apply_policy`); disabled costs one `HashSet` lookup per UPDATE. The other families (#866): `evpn` holds only the routes the policy rejected (a held EVPN route IS the raw route, the policy only accepts or rejects, so `learn_evpn` moves a route between `evpn_adj_rib_in` and `Retained::evpn`); `flow` and `vpn` hold the raw rule/path cloned before `import_flow`/`apply_policy`, since those rewrite the stored copy (re-running a policy on the stored copy would apply its rewrites twice). `drop_flow`/`drop_vpn`, the EVPN withdrawals and the stale purges remove the raw copy as well. `retained_count` sums every family; for EVPN it is held plus rejected. `remove_path` drops the copy, so every withdrawal, treat-as-withdraw and GR stale sweep does; `peer_disconnected` drops all (documented: no retention across a GR restart).
- **Re-evaluation** (`BgpRib::begin_reevaluation` / `reevaluate_chunk`): `begin_reevaluation` takes `ImportPolicies { unicast, evpn, flowspec }` and installs the EVPN and Flowspec ones in the rib under the same lock hold as the key snapshot (the unicast one is read from the slot per UPDATE). The pass snapshots the retained KEYS (unicast prefixes, EVPN held plus rejected keys, Flowspec and VPN keys); each chunk looks keys up in the current table (a path withdrawn since is skipped), refreshes `validation_state`, runs `apply_policy`, admits, replaces or removes in `adj_rib_in` (no damping, `received_at` kept) and re-decides only changed prefixes. Per family: EVPN `evpn_rejected` moves a route in or out of the table (a newly admitted Type-2 registers with `MacMobility` at that chunk, with the route as it is then, and gets `mac_mobility_recheck`; nothing is propagated, the fdb feed is derived from the table); Flowspec runs `import_flow` on the raw rule and then `track_flow` (validity and `select_flow`); VPN runs `apply_policy` with the RD and then `select_vpn` (the VRF import is derived from the table). A key withdrawn between chunks is skipped, one re-announced between chunks is already evaluated by the live path and is a no-op, so the end state equals a one-step run; the intermediate states are visible. `reevaluate_peer` is the one-shot form used by tests.
- **Driver** (`session/reeval.rs`): `SessionManager::start_reeval` spawns a task that locks the RIB per `REEVAL_CHUNK` (5000) and yields between chunks. `PeerSlot::reeval_begin(supersede, waiter)` implements the trigger rules: a policy change or enable bumps the generation (old waiters get `import policy changed during re-evaluation`, the old task exits at its next chunk), `soft-in` joins a running pass. A chunk ends with `check_max_prefix`; a trip aborts the pass (`maximum prefix exceeded during re-evaluation`) and Ceases like `fsm::classify_inbound`; a disconnect ends it with `session down`. The reason strings are constants in `collision.rs`.
- **Live policy**: `PeerSlot::import_policy()`/`evpn_import_policy()`/`flowspec_import_policy()` (replaceable, like `auth()`) are what `classify_inbound` and `apply_vrps` read; `ResolvedPeer.import_policy` is only the initial value.
- **`diff_peers`** returns a fourth list: peers differing only by the three import policies and `soft_reconfiguration_inbound` get a `Reapply`: `Policy` (flag on before and after, whatever the families), `Enable` (off to on), `Disable` (on to off, policy unchanged). Anything else restarts. `reconcile_peers` downgrades `Enable` on an Established peer without `PeerSlot::route_refresh_negotiated()` to a restart; on a down peer it only updates the slot. `Enable` calls `enable_soft_reconfig_live` and queues `FsmCommand::SendRouteRefresh`; `retention_eorr` (called on an inbound EoRR) logs completion.
- **`soft-in`**: `server.rs` asks `SessionManager::soft_in_local` first (flagged and Established); it answers `BgpEvent::SoftInReevaluated { families }` (one `FamilyReeval` per `ReevalFamily`: both unicast families always, the others when negotiated or non-empty), or `BgpEvent::Error` if the pass was superseded or aborted; otherwise the usual `RouteRefreshSent`/`PeerNotFound`.
- **Route refresh**: `send_route_refresh` also requests EVPN (AFI 25/SAFI 70) and Flowspec (AFI 1,2/SAFI 133) when negotiated. Inbound, `resend_loc_rib` maps SAFI 70 through `gr::family_of` and `BgpRib::resend_all(L2vpnEvpn)` calls `resend_evpn`, which replays `evpn_adj_rib_out`.
- Stale sweeps (RFC 7313 purge, GR) remove the raw copy only for keys that were held; a rejected route the peer silently stops sending after a refresh stays retained until its withdrawal or the session ends (`ponytail`, same as unicast).
- Verified by `nos-e2e policy` (two nos routers), `soft-reconfig-frr` (FRR with `dont-capability-negotiate`), and, for #866, the `evpn`, `vpn` and `flowspec` phases.

### BMP exporter (RFC 7854, #878)

- Code: `bmp.rs` (pure codec, then `Hub` and the station task). One `Hub` per instance lives in `SharedRib` (`bgp_rib.bmp()`); it is always there and does nothing without stations.
- Hooks: `fsm::run` calls `Hub::peer_up` when `ReportEstablished` ran (both OPENs re-encoded with `BgpCodec`; ports from the socket; the A flag is `!four_octet_as`) and `Hub::peer_down` at the single exit under the `registered` flag (`bmp_down_reason` maps `FsmOutcome`). `session::reconcile_peers` calls `peer_down(LocalFsm(0))` beside its `peer_disconnected` for aborted sessions. Peer Down only goes out for a peer in the registry, so a collision loser sends none.
- State: a std mutex over `registry` (Established peers' Peer Up data), the stations, and per station a bounded queue (1024 encoded frames, drop-oldest) with a `Notify`. Pushing never awaits the network. The queue only fills while the station is connected; the connect-time replay (registry snapshot plus queue clear, under both locks) covers anything older.
- Station task (`run_station`): dial with `tcp::connect` (VRF-scoped, 10 s bound), Initiation, replay, then drain; the same `select!` reads the station socket (EOF or error means reconnect). Writes time out after 30 s. A dropped frame sets `resync`: Termination (reason 2), reconnect, replay. Stop (removal, restart of a changed station, SIGINT): Termination (reason 0).
- Config: `reconcile::resync` calls `SessionManager::set_bmp_stations` every pass; `Hub::set_stations` restarts only stations whose `StationCfg` (address, VRF, instance, table, peer type) changed. Only a `Resolved` VRF dials.
- Logs (e2e anchors): `bmp station connected`, `bmp initiation sent`, `bmp peer up sent`, `bmp peer down sent` (with `reason`), `bmp station disconnected`, the overflow `warn!` with the dropped count.
- `ponytail:` the OPEN and NOTIFICATION PDUs are re-encoded: unknown capabilities and RFC 9003 shutdown text of a received NOTIFICATION are lost; carry the raw frames if a collector needs them. Reason 2 always uses event 0 ("none"), not an RFC 4271 section 8.1 event number.
- Route Monitoring (#864), `bmp/monitor.rs` (pure builders) and `bmp/dump.rs`:
  - Pre-policy stream: `fsm::classify_inbound` calls `Hub::route_pre(peer, &update)` before the RIB lock; every family goes through (`monitor::has_routes` skips an attribute-only UPDATE); one atomic check when no station wants it.
  - Post-policy stream, the RIB tap (`BgpRib.bmp`, set by `SharedRib::new`; gate `rib/bmp_tap.rs::tap`): `learn_prefix` (announce unless the stored route is identical, withdraw when a policy reject removed a path), `remove_path` (explicit and treat-as-withdraw withdrawals, GR and refresh sweeps) and `retain.rs::settle` (soft-reconfiguration re-evaluation). The other families tap beside their retention hooks (same sites #866 hooks): `learn_evpn`, `learn_flowspec`, VPN `learn_batch` (announce when the stored route changed, withdraw when the policy rejected a held one), `drop_flow`, `drop_vpn`, both EVPN withdraw sites, `purge_stale_evpn`, `set_peer_evpn_import_policy` and `reeval_evpn/flow/vpn`, via `Hub::{evpn,flow,vpn}_post`. Builders in `monitor.rs` (`evpn_to_update`, `flowspec_to_update`, `vpn_to_update` and the withdraws). Not tapped: `peer_disconnected`/GR retain sweeps (the peer is already down for the collector) and `set_peer_flowspec_policies`' in-place rewrite of held rules (`ponytail:` it runs at session restart; tap it if policies ever change live). `peer_disconnected` emits nothing: Peer Down flushes the peer. The frame is encoded under the RIB lock and the hub mutex (microseconds, only while monitored); `ponytail:` typed events encoded by the station task is the upgrade.
  - `Hub::emit` looks the peer up in the registry (`PeerUpInfo.add_path_afis` decides the path-id form) and pushes to every station whose `monitor` includes the stream. An UPDATE over 4096 bytes is split by `BgpCodec`; one BMP message per PDU.
  - Dump (`dump::run`, after the Peer Up replay): per peer and wanted stream (pre first), a key snapshot (`BmpKey`: prefix, EVPN route key, Flowspec key or VPN key, all families in one list), then `DUMP_CHUNK` (1000) keys per RIB lock hold, re-reading each key's current value (`BgpRib::bmp_updates`) (a withdrawn key yields nothing), writing the frames, then `drain` of the station queue. Events queued meanwhile are applied after the chunk, so the collector ends equal to the RIB. A queue overflow resyncs (reconnect, re-dump). `Hub::session_alive` (same `time` and `remote_port` in the registry) aborts a dump when the peer went down.
  - End-of-RIB per negotiated family but RT-Constraint after each dump (`BgpRib::bmp_families`, RFC 4724 form per family); the peer's own one is forwarded from the `EndOfRib` arm.
  - Logs (e2e anchors): `bmp rib dump sent peer=<ip> stream=pre-policy|post-policy routes=N`, `bmp end-of-rib sent peer=<ip> stream=..`, warn `bmp pre-policy dump skipped peer=<ip> reason="soft-reconfiguration inbound is off"`; per-route frames are `debug!` only.
  - `ponytail:` one UPDATE per path (grouping by attributes is the upgrade); a GR-stale route kept across a session restart is not re-dumped until it changes; the post-policy `LOCAL_PREF` of an eBGP route is the RIB's default.
  - GoBMP: EVPN is `msg_type` 14 (`mac`, `route_type`), VPN is 114 (`vpn_rd`, `prefix`), both with `action` add/del, `is_adj_rib_in_post_policy` and `"is_eor":true` End-of-RIB lines; a unicast prefix is `msg_type` 74 with `prefix`, `prefix_len`, `action` add/del and `is_adj_rib_in_post_policy`; End-of-RIB is a msg_type 74 line with `"is_eor":true`, `peer_ip` and the same flag.
- Adj-RIB-Out (#867, RFC 8671), `rib/bmp_out.rs` plus `fsm::write_update`:
  - Flag layout (RFC 8671 section 4, IANA): `V=0x80 L=0x40 A=0x20 O=0x10`, reserved bits 0 (`bmp::Flags`, unit-tested over all 16 combinations). Only Route Monitoring sets O; Statistics, Peer Up and Peer Down never do. `StationCfg.monitor_out` joins the restart comparison, which is the RFC 8671 section 7.2 session bounce.
  - Post-policy: `write_update` is the only place an UPDATE or End-of-RIB reaches the wire (the `send_outbound` and EoR drain, and the MRAI flush arm). When `Hub::out_enabled(true)` (one atomic) it clones the writer's own `BgpCodec`, encodes the same message again and hands the bytes to `Hub::route_out_wire`, so the frame equals the wire bytes (2-octet AS, ADD-PATH ids, extended length). `RefreshMarker` is not monitored.
  - Pre-policy: `eligibility` (split out of `build_advertisement`: family negotiated, no echo, iBGP split horizon / RFC 4456) is shared, so the candidate set cannot drift. `fan_out` calls `bmp_out::pre_step` per monitored peer (`Hub::is_up`) before the ADD-PATH `continue`; `BgpRib.bmp_pre_out` remembers what the collector was told so a withdrawal is sent only for an announced prefix. It is dropped in `peer_disconnected`; `bmp_pre_out_sync` (called after `Hub::peer_up`, since `initial_update` ran before the hub knew the peer) announces the initial candidates. EVPN, Flowspec and VPN have no pre-policy stream.
  - Dump (`dump::out_dump`): `BgpRib::bmp_out_snapshot` rebuilds the current post state in one RIB lock hold (`adj_rib_out` through `build_advertisement`, `add_path_sent` with its ids, the EVPN/Flowspec/VPN out maps) and resets `bmp_pre_out`. ponytail: one hold for the whole table, chunk it like the In dump if a full table stalls the RIB. Live frames queue behind it; a duplicate is idempotent for a collector.
  - Statistics 14-17 come from `BgpRib::bmp_out_counts`; 16 and 17 cover the unicast families only.
  - Admin Label: not emitted. The IANA registry has it as Peer Up TLV 4 (RFC 8671 section 6.3.1 is right, section 9.3's Initiation registry is wrong).
  - ADD-PATH path ids in BMP: RFC 7854 and RFC 8671 say nothing; a receiver infers them from the OPENs in the Peer Up.
  - GoBMP keys: see the `bmp` phase in `docs/e2e-phases.md`.
- `show bgp bmp` (#864): `BgpRequest::ShowBmp { instance }` → `BgpEvent::BmpStatus(Vec<BmpStationStatus>)` (`user`/`restd`; a daemon of another instance answers `BgpEvent::Error`). Each `Shared` holds a `Counters` mutex (state, dials, overflows, last error, `BmpFrameCounts`); `bmp::send`/`send_as` count every frame that was written, by its BMP type byte (Route Monitoring split on the L flag; End-of-RIB flagged by the caller, so it is not also counted as Route Monitoring). `Hub::station_status` reads them with the registry size. A new send site must go through `send`.
- Statistics Reports (#864), `bmp/stats.rs` (codec `stats_report`, `Stat::{Counter,Gauge,AfiSafi}`; Stats Count first, L flag 0) and `rib/stats.rs`:
  - `BgpRib.peer_stats` (`PeerStats`, wrapping `u32`) is reset in `peer_established` and removed first thing in `peer_disconnected`. Bump sites in `adj_in.rs`: `learn_prefix` (`None` arm = type 0, the `same` branch = 1), `learn_evpn`/`learn_flowspec`/VPN `learn_batch` reject paths (0), `apply_withdrawals` when `remove_path` finds nothing (2), the `handle_update` branches (3, 4/6 from the split `looped`, 5, and 11/12 for a bad next hop or stray confederation segment), and `treat_as_withdraw_prefixes` (set by `parse_update`, not on the wire) for the parse-level RFC 7606 cases.
  - The station `select!` has an `interval_at`; a tick calls `stats::send_reports`: one RIB lock hold, one `loc_totals` scan shared by all peers, then one frame per registry peer written directly. Gauge 9 lists the families in `bmp_families` (all negotiated but RT-Constraint). `ponytail:` the Loc-RIB scan is O(n) per tick, and type 10 covers unicast only; keep running counts if a full table makes it hurt.
  - Log anchor: `bmp statistics sent peer=<ip> stats=N`. GoBMP prints the report as a JSON line with the counters and gauges.
- Verified against GoBMP (digest in `consts.rs`): it dumps Peer Up/Down as `msg_type` 10 (`action` add/down, `bmp_reason`), takes the router address from the Peer Up local address, and never prints Initiation or Termination. Not verified against GoBMP: peer type 1 with a distinguisher.

| `External` | identifier (or `local-as`) | confed segments stripped, identifier prepended |

### RPKI origin validation (RFC 6811, RFC 8210)

`BgpInstance.rpki_caches` (`nos_proto::RpkiCache { address, port (323), preference (0), auth }`, keyed by address; `set bgp instance <i> rpki-cache <addr>` then `port`/`preference`/`md5-password`/`ao-key`) makes this `nos-bgpd` run an RTR client — inside the instance, no separate daemon (owner decision on #17).

- **`rpki/rtr.rs`**: the RFC 8210 PDU codec (`RtrCodec`, every PDU incl. Error Report; Router Key parsed and dropped) and the client (`rtr::run`). One cache at a time in preference order (ties: config order, RFC 8210 §10); a cache that fails or closes moves on to the next, a full round waits the retry interval. Reset Query on every connect (no serial resume across connections), Serial Query on Serial Notify and every refresh interval, Cache Reset → Reset Query, a changed session id → Reset Query; a v0-only cache (its first answer is version 0) gets a reconnect at version 0. Intervals come from End of Data (v0: RFC defaults), clamped to the RFC maxima but not the minima, so a lab can use a 10s expire. VRPs older than the expire interval are dropped (`rpki data expired ...`): everything is `not_found` again. `ponytail:` no preemption back to a preferred cache while a lesser one's session holds; duplicate announces / unknown withdraws are tolerated.
- **`rpki/vrp.rs`**: `VrpTable` (`HashMap<IpNet, BTreeSet<(max_len, asn)>>`, supernet walk per lookup) and RFC 6811 §2 `validate`; `origin_as` is the last ASN of a trailing `AS_SEQUENCE`, NONE for a trailing `AS_SET`, our AS (confed identifier if any) for an empty/confed-only path.
- **RIB**: `RibRoute.validation_state` is set in `handle_update` and `refilter_redistribute` before policy (RPL `this.bgp.validation_state`) and logged on `learned route ... validation_state=…`; `learn_prefix`'s damping comparison ignores it. `BgpRib::set_vrps` re-validates every Adj-RIB-In and redistributed route in place and re-decides changed prefixes (best path and export policies see it at once).
- **Re-evaluation**: `SessionManager::reconcile_rpki` (re)starts the client on a cache-list or VRF change (only with a resolved VRF; no caches empties the VRP set), and `apply_vrps` installs each published set, then 5s after the first change of a burst sends `FsmCommand::SendRouteRefresh` to every Established peer whose import policy `reads_validation_state()` (`rpki change: requesting route refresh`) — rejected routes aren't held, so only the peer can give them back. No session reset.
- **Auth** (#498): `Client::connect` maps `RpkiCache.auth` through `session::ResolvedAuth` into `tcp::connect` (key installed after `SO_BINDTODEVICE`, like a peer); the derived `PartialEq` on the cache list makes an auth change restart the client; secrets are never logged (`cache = %addr` only), `RpkiCacheStatus.authenticated` is a bool.
- **Query**: `BgpRequest::GetRpkiSummary` → `BgpEvent::RpkiSummary(Vec<RpkiCacheStatus>)` (`user`/`restd`), `show bgp rpki`, `GET /v1/bgp/rpki`.
- **Routes** (#500, paged in #722): `BgpRequest::GetRoutesPage { after, limit }` → `BgpEvent::RoutesPage { routes, next }` (`user`/`restd`), `show bgp routes`, `GET /v1/bgp/routes`. `BgpRib::route_keys` lists every `adj_rib_in` path (all ADD-PATH ones) plus `redistributed` (`peer: None`) as sorted `BgpRouteCursor`s; `route_at` builds one summary (`best` is equality with `loc_rib[prefix]`); `routes()` is the two combined. The old `GetRoutes` is answered with `BgpEvent::Error`. The EVPN and Flowspec keys are `page::Keyed { cursor, row }` (ordered by the text cursor alone; `row` is the table key, since the text cannot be inverted): `BgpRib::evpn_keys`/`evpn_at`, `flowspec_keys`/`flowspec_at`; the VPN ones are plain `VpnRouteCursor`s (`vpn_keys`/`vpn_at`, `rib/vpn_out.rs`).
  - **Paging mechanism** (`bgp/src/page.rs`, generic over the key so the EVPN/Flowspec/VPN queries reuse it): each connection holds one `Snapshot<K>` per query kind, a sorted `Vec` of keys (not rows) built on a first page (`after == None`). A later page `partition_point`s `after`, takes up to `limit` keys (clamped to `BGP_PAGE_MAX`, 0 = max) and reads just those rows from the live RIB, skipping keys that vanished; the RIB lock is held per page only. The page is cut early at `PAGE_BYTES` (half of `MAX_FRAME`, always at least one row) and `next` is the last consumed key.
  - The snapshot is dropped on the last page, on connection close, on a new first page, and rebuilt when older than 30s at the next request. It is a cache, not required for correctness: a page on a connection with no snapshot builds one. Paths added after the snapshot appear on the next walk. Cost: one O(n log n) key sort per walk, then O(log n + limit) per page; about 40 bytes per path held per live snapshot, freed at the last page or close (a pooled REST connection can hold one idle snapshot until reused).

- **RFC 8097 state community** (#162, `rpki/community.rs`): `BgpPeerGroup.announce_rpki_state` (iBGP only, refused on eBGP at commit) reaches the RIB as `BgpRib::set_peer_rpki_state`, called by `fsm::run` before `peer_established` (gated on the session being iBGP). `handle_update` always strips type `0x43`/subtype `0x00` from received extended communities; from an opted-in peer the first decodable one is kept as `RibRoute.received_ov`, and `ov_state` uses it instead of local validation while the VRP table is empty (`set_vrps` too, so it comes back after an expiry). `build_advertisement` removes any copy (e.g. an RPL `.add`) and, toward an opted-in iBGP peer, appends exactly one carrying `validation_state`. Note the wire order differs from `nos_rpl::ValidationState`'s discriminants (0 valid, 1 not-found, 2 invalid). Verified by `nos-e2e rpki` (router-c).

Not implemented: RTR over SSH/TLS or with TCP-MD5/AO, BGPsec, ASPA, EVPN validation. Verified by `bgp/tests/session.rs`'s `rpki_validation_follows_the_cache` (scripted cache, two localhost instances) and `nos-e2e rpki` (StayRTR).

### Extended Message (RFC 8654)

`fsm::run` always advertises `Capability::ExtendedMessage` (code 6, no payload). On `Established`, `BgpCodec::extended` is set on both reader and writer from whether the peer's OPEN carried it (`RemoteInfo::extended_message`, logged as `extended message negotiated`). The codec limit is then per-session: 4096 bytes by default, 65535 for UPDATE/NOTIFICATION/ROUTE-REFRESH once negotiated — OPEN and KEEPALIVE stay at 4096 always (§4). The encoder refuses to emit anything over the current limit. `BgpCodec::encode` splits an UPDATE that exceeds the limit (`message::split_update`: halves its largest NLRI/withdrawn/MP/EVPN list recursively, the second half carrying only that list plus the attributes when announcing); an UPDATE that can't be split further (e.g. one prefix with a huge `AS_PATH`) fails to encode. Verified by `nos-e2e established` (nos↔nos).

The command channel lives on `PeerSlot` (not per-connection) since it's already the single per-peer object shared across a peer's active/passive reconnects, alongside `status`. Its receiver is polled in `fsm::run`'s `select!` loop **only while that task's own state is `Established`** — RFC 4271 §6.8 collision resolution always happens before either side reaches `Established` (see above), so the collision loser never polls it: exactly one task ever contends for the shared receiver at a time, with no take/hand-off dance needed.

### Graceful restart (RFC 4724, RFC 8538, #12)

On by default: `BgpInstance.graceful_restart` (`nos_proto::BgpGracefulRestart { disabled, restart_time, stale_time, selection_deferral_time }`, a plain struct so each field sets/deletes alone; accessors `enabled_restart_time()`/`stale_time()` hold the 120/180/360 defaults). `reconcile::resync` puts `enabled_restart_time()` on `ResolvedPeer.graceful_restart` (it goes in the OPEN, so a change restarts sessions) and hands `stale_time` to `BgpRib::set_gr_stale_time`. Both the receiving (helper) side and the restarting side (below).

- **Wire** (`message.rs`): `Capability::GracefulRestart(GracefulRestartCap)` (code 64; the last of several wins, `graceful_restart(open)`); `BgpMessage::EndOfRib { afi, safi }`, decoded from the **raw** UPDATE bytes (`end_of_rib`) — an attribute-only UPDATE parses to an empty `UpdateMessage` and must not purge anything; `CeaseSubcode::HardReset` (9) + `encode_hard_reset`. Pure decisions live in `gr.rs` (`PeerGr`, a `Copy` bitset of the peer's families/F bits; `Disconnect`; `retains`; `sends_hard_reset`).
- **OPEN** (`fsm::run`): our capability with N always set, one tuple per configured family, F = `BgpRib::gr_forwarding(peer)` — 1 iff this process already had a session with the peer (its `BgpRib.gr` entry) or `nos-ribd` kept BGP routes across its start (`forwarding_preserved`); otherwise a fresh process's first `Full` push emptied `nos-ribd`. R = `BgpRib::deferring()`.
- **Established**: `set_peer_gr(peer, ours.and(theirs))` before `peer_established`; with both, `graceful restart negotiated peer=… restart_time=… notification=… restarting=… families=…` is logged and `BgpRib::initial_update` (called by `peer_established`, or for every peer when a deferral ends) queues one `OutboundUpdate::EndOfRib` per negotiated family right after the dump, toward a peer with a `BgpRib.gr` entry (MRAI drained first, like EoRR). Received End-of-RIB → `BgpRib::end_of_rib` (logs `received end-of-rib peer=… family=…`).
- **Session end** (`fsm::disconnect_kind` → `peer_disconnected(peer, Disconnect)`): `Transport` (TCP EOF/error, or replaced), `Graceful` (a NOTIFICATION sent/received, hold-timer expiry included, with N exchanged, not a Hard Reset), `Hard` (anything else). `reconcile_peers` passes `Graceful` for Cease 6 and `Hard` for 2/3; its second call after an abort is a no-op for a peer already retaining unless `Hard`.
- **Retention** (`retain_as_stale`): the peer's listed ∩ negotiated families stay in Adj-RIB-In (best paths, kernel, advertisement unchanged), marked in `stale`/`evpn_stale`; other families are withdrawn; without N, routes still stale from an earlier restart go first. `gr_deadline = now + restart_time` (0 purges at once). Logs `bgp: peer down, retaining routes as stale peer=… families=… restart_time=…`.
- **Return** (`gr_peer_returned`, start of `peer_established`): a family the new capability doesn't list, lists with F=0, or no capability at all → purged now (`flushing stale routes … reason=no-capability|forwarding-not-preserved`); the rest waits for End-of-RIB (`purged stale routes after end-of-rib … count=…`) under `gr_deadline = now + stale_time`. `gr_tick` (in the 5s damping tick, `ponytail:` granularity) purges expired deadlines (`graceful restart timer expired`). Re-announcing or withdrawing a route clears its mark in `handle_update` (EVPN too). An End-of-RIB also purges RFC 7313 BoRR marks; they never overlap in practice.
- **Cease with N** (`FsmCommand::Cease` arm): subcodes 1–4 go out as a Hard Reset wrapping the original (`sent cease notification … subcode=<original> hard_reset=true`), 6 stays graceful. A received Hard Reset is logged with the inner pair (`code=6 subcode=9 hard_reset_code=… hard_reset_subcode=… shutdown_message=…`).
- **SIGINT** (`SessionManager::shutdown`): a concurrent Cease/Administrative Shutdown (a Hard Reset with N) to every Established peer before aborting — the watchdog only stops `nos-bgpd` when the instance goes or the router stops, and `nos-ribd` deletes the VRF then, so peers must not keep forwarding to us. Crashes (SIGKILL, panic) still get the graceful path.
- **New connection replaces old** (`collision.rs`, §4.2): an `Established` record of a GR peer (`mark_established(role, gr_capable, replaced)`) is replaced by a connection *begun after* it came up — in the same role through `begin`, in the other role through `on_open` only when the new OPEN has the R bit (otherwise it is the far side of an ordinary collision race). The old session ends with no NOTIFICATION (`FsmOutcome::GrReplaced` → `Transport`); the new one waits (≤1s) for it to clear before registering.
- **Restarting side** (RFC 4724 §4.1): `reconcile::restart_check`, once per process on the first pass whose VRF is resolved and before any session or push starts (until then `resync` hands `reconcile` a `Pending` VRF, no routing table and no EVPN targets), asks the owning `nos-ribd` for `RibRequest::BgpRouteCount`. GR on and > 0 → `BgpRib::begin_deferral` (`gr::Deferral`; logs `graceful restart: forwarding state preserved, deferring route selection bgp_routes=<n>`) with every configured non-shut peer waiting. While deferring, the Loc-RIB fills normally but nothing leaves: `fan_out`, `propagate_add_path`, `resend_all`, `announce_evpn`/`withdraw_evpn` return early, `peer_established` registers the outbox without its dump, `push_snapshot` returns no table (so `rib_push_client` never sends its `Full`) and `evpn_feed_snapshot` no targets. A peer is done at its last End-of-RIB, at once if it sent no capability or set R (two restarting nos routers would otherwise wait for each other), dropped by `gr_tick` if still not `Established` our restart time after the start (a dead peer must not outlast a helper's stale timer), or on a `Hard` disconnect. The deferral also waits for `nos-ribd`'s first redistribution `Full` (`redistribute_seen`), so our End-of-RIB carries the redistributed routes. It ends (`route selection deferral ended reason=end-of-rib|timer`, `selection-deferral-time`) with `initial_update` for every peer; the next push is a `Full` replacing `nos-ribd`'s retained set (§4.1's stale forwarding state). `ponytail:` EVPN routes from `nos-fdbd`/IP-VRF tables aren't waited for; a deferral ended by a `Hard` disconnect is noticed by the next 5s tick.
- **BFD Down** (#286, `bfd_client.rs`, `SessionManager::bfd_down`): `FsmCommand::BfdDown { flush }` sends Cease/10 (`CeaseSubcode::BfdDown`), wrapped in a Hard Reset when `flush` and N is exchanged; `gr::sends_hard_reset` stays false for 10. Not `Established` with stale routes and `flush` → `BgpRib::gr_abort`; `bfd_action` is the decision table. `flush` is `BfdEvent::State.control_plane_independent` (C bit at both ends).
- `PeerSummary.graceful_restart`/`stale_prefixes`; `show bgp brief` renders `Idle (gr-stale <n>)` and `gr <s>s N F:ipv4,…`.
- Found while adding it: a connection already in flight when a peer tripped its maximum-prefix limit (the other side of a collision) used to bring the session back; `fsm::run` now answers its OPEN with Cease/Connection Rejected (5) while the hold is on.

Verified by `nos-e2e bgp-graceful-restart` (nos↔nos, both sides) and `bgp-gr-frr` (FRR), and `bgp/tests/session.rs`'s `graceful_restart_keeps_routes_across_a_graceful_reset` and `shutdown_sends_a_hard_reset_so_the_peer_keeps_nothing` (SIGINT's Cease, which a bare abort would turn into retention).

Performance: run `tools/bench-bgp.sh` around RIB changes; `--features dhat-heap` profiles memory. `set_igp` re-decides every Adj-RIB-In prefix, not only the Loc-RIB, and `next_hop_feasible` also gates the backup pick.

### RT-Constraint (RFC 4684, #875)

- Code: `rib/rtc.rs` (RIB), `message.rs` (`RtcNlri`, `decode_rtc_nlris`/`encode_rtc_nlris`, `SAFI_RTC`), `fsm.rs` (`negotiate_rtc`). Family `AddressFamily::RtConstraint` (AFI 1 / SAFI 132, IPv4 only), carried in the Multiprotocol capability and our graceful restart capability tuple.
- State: `rtc_adj_rib_in` (per peer), `rtc_local` (our import RTs, `rtc::membership(cfg, instance)`, pushed by `SessionManager::set_rtc_membership`, cleared while `!restart_decided`), `rtc_loc` (best per key), `rtc_adj_rib_out`. A key is `RtcNlri { origin_as, rt, bits }`; `bits` is 0 or 32..=96, trailing bits are zero.
- Selection and advertisement reuse `best_path` and `build_advertisement` (reflection, eBGP prepend) with an accept-all policy; the next hop is always our session address. `ponytail:` export/import policy does not apply to membership.
- Filter: `PeerOutbox.rtc_interest` is `None` when the family is not negotiated (nothing filtered), else `RtcInterest` built from the peer's whole `rtc_adj_rib_in`. `advertise_vpn` and `evpn_out::advertise` consult it (Type-4 never). `rtc_changed` re-syncs only routes whose RTs the changed keys cover (`resync_vpn`, `resync_evpn`). `ponytail:` O(table) scan per membership batch; index by RT if profiling asks.
- Initial update: membership dump, RTC End-of-RIB (sent whenever the family is negotiated, not duplicated by the graceful restart loop), then the VPN/EVPN dump.
- Unverified RFC points: RFC 4684 section 4 does not define what a partial prefix or a 32-bit prefix matches; the rule used is "first `bits - 32` bits of the RT, origin AS ignored". Interop: the `rtc` e2e phase runs against GoBGP 4.9.0; its VPN/EVPN filtering by a 96-bit membership and the default route behave as implemented, and GoBGP cannot announce a partial prefix (its CLI stores any length as /96), so partial matching is unit-tested only. GoBGP does not send its unicast routes to a peer once RT-Constraint is negotiated, so the restart-deferral wait for the RTC End-of-RIB is unit-tested only.
- Graceful restart (Q10 b): `peer_disconnected` keeps `rtc_adj_rib_in` when `RtConstraint` is among the retained families and `retain_as_stale` -> `mark_rtc_stale` fills `rtc_stale: HashMap<IpAddr, HashSet<RtcKey>>`; otherwise it drops the membership as before. Stale entries are live interest (`rtc_interest_for` reads the whole table), so the returning peer's VPN/EVPN dump is already filtered. `apply_withdrawals` clears a key's stale mark when the peer mentions it again. `purge_stale_rtc` removes the stale keys through `drop_rtcs` (re-select, re-advertise, `rtc_changed` -> `resync_vpn`/`resync_evpn`); it is the `RtConstraint` arm of `purge_stale`, `begin_refresh_in`/`end_refresh_in` (BoRR/EoRR) use `mark_rtc_stale`/`purge_stale_rtc`, and `has_stale`/`stale_count` count `rtc_stale`. `resend_all` re-sends `rtc_adj_rib_out` (`resend_rtc`). Our own restart: `Deferral` waits for the End-of-RIB of every negotiated family, RT-Constraint included, so no extra timer exists.

### BFD (RFC 5880, RFC 5882, #286)

- `bfd` lives outside `ResolvedPeer` (which `diff_peers` compares), so changing it restarts nothing. `reconcile::bfd_target` builds the wanted sessions (non-shut peers of a group with `bfd`; each `Want` carries `multihop` = `max-hops` above 1 or `!Config::is_connected(table, peer)`, and the peer-group's resolved `source-address` as `local`) and `SessionManager::set_bfd_targets` publishes them on a `watch`; `DiffScope::BfdProfiles` triggers the resync.
- `bfd_client.rs` (modelled on `nos-ribd`'s): one persistent connection to `ServiceRef::Bfd`, sessions keyed by (table, peer, local, multihop) with no interface (a path change deregisters the old key first), registered once the VRF is `Resolved` and the restart decision is made. Only an `Up` to `Down` transition acts (the first event after a `Register` is `Down`). Verified for both hop modes by `nos-e2e bgp-bfd` (`max-hops 2` makes the lab's direct peers multihop; the off-link branch of `is_connected` is unit-tested only).
- Log anchors: `bgp: bfd session down, closing peer=`, `sent cease notification … subcode=10 hard_reset=`, `bgp: bfd down, aborting graceful restart`.
- Verified by `nos-e2e bgp-bfd`.

### Confederations (RFC 5065)

`BgpInstance.confederation { identifier, peers }` (`set bgp instance <i> confederation identifier <asn>` / `... peer <asn>`): once `identifier` is set, `asn` is this router's **member AS** and each peer is one of `session::PeerKind` — `Internal` (`remote_as == asn`), `ConfedExternal` (`remote_as` in `peers`), `External` (anything else). `reconcile::resync` puts the identifier and the peer's membership on `ResolvedPeer`, so a change restarts the session; `LocalIdentity.confed_id` reaches the RIB (`BgpRib::set_confederation`), and `fsm::run` tells it which peers are confed-external (`set_peer_confed`) before `peer_established`.

| Toward | OPEN `My AS` | AS_PATH | NEXT_HOP / MED / LOCAL_PREF |
|---|---|---|---|
| `Internal` | member AS | unchanged | as iBGP |
| `ConfedExternal` | member AS | member AS prepended in an `AS_CONFED_SEQUENCE` | as iBGP: next hop unchanged by default, MED kept, LOCAL_PREF sent |
| `External` | identifier | confed segments stripped, identifier prepended (route-server clients: stripped, no prepend) | as eBGP |

EVPN origination (`evpn_out::advertise`) follows the same table. On receipt, confed segments from an `External` peer, or from anyone when no confederation is configured, are treat-as-withdraw (`withdraw_announced`, logged `treating bgp update as withdraw: as_path has confederation segments ...`); loop detection drops the identifier (or `asn`) in a plain segment and the member AS in a confed segment, with the existing `dropping bgp update: as_path already contains our own asn` line. Decision step 6 ranks external > confed-external > internal (`peer_rank`; step 8's oldest-route rule applies between two external routes only); a route learned from a confed peer is not iBGP-learned, so it reaches `Internal` peers without route reflection, and the RFC 4456 gate stays keyed on `Internal` only. RPL sees the flat path (`AsPath::flat`), confed ASNs included; an RPL prepend joins the leading `AS_SEQUENCE`.

`AS_PATH` is a structured `as_path::AsPath` (segment types kept, `Debug` of a pure sequence unchanged: `[a, b]`; mixed: `[(65101), 65003, {1, 2}]`), so step 3 counts an `AS_SET` as one hop and confed segments as none, and MED's neighbour AS skips confed segments. Not implemented: a `bestpath med confed` knob.

**Deterministic MED (#600).** `decision_cmp` is a total order only between paths of one neighbouring AS (MED is skipped across ASes), so a mixed set is never fed to `sort_by`/`max_by` directly: `decision::rank` (ADD-PATH / route-server ranking) and `best_index` (`best_path`, VPN import) take each neighbouring-AS group's best first, then compare those winners. The result no longer depends on input or `HashMap` order, and `rank(..)[0]` is always `best_path`. Verified by `nos-e2e confederation`.

### local-as (#166)

`BgpPeerGroup.local_as: Option<BgpLocalAs { asn, no_prepend, replace_as }>` (vendor IOS/Junos, no RFC; `set local-as asn <n> [no-prepend] [replace-as]`) — G below is the AS an `External` peer sees otherwise (identifier or `asn`).

- **OPEN**: `ResolvedPeer::open_as` returns `local_as.asn` for an `External` peer; the field is on `ResolvedPeer`, so a change restarts the session.
- **RIB**: `fsm::run` calls `BgpRib::set_peer_local_as` before `peer_established` (only for `External`); `PeerOutbox.local_as` is copied at registration.
- **Outbound**: `PeerOutbox::prepend_external` (shared by `build_advertisement` and `evpn_out::advertise`) prepends `[L, G]`, or `[L]` with `replace_as`; route-server clients still get no prepend (the combination is refused at commit anyway).
- **Inbound**: in `handle_update`, a path holding L from that peer is a loop (same log line as any loop); otherwise L is prepended before the import policy unless `no_prepend`, so policy and every other peer see `[L, peer…]`. L from other peers is not a loop (IOS behaviour, the migration case).
- **Validation** (`bgp_instance::valid_local_as`): External peer-groups only, not `asn`/identifier/`remote_as`, not with `route_server_client`. `no_prepend`/`replace_as` are independent (inbound vs outbound); IOS's `no-prepend replace-as` is both set.
- Not implemented: `dual-as`, per-peer local-as, Junos `private`/`alias`/`loops`. Verified by `nos-e2e local-as` against ExaBGP.

### BGP roles (RFC 9234, #14, #220)

`BgpPeerGroup.role: Option<BgpRole>` + `strict_mode: bool` (`set role provider|route-server|route-server-client|customer|peer`, `set strict-mode true`). Roles plus the OTC leak procedures (#221).

- **OPEN**: `Capability::Role(u8)` (code 9, length 1, other lengths dropped as unknown, `message::peer_role`); `ResolvedPeer.role/strict_mode` (so a change restarts the session) feed `NegotiationContext`, and `fsm::run` appends the capability when `role` is set.
- **Negotiation** (`fsm::negotiate_role`, in `handle_open`): peer role must be `BgpRole::counterpart` of ours, else NOTIFICATION OPEN Message Error subcode 11 (`OpenMessageSubcode::RoleMismatch`); no peer role is refused only under `strict_mode`, else no role negotiated (`RemoteInfo.role = None`). We announce no role: the peer's is ignored. Logs `bgp role negotiated peer= local= remote=` on accept; every NOTIFICATION we send is now logged (`sent notification peer= code= subcode=`).
- **RIB**: `BgpRib::set_peer_role` before `peer_established` stores the *configured* role (not the negotiated one: RFC 9234 §4.2 applies the procedures even when the peer sent no Role); the remote's role is its `counterpart()` (`PeerOutbox.remote_role` for egress).
- **OTC** (RFC 9234 §4.1/§5, #221): `PathAttributes.otc: Option<u32>` (type 35, optional transitive, length 4; another length is treat-as-withdraw), mirrored on `RibRoute`/`AdvertisedRoute`. Ingress in `handle_update` (unicast only, before import policy, after the loop checks): `otc_leak` (Customer/RS-Client with OTC, Peer with OTC != peer ASN) drops the update like an AS loop (`withdraw_announced`, log `route leak detected`); Provider/Peer/RS with no OTC gets `otc = peer ASN`. Egress in `build_advertisement` after the export policy: to Customer/Peer/RS-Client with no OTC set `open_as`; to Provider/Peer/RS with an OTC refuse (a plain refusal, frees an ADD-PATH slot; an RS-Client does receive OTC routes, per the RFC). The `learned route` log line has `otc=`. Policies read `this.bgp.otc` (the post-ingress value) and `this.bgp.{local,remote}_role` (#872): `BgpRib::policy_roles` gives our role from `role_peers` and the counterpart only if `set_peer_role_negotiated` was called (fsm, `negotiated_role.is_some()`); import passes them through `PolicyPeer` in `handle_update`/the soft-reconfiguration re-run, export through `PeerOutbox::policy_roles`; EVPN, VPN, Flowspec and redistributed runs leave them unset. No show/REST exposure yet.
- **Validation** (`bgp_instance::valid_role`): `strict_mode` needs `role`; no role on iBGP or confederation groups; a `route_server_client` group only takes `route-server`/`route-server-client`.
- Verified by `nos-e2e bgp-role` (two nos routers: pair, mismatch, strict, non-strict; then router-c and ExaBGP for OTC: no provider-to-provider leak, OTC reaching a customer, a customer's raw OTC dropped; then import policies on `this.bgp.{local_role,remote_role,otc}`, including a role-less peer's unset `remote_role`).

### Route reflection and route server

A `BgpPeerGroup` carries two mutually exclusive bools, `route_reflector_client` and `route_server_client` (enforced, along with the iBGP/eBGP requirement below, by `nos-config`'s commit-time validation — `bgp_instance::valid_route_reflection_and_server`), plus a `BgpInstance.cluster_id: Option<Ipv4Addr>` (`None` resolves to the instance's own `router_id`). Both features are additive on top of the existing single-best-path `BgpRib` — no new process, no new IPC socket.

**RFC 4456 route reflection** (`route_reflector_client`, requires an iBGP peer-group — `remote_as == asn`): `build_advertisement`'s iBGP split-horizon check (`rib/decision.rs`) gains an exception — a route learned via iBGP is still reflected to another iBGP peer when either the source or the destination is a configured client, rather than unconditionally withheld. Reflecting attaches/preserves `ORIGINATOR_ID` (the route's original advertising router, set once and never rewritten by a later reflector) and prepends this instance's own `cluster_id` to `CLUSTER_LIST`; `handle_update` drops (with a `warn!`, same style as the existing AS_PATH loop check) any inbound update whose `CLUSTER_LIST` already contains this instance's own cluster-id or whose `ORIGINATOR_ID` equals this instance's own router-id — RFC 4456 §5's reflection-loop prevention. Configuring zero `route_reflector_client` peer-groups is a complete no-op: the split-horizon exception's condition is never true, so behavior is byte-for-byte identical to before this feature existed.

**RFC 7947 route server** (`route_server_client`, requires an eBGP peer-group — `remote_as != asn`): `build_advertisement` never prepends this instance's own ASN to `AS_PATH` when advertising to such a peer, regardless of its eBGP-ness — full transparency, the defining route-server property — and its `next_hop: None` defaults to `Unchanged` like iBGP (RFC 7947 §2.2.1). A received MED is passed through to it unchanged (RFC 7947 §2.2), unlike toward any other eBGP peer. Full multi-path visibility for a route-server client (every other source's path for a prefix, not just the elected best path) needs RFC 7911 ADD-PATH; see "ADD-PATH" below. A route-server client's candidates in `BgpRib::propagate_add_path` (see "ADD-PATH" below) are every source's paths (`rs_candidates`: the redistributed route and every peer's paths) — not the Loc-RIB's, and not filtered by next-hop feasibility, aggregates or summary-only (RFC 7947 transparency) — and its unset `add_path_send_count` is unlimited. A route-server client without ADD-PATH send for a family gets the ordinary best path.

### ADD-PATH (RFC 7911, #13)

`BgpPeerGroup.add_path: Option<BgpAddPath { Receive, Send, Both }>` (CLI `set add-path receive|send|both`, `--add-path` on `nos-provision`); `BgpPeerGroup::effective_add_path` makes it `Both` for a route-server client when unset. `reconcile::resync` puts the effective mode on `ResolvedPeer.add_path`: it goes in the OPEN, so a change restarts the sessions (`diff_peers`). Unicast families only, never EVPN.

- **OPEN** (`fsm::run`): with a mode, one `Capability::AddPath` carrying a tuple per configured unicast family, Send/Receive = `BgpAddPath::send_receive` (1/2/3).
- **Negotiation** (`fsm::negotiate_add_path` → `[AddPathDir { rx, tx }; 2]` for ipv4/ipv6, RFC 7911 §5): rx iff we offered 1|3 and the peer 2|3; tx iff we offered 2|3 and the peer 1|3; SAFI 1 only; any tuple outside 1..=3 voids the whole capability (§4). Logged `add-path negotiated peer=… ipv4=… ipv6=…` (`none|receive|send|both`) when a mode is configured.
- **Codec**: the reader's `add_path_afis` is the rx set, the writer's the tx set — they differ. Encoding writes an id whenever the update carries one, so the RIB must never hand a tx session an id-less NLRI.
- **Adj-RIB-In**: `HashMap<IpAddr, PeerTable>`, `PeerTable = HashMap<IpNet, Paths>`, `Paths = SmallVec<[(u32, RibRoute); 1]>` (path id 0 without ADD-PATH; inline, so no extra allocation per prefix). `handle_update` reads the ids index-aligned from `*_path_ids` (`withdrawn_paths`/`announced_paths`), upserts/removes by `(prefix, id)` (`put_path`/`take_path`/`remove_path`); an unknown id is a no-op. Logs: `learned route for <p> into adj-rib-in peer=… path_id=… … communities=…`, and (debug) `withdrew path for <p> from adj-rib-in peer=… path_id=…`. RFC 7313/GR `stale` marks are per `(prefix, id)`; treat-as-withdraw removes only the announced ids.
- **Decision**: every path of every peer is a candidate, `Candidate = (RibRoute, Option<(IpAddr, u32)>)`; step 10 compares `(peer address, path id)`, so `decision_cmp` is a total order and two paths of one peer can form multipath (`multipath_next_hops` already dedups by next hop).
- **Send** (`PeerOutbox.add_path_tx`): every NLRI toward a tx family carries an id, so `fan_out`/`initial_update`/`resend_all`'s plain single-best path skips those families (`adj_rib_out` never holds them) and `BgpRib::propagate_add_path` sends them instead. It runs first in `recompute_and_propagate` (before the "best unchanged" return: a non-best path can change the top N), from `initial_update`/`resend_all` for one peer (`only`, re-sending unchanged paths too), and next to `fan_out` in `aggregate.rs`'s re-fans.
  - **Candidates**: an ordinary peer gets `candidates(prefix)` (exactly what `best_path` decides over: redistributed, aggregate, non-damped feasible peer paths; none when summary-only suppresses the prefix); a route-server client `rs_candidates` (see "RFC 7947 route server"). Both ranked once per prefix with `decision_cmp` (`ranked`), shared by every peer. `Candidate = (RibRoute, path id)`; a path's identity is `PathKey = (origin, id)`, the redistributed route `(Local, 0)` and the aggregate `(Local, 1)`.
  - **Selection** (`send_add_paths`): walk the ranking through `build_advertisement` and keep the first `PeerOutbox.add_path_send_count` it accepts (`None`: all) — a refused path (split horizon, RR rules, export policy, the peer's own path) doesn't use a slot, and rank 1 is the Loc-RIB best path (RFC 7911 §5).
  - **Ids**, diffed against `add_path_sent[(peer, prefix)]` (`PathKey → (id, route)`): a path still selected keeps its id, re-announced only if its route changed (or for `only`); one that left frees its id; an entering one takes the lowest freed id (RFC 7911 §3 implicit replace, one UPDATE, the receiver never holds N−1) else a fresh `add_path_next_id` — monotonic per (peer, prefix), cleared only with the session (`ponytail:` never recycled once withdrawn); ids still free are withdrawn. A path whose new attributes are refused thus loses its id too.
  - **Count**: `BgpPeerGroup.add_path_send_count` (2..=64, needs effective add-path send|both — `valid_route_reflection_and_server`); `effective_add_path_send_count` defaults it to 2, unlimited for a route-server client. `ResolvedPeer.add_path_send_count` → `BgpRib::set_peer_add_path_send_count` before `peer_established`. Not in the OPEN, but a change restarts the sessions like any field (`ponytail:` re-run the fan-out for that peer instead). Independent of `maximum_paths` (install only).
  - Cost: one sort of the prefix's candidates plus up to N + refused `build_advertisement` calls per ADD-PATH peer, per touched prefix; nothing when no peer sends ADD-PATH for the family (the peer filter runs first).
- `ponytail:` damping stays keyed by (peer, prefix): a flap of any one path penalises the prefix from that peer.


### Communities

`message.rs` decodes/encodes all three community attribute types — RFC 1997 `COMMUNITY`, RFC 4360 `EXTENDED_COMMUNITIES`, RFC 8092 `LARGE_COMMUNITY` — each stored on `PathAttributes`/`RibRoute`/`AdvertisedRoute` as a plain `Vec` (`u32` for standard — `AA:NN` packed `(AA << 16) | NN`; `u64` for extended — the 8 raw wire bytes; `(u32, u32, u32)` for large), following `cluster_list`'s existing empty-`Vec`-means-absent convention rather than an `Option` wrapper. All three are optional *transitive* attributes (`ATTR_FLAG_OPTIONAL_TRANSITIVE`, distinct from `cluster_list`/`originator_id`'s optional non-transitive flag) and — unlike `local_pref`/`med`/`AS_PATH`-prepend — `build_advertisement` propagates them to every eligible peer unconditionally, with no eBGP/iBGP split: RFC 1997/4360/8092 default behavior is pass-through, and any peer-specific stripping is left entirely to that peer-group's export policy (see `docs/architecture/rpl.md`).

Well-known standard community values (`NO_EXPORT`/`NO_ADVERTISE`/`NO_EXPORT_SUBCONFED`) are enforced (#873): `decision::well_known_blocks`, called in `build_advertisement` on the stored post-import route before the export policy runs, so every export path (unicast, ADD-PATH, GR/route-refresh replay, VPN, Flowspec) honours it and only an import policy can lift it. Only `RouteOrigin::Peer` routes are filtered; the peer class (own AS, other member AS, outside) comes from `PeerOutbox::is_ibgp`/`is_confed`. The RFC 4360 transitive bit *is* enforced (#162): `build_advertisement` drops every extended community whose type has bit `0x40` set toward an eBGP peer (not confederation-external, kept like MED), after the export policy, so one an RPL `.add(..)` attached can't leak either.

**Blackhole (RFC 7999, #861)** (`65535:666`, `message::COMMUNITY_BLACKHOLE`):
- `BgpPeerGroup.blackhole` is resolved by `reconcile::resolve_peers` into `ResolvedPeer.blackhole` (the prefix-list entries), so an edit restarts the session, and handed to `BgpRib::set_peer_blackhole` on establishment (eBGP only).
- `rib::blackhole_applies` (community plus prefix-list match, same `range` rules as RPL) is used twice: `learn_prefix` adds `NO_EXPORT` after the import policy accepted the route, and `push_snapshot` emits `(vec![], None, true)`. There is no per-route flag: a blackhole is derived from the stored route and the peer's list, so a policy stripping the community makes it ordinary.
- `rib_push_client` sends `BgpRoute { discard: true, next_hops: [] }`; `nos-ribd`'s `bgp_entry` builds an empty-next-hop `RibEntry` (the Linux driver installs it as `RTN_BLACKHOLE`, protocol static, like an OSPF ABR discard) and `to_prefix_routes` reports `RouteEntry.blackhole` for a BGP-sourced discard.

**Graceful shutdown (RFC 8326, #860)** (`65535:0`, `message::COMMUNITY_GRACEFUL_SHUTDOWN`):
- Two `BgpPeerGroup` bools, `graceful_shutdown` (sender, eBGP groups only) and `graceful_shutdown_receive_disabled`. They are not in `ResolvedPeer`: any difference there respawns the session (`diff_peers`), which would defeat a drain. `reconcile::gs_knobs` builds a per-peer map, `SessionManager::set_graceful_shutdown` hands it to `BgpRib::set_graceful_shutdown` (called before `reconcile`, like `set_maximum_paths`).
- Receive, in `learn_announced` where `base_route` is built, so before import policy (policy can override) and shared by unicast and VPN (`learn_vpn` clones it): on an eBGP session (not iBGP, not confed-external) a path with the community gets `local_pref = 0`, unless `receive_off`. With the sender knob on, every path from that peer is tagged and demoted too (RFC 8326 section 4.2). The learned-route log has `local_pref=`.
- Send: `PeerOutbox.gs_send`. `build_advertisement` adds the community to unicast and VPN exports toward eBGP before the export policy (a policy may strip it); Flowspec is untagged. EVPN bypasses export policy, so `evpn_out::advertise` tags unconditionally (`AdvertisedEvpn.communities`).
- Live change: a sender change re-advertises inside `set_graceful_shutdown` (`resend_all` for unicast, `announce_vpn_to` for VPN since `resend_vpn` replays what was last sent, `announce_evpn_to` for EVPN). Any change then asks established peers for a Route Refresh (rewritten routes are not retained); a peer without the capability keeps old LOCAL_PREFs until it re-announces.
- EVPN receive (#874): `learn_evpn` takes the peer's knobs (`None` for iBGP/confed) and applies the same `GsKnobs::apply` as `learn_announced`, so the rule lives once. `EvpnRoute` gains `communities` and `local_pref`; the `evpn route learned` log ends with `local_pref=<n> communities=[graceful-shutdown]` (names from `nos_proto::bgp::{community_name, fmt_communities}`, shared with `show bgp evpn`; unicast logs still show packed numbers).
- Preference is applied at push time in `evpn_push_snapshot`, not as a best path. Order: MAC mobility (`holds`), then highest LOCAL_PREF, then lowest VTEP for a Type-2 `(VNI, MAC)`; a Type-5 below the group's maximum for `(prefix, label)` is skipped. Types 1/3/4 are untouched, and the policy cannot override (accept/reject only). Different-ESI copies of one MAC are decided by mobility alone. A knob change's Route Refresh re-delivers the routes and the push re-runs.

### EVPN (RFC 7432): receive side, plus origination for `nos-fdbd`

A peer-group's `address-family l2vpn-evpn` (`AddressFamily::L2vpnEvpn`, appended last in the enum — postcard indexes variants by position) adds MP capability AFI 25 / SAFI 70 to that session's OPEN (`fsm::build_mp_capabilities`; no RFC 8950 Extended Next Hop tuple — an EVPN next-hop's family is independent of its NLRI). `fsm::negotiate_address_families` reports it as a fourth bool and `Action::ReportEstablished` inserts `L2vpnEvpn` into the peer's `negotiated_afs`; ADD-PATH tuples and ROUTE_REFRESH stay unicast-only.

`evpn.rs` is the pure codec: `EvpnNlri` (`EthernetAd`/`MacIp`/`InclusiveMulticast`/`EthernetSegment`/`IpPrefix` for route types 1–5, RFC 9136 for Type 5, plus `Unknown{route_type, body}` kept verbatim) with `decode_nlris`/`encode_nlri`; it doubles as the RIB key (`Eq + Hash`). `message::MpReachNlri`/`MpUnreachNlri` carry `evpn: Vec<EvpnNlri>` next to the prefix list (which is empty for such a batch); `decode_mp_reach`/`decode_mp_unreach` branch on `(afi, safi) == (25, 70)` before `decode_prefixes`, which still rejects any other AFI. Route Targets, the Encapsulation community and MAC mobility are ordinary extended communities and were already carried.

`BgpRib` keeps `evpn_adj_rib_in: HashMap<peer, HashMap<EvpnNlri, EvpnRoute{nlri, next_hop, extended_communities}>>`, separate from the `IpNet`-keyed tables so no unicast path changed. It is keyed by `EvpnNlri::route_key` (#188): the NLRI with RFC 7432 §7.1/§7.2 and RFC 9136 §3.1's *attribute* fields zeroed (Type-1 label, Type-2 ESI and labels, Type-5 ESI/gateway/label), so a re-announce changing them is an implicit replace and a withdrawal with other labels still removes the route; the value keeps the received NLRI (`EvpnRoute.nlri`), which is what `evpn_push_snapshot` and `show bgp evpn` read. `evpn_stale` holds route keys too. `handle_update` applies it *after* the same loop-prevention checks as unicast (own ASN in `AS_PATH`, own cluster-id, own originator-id); withdrawals are applied first and `peer_disconnected` clears the peer's table. It logs `evpn route learned peer=… route_type=… route=… next_hop=…` / `evpn route withdrawn …` (the `evpn` e2e phase anchors on these). **Explicit ceilings** (`ponytail:` in `rib.rs`): no Loc-RIB/best-path (other than RFC 7432 §15 MAC mobility, below), no reflection of received routes, Route-Target import filtering happens downstream in `nos-fdbd` (not here), and import policy is **not** applied — RPL's `Input` is prefix-shaped, so an EVPN route can't be filtered by it yet.

### Flowspec NLRI (RFC 8955 / RFC 8956)

- `flowspec.rs` is the pure codec for SAFI 133 (and SAFI 134). SAFI 133 is wired into negotiation, the Adj-RIB-In, selection and propagation (below); SAFI 134 is not used yet (the constants `SAFI_FLOWSPEC`/`SAFI_FLOWSPEC_VPN` sit next to `SAFI_EVPN` in `message.rs`).
- `AddressFamily::Ipv4Flowspec`/`Ipv6Flowspec` are appended after `L2vpnEvpn`; `fsm::negotiate_flowspec` returns `[ipv4, ipv6]` (both sides advertised the tuple), `RemoteInfo`/`Action::ReportEstablished` carry it as `negotiated_flowspec`. `fsm::is_unicast` keeps Extended Next Hop (RFC 8950) and ADD-PATH off these families, and `negotiate_address_families` ignores them (its unicast `configured` test checks SAFI 1).
- `MpReachNlri.flowspec`/`MpUnreachNlri.flowspec` hold the rules (the prefix list is empty); `decode_mp_reach` accepts next-hop length 0 for SAFI 133 only (stored as the AFI's unspecified address) and `encode_mp_reach` always writes 0. `split_update` splits `flowspec` lists like EVPN ones. A bad NLRI is `WireError::MalformedUpdate`, so the session resets (RFC 7606 section 3(g)); the withdraw rule of RFC 8955 section 10 cannot apply when the NLRI cannot be read.
- `BgpRib.flowspec_adj_rib_in: HashMap<peer, HashMap<(AddressFamily, FlowSpec), FlowspecRoute{family, nlri, attributes, router_id, received_at, ..}>>` (the whole `PathAttributes`, after the import policy); `flowspec_stale` is the graceful-restart twin. The key is the family plus the NLRI, since the same bytes mean different rules per AFI. `adj_in::learn_flowspec` logs `flowspec route learned peer=… family=… route=…` only when a rule is new or changed; withdrawals, `peer_disconnected` and the stale purge log `flowspec route withdrawn …` (the `flowspec` e2e phase anchors on these).
- Validation (#559): `rib/flowspec_validate.rs`. `validate(&Flow, BgpFlowspecValidation, best, more_specific)` is pure (RFC 9117 by default; `rfc8955_strict` restores RFC 8955: `Flow.local_domain` is rule b.2, `Unicast.leftmost_as` feeds the eBGP leftmost-AS check, and confederation-member peers count as iBGP) (the unicast RIB is two closures), returning `FlowValidity{Valid, Invalid(InvalidReason)}`; `FlowspecRoute.validity` holds it (`None` only until the first validation) and `is_usable()` is `Valid`. `learn_announced` collects the learned keys and runs `track_flow` after the Adj-RIB-In loop (it needs `&mut self`).
- Incremental revalidation: `BgpRib.flow_ix` (`FlowIndexes`) is derived, never authoritative, and off until the first rule is learned (`enable_flow_indexes` then builds it from the Adj-RIB-In). `flows` maps a rule's destination `(is_v6, address, length)` to the `(peer, key)` using it; `unicast` maps each received unicast prefix to its neighbouring ASes (rule (c), refreshed from every peer's Adj-RIB-In). `recompute_and_propagate` is now `recompute_prefix` plus `revalidate_around(prefix)`, so every unicast change reaches it, including the `unchanged` case and non-best paths: it looks up the ancestors of the prefix (at most 129 exact lookups) and the descendants (a `BTreeMap` range) and revalidates only those rules. Entries of withdrawn rules are dropped when next met and by `compact_flows` (when index entries exceed twice the live rules plus 64). `FlowIndexes.visits` counts revalidations for the tests.
- Neighbouring AS of a route: the leftmost AS of its path, else the peer's AS, else ours (`neighbour_as_of`). The knob is `ResolvedPeer.flowspec_validation` -> `BgpRib::set_peer_flowspec_validation`.
- Actions: `flowspec_action.rs` (pure) decodes the extended communities into `FlowAction`; `decode_actions` also runs in `parse_update` (a Flowspec announcement with an undecodable action is treat-as-withdraw, RFC 8955 section 10), `describe(ext, ipv6)` feeds `FlowspecRouteSummary.actions`, the IPv6 redirects last (`decode_redirect_ipv6` over `PathAttributes::ipv6_extended_communities`).
- Attribute 25 (RFC 5701): `message.rs` parses it into `PathAttributes::ipv6_extended_communities: Vec<[u8; 20]>` (a length not a multiple of 20 is treat-as-withdraw) and encodes it back. `ponytail:` only Flowspec re-advertises it; a unicast route loses it on re-advertisement.
- Selection and propagation (#560): `rib/flowspec_out.rs`. `flow_rib_route` adapts a `FlowspecRoute` into a `RibRoute` (no next hop, `validation_state` not-found) so `select_flow` reuses `best_path` with an empty IGP map; `flowspec_loc: HashMap<key, (peer, FlowspecRoute)>` holds the winner. `select_flow(k)` runs per rule from `track_flow` (learn), `revalidate_flow` (a validity change) and `drop_flow` (every removal: withdraw, treat-as-withdraw, policy reject, stale purge, peer down), so nothing ever rescans the table.
- Advertisement: `sync_flow_to(peer, k, force)` diffs against `flowspec_adj_rib_out` and calls `build_advertisement(.., Some((family, policy)))`, which skips the RFC 9234 OTC and RFC 8097 steps for Flowspec and runs the Flowspec export policy (`flowspec_export`, `ACCEPT_ALL` when unset). `OutboundUpdate::AnnounceFlowspec(AdvertisedFlowspec)`/`WithdrawFlowspec(family, nlri)`; `fsm::outbound_update_to_message` encodes them as SAFI 133 with an empty next hop. Logs: `flowspec route advertised peer=… family=… route=…`, `flowspec route advertisement withdrawn …`.
- Import: `adj_in::learn_flowspec` runs `flowspec_out::import_flow` (the `flowspec_import` map, D5 input from `flow_prefix`) before storing; a reject removes the rule and logs `flowspec route rejected by import policy`. Rewrites are written back into the attributes, except an AS-path prepend. `set_peer_flowspec_policies` (via `set_peer_flowspec(&ResolvedPeer)`, before `peer_established`) re-runs the stored rules, for those kept across a graceful restart.
- Graceful restart and the rest: `select_flow` sends nothing while `deferring()`; `initial_update` calls `announce_flowspec_to`. A route refresh for SAFI 133 goes to `resend_flowspec`, which re-sends `flowspec_adj_rib_out`. The outbox backlog keeps lost rules in `Backlog::flows` and `drain_backlog` re-syncs them with `force` (`ponytail:` all at once, not batched).
- Ceilings: no local origination (#16 D7). The max-prefix count adds `accepted_flowspec(peer)` (`[ipv4, ipv6]`) to `accepted_prefixes`'s three; `PeerSummary.accepted_prefixes` still shows only the first three.
- `BgpRequest::GetFlowspecRoutesPage { after: Option<FlowspecRouteCursor>, limit }` → `BgpEvent::FlowspecRoutesPage { routes: Vec<FlowspecRouteSummary{peer, nlri, extended_communities, validity, actions, dataplane}>, next }` (`user`/`restd` only; paged in #723 over the same per-connection key snapshot as `GetRoutesPage`, cursor = `(peer, family text, rule text)`, the old `GetFlowspecRoutes` answers `BgpEvent::Error`) backs `show bgp flowspec` and `GET /v1/bgp/flowspec`. The NLRI is the `Display` text and the actions come from `flowspec::format_action`. `dataplane` (selected copy only, `BgpRib::flowspec_selected`) joins `nos-acld`'s `ShowFlowspec` rows on (instance, flow text), asked once per page request and joined for that page's rows only (`acl_push_client::show`/`dataplane`; `Role::Bgpd` is allowed on `ShowFlowspec`, #562 D-B).
- Dataplane push (#562): `acl_push_client.rs`, one task per process, shaped like `fdb_push_client` (`push_changed`, 50 ms hold-down, 10 s tick, 1 s retry, EOF watch). Each push is a whole `FlowspecSet { instance, devices: [], rules }` (`AclRequest::PushFlowspec`, awaited `AclEvent::Ack`), skipped while equal to the last acknowledged one and resent on reconnect. `BgpRib::flowspec_push_snapshot` gives the `flowspec_loc` rules, IPv4 then IPv6, each in `cmp_precedence` order, converted by `flow_rule` (components one to one; actions in attribute order minus `ignored` rates; redirects as `FlowRuleAction::Unsupported`); `None` while `deferring()`, so `nos-acld` keeps what it holds. Shutdown pushes an empty set. `nos-acld` picks the devices itself (the `flowspec` devices of the instance's table, #562 D-A/D-C). Log: `connected to nos-acld, pushing flowspec rules instance= routes=` (info), `flowspec push instance= routes=` (debug).
- `FlowSpec::decode(afi, data)` reads one length-prefixed NLRI (1 octet below 240, else `0xfnnn`) and returns it with the octets consumed; `encode(&mut Vec<u8>)` writes it back. `FlowSpecVpn { rd, flow }` is the SAFI 134 form (the length covers the 8-octet RD).
- `Component` has one variant per type: 1-12 for IPv4, 1-13 for IPv6 (`FlowLabel` is IPv6 only). Numeric operators are `NumOp { and, lt, gt, eq, value }`, bitmask ones `BitOp { and, not, m, value }`.
- IPv6 prefixes (types 1/2) are `Prefix { net, offset }`: the pattern sits at bits `offset..len` of `net`, everything else is zero. Valid only if `offset < len <= 128`, or both 0.
- Malformed (all `WireError::MalformedUpdate`/`Truncated`): zero length, overrun, component types not strictly increasing, an unknown type (13 on IPv4 too), a bad IPv6 length/offset, the DF bit in an IPv6 fragment mask. The caller treats this as withdraw (RFC 8955 section 10).
- Canonical form: the operand size is the smallest of 1/2/4/8 octets, the first operator's AND bit is read and written as 0, and padding or out-of-range pattern bits are zeroed. So decode then encode is stable and the value is a valid RIB key (`Eq + Hash`).
- `cmp_precedence(a, b)` is the section 5.1 order: `Less` means `a` matches first. Lowest type first, more specific prefix first, else lowest address, memcmp of the encoded operators for other types (the longer wins a common-prefix tie), the rule with fewer components loses, IPv6 lowest offset first. A test checks it against a literal transcription of the Appendix A code.
- `Display` is the text form for `show`: `dest 192.0.2.0/24 proto =6 port =25`, `port >=137 && <=139 || =8080`, `tcp-flags match 0x12`, IPv6 `dest 2001:db8::/32 offset 0`.
- Unsupported match types are a downstream concern: the codec decodes everything the RFCs define.

#### MAC mobility (RFC 7432 §7.7/§15)

A Type-2 route's `(VNI, MAC)` identity can be advertised by more than one PE — a real host move, or two VTEPs disagreeing — so `mac_mobility.rs`'s `MacMobility` (pure state, modeled on `damping::Damping`) decides which advertisement, local or received, is authoritative and detects a genuine duplicate. `learn_evpn` decodes each received Type-2's MAC Mobility extended community (`nos_proto::evpn_id::parse_mac_mobility`, `(0, false)` when absent) and registers it as a candidate (`MacMobility::candidate`); §15.1's rule is higher sequence wins, a tie breaks on the lower owner IP (the route's `next_hop`/VTEP, the same identity `fdb/`'s ESI/DF-election code already uses as "which PE" — not a separate BGP-identifier field). `apply_evpn_local` (`evpn_out.rs`'s `with_local_mobility`) attaches a mobility community to every Type-2 `nos-fdbd` pushes: `owner`'s own unchanged sequence if it already holds `(VNI, MAC)` (an ordinary re-push isn't a re-learn), or one past whatever the current winner holds otherwise — so a genuine local re-learn always outranks a stale remote copy (§7.7). `evpn_push_snapshot` — the feed to `nos-fdbd` — only includes a Type-2 route that is its `(VNI, MAC)`'s current winner, which is what actually fixes the old "two peers' copies race into the kernel FDB by iteration order" bug (`fdb/`'s `EvpnKey` keeps different RDs apart, so they'd otherwise never even collide there); `mac_mobility_recheck`, called right after registering a remote candidate, withdraws a stale local advertisement that a remote route has just outranked (§15's "a PE that learns a higher-sequence remote route for a MAC it holds locally must withdraw its own claim") — the MAC stays known to `nos-fdbd`'s own local-MAC bookkeeping, so a later real re-learn reclaims it. A sticky (RFC 7432 §7.7 static) incumbent is never displaced by an ordinary candidate, and any conflicting candidate against one is an immediate duplicate — nos never originates a sticky MAC itself (no per-MAC administrative config surface exists), but honors a received one. §15.2 duplicate-MAC detection: more than `MOVE_LIMIT` (5) real ownership changes within `MOVE_WINDOW` (180s) freezes the `(VNI, MAC)` — it keeps reporting its last winner regardless of further candidates, logged `duplicate mac detected, freezing` — until a full window passes with no further contention (`mac_mobility_tick`, a 5s task alongside `damping_tick`).

**Same ESI is not a move** (#172): a MAC is held by its owner *or* by the owner's non-zero ESI. Every PE on one all-active segment advertises the CE's MAC with that ESI (RFC 7432 §8.4/§14.1.1) — §15.1 only speaks of a MAC behind a *different* ESI — so `MacMobility::candidate` holds a same-ESI candidate unconditionally (no move, no sticky conflict, sequence shared via `max`), `local_seq` doesn't bump for it, and `holds(vni, mac, owner, esi)` replaces the old single `winner`: `mac_mobility_recheck` never withdraws a local route on the holder's segment, and the frozen state still admits the segment's PEs. ESI 0 (single-homed) is never the same segment. `evpn_push_snapshot` sends `nos-fdbd` one held copy per `(VNI, MAC)` — the lowest remote VTEP — keeping fdbd's one-route-per-MAC invariant. Before, two PEs on one segment bumped each other's sequence, withdrew in turn and ended frozen as a duplicate. `nos-e2e evpn-dataplane`/`evpn-v6` assert neither PE logs `local mac mobility lost`/`duplicate mac detected` once both hold the CE's MAC.

There is deliberately **no withdraw**: a route disappearing from `evpn_adj_rib_in`/`evpn_local` doesn't erase what `MacMobility` remembers about its `(VNI, MAC)` — a sequence number only means anything relative to the last one seen, so forgetting on withdrawal would let a stale, lower-sequence re-announcement win a tie-break it shouldn't. `tick` instead expires an entry with no candidate at all for an hour (`EXPIRE`), bounding memory for a MAC that stops being advertised entirely. **Ceilings** (`ponytail:` in `mac_mobility.rs`): keyed by `(VNI, MAC)` only, not by broadcast domain — two different domains sharing one BGP instance with a coincidentally identical MAC and VNI isn't a real deployment scenario; no persistence across a `nos-bgpd` restart, like `damping`'s own per-session state; freeze auto-recovers after a quiet window rather than needing an administrative clear. Verified by `nos-e2e evpn-fdb`.

`BgpRequest::GetEvpnRoutesPage { after: Option<EvpnRouteCursor>, limit }` → `BgpEvent::EvpnRoutesPage { routes: Vec<EvpnRouteSummary>, next }` (`user`/`restd` only, like `GetSummary`; paged in #723, cursor = `(peer, route text)`, the old `GetEvpnRoutes` answers `BgpEvent::Error`) backs `nos-cli`'s `show bgp evpn` and `GET /v1/bgp/evpn`; `route` is the NLRI rendered by bgpd (`[2]:[65010:1]:[<esi>]:[0]:[48]:[<mac>]:[<ip>]:[<vni>]`) and extended communities are rendered `RT:65010:10000` / `encap:8`. Verified end to end by `nos-e2e evpn` against GoBGP (an independent implementation), which builds its own image the way `tools/bench-bgp.sh` does.

#### Origination and the `nos-fdbd` feed

`nos-bgpd` is deliberately dumb about EVPN: `nos-fdbd` (see [EVPN implementation notes](evpn-vxlan.md#implementation-notes-nos-fdbd)) resolves RD, Route Targets, VTEP next-hop and VNI and pushes fully formed routes (`BgpRequest::RedistributeMacs { domain, update }`, `Role::Fdbd` only, `nos_proto::EvpnRoute`); `rib/evpn_out.rs` only carries them. `BgpRib.evpn_local` holds them per domain (a `Full` replaces just that domain's — several domains feed one instance, unlike `nos-ribd` where table and instance are 1:1); `evpn_adj_rib_out` records what each peer was last told. Every change is a **per-key delta** (`announce_evpn`/`withdraw_evpn`, one NLRI per peer) and `peer_established` replays the whole set to a new peer. Only peers that negotiated AFI 25/SAFI 70 get them; the next-hop is the VTEP **verbatim** (never next-hop-self), our ASN is prepended toward eBGP, LOCAL_PREF set toward iBGP. `OutboundUpdate::{AnnounceEvpn, WithdrawEvpn}` are encoded by `fsm::outbound_update_to_message`. **Type-3 routes need the RFC 6514 PMSI Tunnel attribute** (`message::Pmsi`, ingress replication: VNI in the label field, tunnel id = the VTEP) — added to `PathAttributes` for that; it is decoded on receipt too (`EvpnRoute.pmsi_vni`). `ponytail:` EVPN bypasses export policy; the only best-path logic between a local and a received route for one `(VNI, MAC)` is RFC 7432 §15 MAC mobility (see below) — every other EVPN route type has none.

The reverse feed is `fdb_push_client.rs`: a change-driven feed (like `rib_push_client`) that pushes every received Type-1/2/3/4 route (`BgpRib::evpn_push_snapshot`; a Type-2 with an IP is `EvpnKey::MacIp`, without one `EvpnKey::Mac`; a Type-1 is `EvpnKey::EthernetAd` with `origin` = the BGP next hop, since its NLRI names no originator and two PEs' routes must stay apart; `nlri_of` gives a per-ES route MAX-ET and label 0 and a per-EVI route tag 0 and the VNI as its label) to the `nos-fdbd` of each domain whose `redistribute from mac to bgp` names this instance (`BgpRib.fdb_domains`, set by `reconcile.rs` from the config — it also subscribes to `DiffScope::BroadcastDomains` for that), one connection per domain, `Full` on connect, `Add`/`Remove` after. Route-Target filtering is fdbd's job, so bgpd needs no RT knowledge. The same module runs a second feed, `Feed::Tables`: every received **Type-5** (`EvpnKey::IpPrefix`, only the RFC 9136 §4.4.1 interface-less form — a route with a gateway IP or ESI overlay index is skipped with a `debug!`) goes to the `nos-ribd` of each routing table whose `evpn.bgp_instance` names this instance (`BgpRib.evpn_tables`, set by `reconcile.rs`), as `RibRequest::PushEvpnRoutes`; `SessionManager::evpn_feed_snapshot` splits the snapshot (`rib::evpn_feeds`) so `nos-fdbd` never sees a Type-5 and `nos-ribd` sees the Type-5s plus every RFC 9135 symmetric IRB MAC+IP (#188), which goes to both. A received Type-2 with an IP and a non-zero Label2 has it as `EvpnRoute.l3_vni` (RFC 9135 §5.2: zero means asymmetric); MAC mobility selection runs before the split, so a moved host reaches `nos-ribd` from the winning PE only. On origination `nlri_of` sends `l3_vni` as Label2 (`labels: [vni, l3_vni]`); a route gaining it is withdrawn and re-announced like any other NLRI change. Every send goes through `send_split` (`EvpnUpdate::split_with(evpn_push_budget())`): a `Full` over 4 MiB encoded goes as `FullPart`s closed by a `Full` (ribd/fdbd assemble, `nos-e2e evpn-l3-chunked`); `Add`/`Remove` stay one frame. Both feeds also wake on EOF of their write-only connection (and retry an unreachable consumer every 1s), so a restarted consumer gets a fresh `Full` at once. The other direction: `nos-ribd` pushes its IP-VRF's best routes as fully formed Type-5 routes (`BgpRequest::RedistributeEvpnPrefixes { table, update }`, `Role::Ribd` only); `evpn_local` is keyed by `EvpnSource::{Domain, Table}` (`apply_evpn_source`) so a domain and a table with one name never clobber each other (#724: a chunked `RedistributeMacs`/`RedistributeEvpnPrefixes` `Full` is staged per connection and per `EvpnSource` by `server.rs`'s `EvpnStaging` and reaches `apply_evpn_source` once, on the closing `Full`, since a lone part would withdraw the rest; log `assembled chunked evpn route snapshot source=domain:<d>|table:<t> routes=N parts=P`; a lost connection drops it), and `nlri_of` gives an `IpPrefix` no ESI, tag 0, a zero gateway of the prefix's family and the L3 VNI as label (see `docs/internals/rib.md`'s "EVPN IP-VRF"). `format_ext_community` renders the RFC 9135 Router's MAC as `rmac:aa:bb:cc:dd:ee:ff`, and an ESI Label community (RFC 7432 §7.5, whose flags octet carries the Single-Active bit) as `esi-label:single-active|all-active`.

### VPN-IPv4/IPv6 wire format (RFC 4364, RFC 4659, RFC 8277, #577)

- `vpn/nlri.rs` is the SAFI 128 codec; `MpReachNlri.vpn`/`MpUnreachNlri.vpn` hold `VpnNlri { labels, rd, prefix }` (`nlri`/`withdrawn` stay empty).
- NLRI layout: `length(bits) | labels (3 octets: label<<4 | S) | RD(8) | prefix`. The stack ends at the first S=1 (RFC 8277 section 2.3); a length that cannot hold labels + RD, a missing S=1, a prefix longer than the AFI allows, short octets, trailing bytes or an AFI other than 1/2 are `MalformedUpdate`, a session reset (RFC 7606 section 3(j): treat-as-withdraw needs a parsed NLRI). A wrong next-hop length resets too (section 7.11).
- Single label: the encoder always sends one label with S=1, so the Multiple Labels capability (code 8) is not advertised; the decoder still accepts a longer stack (`ponytail:` ceiling, `bgp/TODO.md`).
- Withdrawals: the label field is the fixed Compatibility value 0x800000 on send and ignored on receive (0x000000 and a real label decode the same), so `labels` is empty after decoding. Treat-as-withdraw of an announcement (bad ORIGIN, missing mandatory attribute) moves `vpn` into an unreach batch with labels cleared.
- Next hop: 8 zero octets (RD; a non-zero one is ignored) then the address: 12 (IPv4), 24 (IPv6), 48 (global + RD + link-local, link-local dropped); 4/16/32 without an RD are tolerated. On AFI 2 an IPv4-mapped address decodes to IPv4 and an IPv4 next hop is sent mapped (RFC 4659 section 3.2.1.2).
- ADD-PATH: `add_path_afis` is keyed by AFI only, so the SAFI 128 branches never consult it (a Path Identifier never precedes these NLRI); `vpn_decode_never_consults_add_path` guards it.
- Negotiation: `fsm::negotiate_safi` is shared with Flowspec (`negotiate_vpn` returns `[vpnv4, vpnv6]`, `RemoteInfo.negotiated_vpn`). `build_mp_capabilities` emits `MultiProtocol{1|2, 128}` and no Extended Next Hop. `fsm::is_vpn` names them.
- `split_update` halves `vpn` lists like the others.
- `vpn/ext_comm.rs`: `route_targets`/`sites_of_origin`/`is_route_target` over the `u64` extended communities (types 0x00/0x01/0x02), `rt(type, admin, assigned)` builds one; rendering stays `format_ext_community`.
- One UPDATE carries at most one `MP_REACH_NLRI` and one `MP_UNREACH_NLRI` (RFC 7606 section 3(g): a repeat resets the session). `UpdateMessage.mp_reach` is a `Vec`, and the encoder writes one attribute per entry, so build a single batch per UPDATE: every `OutboundUpdate` does.

### VPN Adj-RIB-In, selection and reflection (#578)

- Storage: `BgpRib.vpn_adj_rib_in: peer -> VpnKey<IpNet> -> VpnRoute { labels, route: RibRoute }`. `VpnKey<T> = (Rd, T)` lives in `vpn/mod.rs` (#574 uses `VpnKey<FlowSpec>`). The family follows the prefix (`rib::vpn_out::vpn_family`). Routes are held whatever their RTs: RFC 4364 section 4.3.5, different RDs never compete, so the key is the full (RD, prefix).
- Learning (`vpn_out::learn_vpn`, called at the end of `learn_announced`): the shared `base_route` plus the batch next hop goes through the peer-group `import_policy` (`apply_policy`, `this.prefix` = the customer prefix); reject drops a held copy. A batch of a family the session did not negotiate is ignored with a `warn!`. Withdrawals, treat-as-withdraw (the martian next-hop check covers `vpn` batches) and the RFC 4456 loop checks go through `drop_vpn`.
- Selection: `select_vpn(k)` runs `best_path` over every peer's copy and the local VRF export of the key (`vpn_local`, below) into `vpn_loc` (`(RouteOrigin, VpnRoute)`), no feasibility filter. Re-advertisement: `sync_vpn_to` diffs against `vpn_adj_rib_out` and calls `build_advertisement(.., Some((family, export_policy)))` (split horizon, RR, eBGP prepend, export policy, no OTC/RFC 8097 step), then sets the next hop: the received one for a reflected path (its label belongs to that PE), `PeerOutbox::local_addr` for a local export. `OutboundUpdate::{AnnounceVpn(AdvertisedVpn), WithdrawVpn(VpnKey)}`; lost ones are re-sent from the outbox backlog (`Backlog.vpns`, batched).
- GR and refresh: `gr::family_of`/`our_cap` include (1,128)/(2,128). `vpn_stale` is the twin of `stale`: `retain_as_stale` marks retained families, `begin_refresh_in` marks one family (`mark_vpn_stale`), `end_refresh_in`/`purge_stale` purge it (`purge_stale_vpn`); `resend_all` of a VPN family is `resend_vpn`; `send_route_refresh` asks for each negotiated VPN family too. Max-prefix counts them (`accepted_count`, scanned only for a limited family).
- Show: `BgpRequest::GetVpnRoutesPage { family, rd, after: Option<VpnRouteCursor>, limit }` -> `BgpEvent::VpnRoutesPage { routes: Vec<VpnRouteSummary>, next }` (`user`/`restd`, #723), sorted by peer, RD, prefix (`VpnRouteCursor { peer, rd: [u8; 8], prefix }`); `best` is the selected copy. The RD filter applies when the snapshot is built, so the connection's VPN snapshot remembers its `(family, rd)` and is rebuilt when a request asks for other ones. The old `GetVpnRoutes` answers `BgpEvent::Error`.
- Logs (e2e anchors): `address families negotiated peer=… families=[…]`; `vpn route learned peer=… family=vpnv4 rd=65001:1 prefix=… labels=[100] next_hop=…`; `vpn route withdrawn …`, `vpn route rejected by import policy …` (peer, family, rd, prefix); `vpn route advertised peer=… family=… rd=… prefix=… labels=[…] next_hop=…`; `vpn route advertisement withdrawn …` (peer, family, rd, prefix).

### VRF export (RFC 4364 section 4.3.2, #580)

- Transport: `nos-ribd` pushes `BgpRequest::RedistributeVpnPrefixes { table, update: VpnPrefixUpdate }` (`Role::Ribd` only), `Full`/`Add`/`Remove` of `VpnPrefix { rd, prefix, labels, ext_communities }`. No next hop on the wire. A `Full` over 4 MiB encoded arrives as `FullPart`s (#791), staged per connection and table by `server.rs`'s `VpnStaging` and applied once on the closing `Full` (a lone part would withdraw the rest); log `assembled chunked vpn export snapshot table=<t> routes=N parts=P instance=<i>`.
- Storage: `BgpRib.vpn_local: table -> VpnKey<IpNet> -> VpnRoute`, a `redistributed_route()` (`RouteOrigin::Local`) carrying the export RTs; per table, so one table's `Full` never clobbers another's. `apply_vpn_prefixes` re-selects every key it touched; an unchanged `Add` keeps its age. Two tables with one (RD, prefix): the first by name.
- Selection: a local export is one more `select_vpn` candidate; decision step 2 makes it beat a received copy of the same key.
- Advertisement: next-hop-self (`local_addr`) toward iBGP and eBGP alike, a peer without one is skipped; on a VPNv6 batch the codec sends an IPv4 address mapped. AS_PATH/LOCAL_PREF as unicast (`build_advertisement`), the peer-group export policy with `this.prefix` = the customer prefix. A label or RT change is a re-announce of the same key (implicit replace).
- GR: `select_vpn` updates `vpn_loc` but sends nothing while `deferring()`; the deferral's end (`initial_update` -> `announce_vpn_to`) sends the set. The VPN `Full` is not waited for (`redistribute_seen` counts only unicast redistribution).
- `show bgp vpnv4|vpnv6` lists received paths only, not local exports.

### VRF import (RFC 4364 section 4.3.2, #579)

- Config: `vpn::VrfSet::from_config(cfg, instance)` (`vpn/vrf.rs`) lists the tables whose `vpn.bgp_instance` is this instance, with RD, import and export RTs as `u64` extended communities. `reconcile.rs` builds it each resync (empty until the restart check is decided) and hands it to `SessionManager::set_vpn_vrfs` (`BgpRib.vpn_vrfs`).
- Matching, family-agnostic (the surface #574/#580 reuse): `VrfSet::import_targets(ext_communities)` is any-of between the route's RTs (`vpn::route_targets`) and each VRF's import set, no RT no import; `VrfSet::import_by_table::<T, R>(routes)` groups `(VpnKey<T>, ext communities, payload)` by table, a route landing in every matching table.
- Selection (`rib/vpn_import.rs`, `BgpRib::vpn_import_snapshot`): every VPN Adj-RIB-In path whose PE passes `next_hop_feasible` is a candidate in each matching VRF, RD stripped, so RDs compete there. `decision_cmp` picks the best per (table, prefix); candidates are sorted by RD and the position is the step-10 path id. With `maximum-paths` above 1, `decision::multipath_ties` (the filter unicast `multipath_next_hops` also uses: steps 1-7 equal, same neighbouring AS, RD ignored) adds the tying paths in decision order up to the cap; `VpnImport.paths` holds them as `(pe, labels, rd)` sorted by `(pe, labels)`, only an identical `(pe, labels)` pair collapsing. Install-only, like unicast: `select_vpn`/`vpn_out` (what is re-advertised) still picks one. A `maximum-paths` change re-runs the import because `set_maximum_paths` takes the shared RIB mutably, which bumps the push generation. `(None, None)` while deferring. Returns the underlay table (`owning_routing_table`) beside it.
- Push (`vpn_push_client.rs`, started in `main.rs`): a copy of `fdb_push_client`'s `Feed::Tables` loop (`ponytail:` merge when a third table feed appears). Each tick resolves every distinct PE with one `RibRequest::ResolveNextHop` to the underlay `nos-ribd` (a failed query keeps the last answers), withholds each next hop whose PE is unresolved (`debug!` `vpn route withheld, pe next hop unresolved in the underlay`) and the whole route only when none resolves (the others are pushed as a `VpnRoute` with fewer `paths`, an `Add`), then pushes `RibRequest::PushVpnRoutes` per VRF table: `Full` on connect, diffed `Add`/`Remove` after, both through `send_frames` (`VpnRouteUpdate::frames`, #715: a `Full` heavier than `VPN_PUSH_CHUNK` paths + routes goes as `FullPart`s closed by a `Full`; `last_sent` moves only once every frame is written, a failed write drops the connection and the reconnect resends a whole `Full`). A label or resolution change is an `Add`.
- Site of Origin (#582): `Vrf.soo` is the table's `vpn.site_of_origin` as a `u64` (`nos_proto::evpn_id::parse_soo`, the RT value with subtype 0x03). `import_targets` skips a VRF whose own SoO (`vpn::has_soo`) is on the route; `VrfSet::soo_blocked` lists those pairs, `BgpRib::vpn_soo_skipped` collects them over the Adj-RIB-In and `vpn_push_client::log_soo_skips` logs each once (`vpn route skipped by site of origin table=… rd=… prefix=… soo=…`, again if it clears and returns). Export is `nos-ribd`'s: `rib/src/vpn.rs::originated` appends the SoO to `VpnPrefix.ext_communities` beside the export RTs, so `nos-bgpd` carries it like any extended community.
- `ponytail:` snapshot-based, O(paths x VRFs) per push tick; an import's multipath set is as wide as `maximum-paths`. A `Connected` underlay hop resolves to the PE itself with no ifindex (#581 looks the device up).
- Logs (e2e anchors): `vpn route imported table=… prefix=… labels=[…] rd=… next_hop=<pe>` (one line per next hop), `vpn route unimported table=… prefix=…` (`info`), `vpn route import changed …` (`debug`), `sent initial vpn snapshot to nos-ribd table=… routes=…`.

### VPN reuse surface (#574)

What the L3VPN code (#573) leaves for VPN Flowspec (#574, SAFI 134) to build on:

- `vpn::VpnKey<T> = (Rd, T)` keys any VPN table; L3VPN uses `T = IpNet`, #574 uses `T = FlowSpec`. Selection is `select_vpn`/`vpn_loc` in `rib/vpn_out.rs`: learn through the peer-group policy, `best_path` over every peer's copy plus the local export, advertise next-hop-self for local and unchanged for reflected. `rib/vpn_out.rs` is the template for a SAFI 134 Adj-RIB-In, selection and reflection.
- `vpn::VrfSet` is the table -> (RD, import RTs, export RTs, SoO) map built from `nos_proto::Config` each resync; `import_targets`/`import_by_table::<T, R>` are family-agnostic (they never name an IP prefix), so #574 imports a `VpnKey<FlowSpec>` by the same RT rule and gets the Site of Origin check for free.
- `vpn/ext_comm.rs`: `route_targets`, `sites_of_origin`, `has_soo`, `rt`, `soo_from_rt`, `format_soo`; `nos_proto::evpn_id` parses the text forms. RPL reaches the same values through `rt()`/`soo()`/`rd()` and `this.bgp.rd` (`nos-rpl` keeps its own encoder; `vpn/ext_comm.rs`'s `rpl_literals_equal_the_config_parsers` pins it to `parse_rt`/`parse_rd`).
- Push: `vpn_push_client.rs` (bgpd -> a VRF's ribd) and `RedistributeVpnPrefixes` (ribd -> bgpd, `VpnPrefix { rd, prefix, labels, ext_communities }`) are the two directions. #574 adds a second payload next to them: the received rules per VRF, validated against that VRF's unicast table, and `nos-acld` receiving the table beside the rule.
- Log conventions: `vpn route learned|withdrawn|imported|unimported|advertised|skipped by site of origin`, fields `table`, `rd`, `prefix`, `labels`, `next_hop`, in that order.

Still #574's: SAFI 134 negotiation (`fsm::negotiate_safi` is shared), the per-VRF validation, and the acld push carrying the table.

### Policy hooks on VPN routes (#582)

- Import policy runs in `vpn_out::learn_batch` through `apply_policy(.., Some(rd))` when the path is stored, before VRF import by RT: an RT added there steers the route into other tables, a reject withdraws a held copy, and the stored and reflected path carries the edit.
- Export policy runs in `build_advertisement` (its `flow` tuple carries the policy and the RD) on every path sent, after ribd attached the RTs and the SoO.
- `to_policy_input(.., rd)` feeds `BgpInput.rd` (`u64::from_be_bytes` of the RD); every non-VPN caller passes `None`, and a route without an RD never equals `rd(..)`.

### Backup path

`BgpRib::recompute_and_propagate` also records, per prefix, the **runner-up** path's next hop in `backups` (`runner_up_next_hop`: `best_path` re-run over every candidate except paths sharing a next hop of the multipath set below — a backup with an installed next hop protects nothing). `push_snapshot` returns `(next_hops, backup)` (`Hops`), `rib_push_client` sends it as `BgpRoute.next_hops`/`backup_next_hop` (a set- or backup-only change is an `Add`), and `nos-ribd` installs the backup as a second, higher-metric kernel route. Verified by `nos-e2e bgp-multipath` (with `maximum-paths 1`, the sibling becomes `backup=true`).

### Multipath (#70)

`BgpInstance.maximum_paths` (1..=64, unset = 1; `set maximum-paths <n>`) makes `recompute_and_propagate` store, beside `backups`, the prefix's install set in `multipaths` (only when it has 2+ hops): `multipath_next_hops` takes `best`'s next hop plus every other peer-learned candidate tying with it on decision steps 1–7 (`multipath_cmp`, the prefix of `decision_cmp` that `best_path` uses) **and** sharing its neighbouring AS (strict, non-relaxed vendor default; no RFC defines multipath selection, RFC 2991/2992 only forwarding), deduplicated, picked in steps 8–10 order, capped, then sorted for a stable push diff. It is updated before the `unchanged` early return, so a sibling joining/leaving reaches `nos-ribd` through the push wake-up without touching `loc_rib`, the `loc-rib best path … updated` log or any advertisement — **only `best` is ever advertised**. `set_maximum_paths` (from `SessionManager::set_maximum_paths`, every resync) re-decides every Adj-RIB-In prefix on a change. `Local` routes never join (one wins step 2 and isn't pushed). `ponytail:` strict neighbour-AS only (a `multipath-relax` is a one-predicate change); a set change is a del+add in the kernel (see `docs/internals/rib.md`). Verified by `nos-e2e bgp-multipath`.

### Memory profiling

`main.rs`'s `--features dhat-heap` cargo feature swaps in the `dhat` global allocator and starts a `dhat::Profiler` for the whole process lifetime, writing a heap-profile report (`--profile-memory-out`, default `dhat-heap.json`) on any exit path (normal SIGINT/SIGTERM shutdown, or the early return while resolving `nos-configd`) — an ordinary local binding declared before `main`'s other `return`s, so Rust's own scope-exit drop writes the report with no extra signal-handling code. Off by default: a normal build pulls in no new dependency and pays no allocator overhead. Load the resulting file at https://nnethercote.github.io/dh_view/dh_view.html to see which call sites allocated how much/how often — this is the starting point for any memory-usage investigation, since `tools/bench-bgp.sh`'s external `/proc/<pid>/status` sampler only gives a peak-RSS number with no attribution.

Reachable through the watchdog with no watchdog code changes, via its existing opaque `--bgpd-arg` pass-through (same mechanism as `--configd-arg`/`--ribd-arg`): build the image with `docker build --build-arg CARGO_FEATURES=nos-bgp/dhat-heap -t nos .`, then run it with `--bgpd-arg --profile-memory-out=/var/lib/nos/bgpd/dhat-heap.json` appended to `nos-watchdogd` (e.g. `docker compose run --rm watchdog --bgpd-arg --profile-memory-out=/var/lib/nos/bgpd/dhat-heap.json`) — `/var/lib/nos` is the `nos-data` volume, so the report survives the container stopping and can be pulled out with `docker cp`. This has no `nos-e2e` phase: a heap-profile dump is a human-inspected artifact, not a protocol assertion grep-able from `tracing` log lines, unlike every other feature covered there. `tools/bench-bgp.sh`'s own `PROFILE_MEMORY=1` env var wires this same flag into its `nos`/`nos-quiet` DUT runs automatically — see "Performance" below.

### Per-peer outbox is bounded (#395)

- The RIB sends to a peer under its mutex, so each session's queue (`rib/outbox.rs`, `OUTBOX_CAPACITY` = 8192) is a bounded channel and the RIB only ever calls `OutboxTx::send` (`try_send`), never blocks. A peer that stops reading stalls `fsm::run`'s write, so without the bound the queue grew without limit.
- When the queue is full, an `Announce`/`Withdraw` is not queued; its prefix goes into a per-peer dirty set (memory bounded by the table, like Adj-RIB-Out). Dropped ADD-PATH withdraws also keep their path id, because `add_path_sent` has already forgotten it. `EndOfRib`/`RefreshMarker` stay as a small ordered list.
- Invariant: while a backlog exists every new item joins it, so nothing overtakes a lost item.
- Resync: `fsm::run` calls `BgpRib::drain_backlog` once the queue is empty (after each dequeued update, and on the `parked` wake-up). It re-evaluates the current Loc-RIB for up to `DRAIN_BATCH` dirty prefixes, `resync_prefix` sending a `Withdraw` for an ineligible prefix even if `adj_rib_out` does not list it (withdrawing an unknown route is legal), then `BORR` markers first and `EoR`/`EORR` markers after the last dirty prefix. Anything that overflows again just returns to the backlog.
- EVPN updates coalesce the same way (#764): a dropped `AnnounceEvpn`/`WithdrawEvpn` puts its NLRI in `Backlog.evpns`, and `drain_backlog` re-sends up to `DRAIN_BATCH` of them from `evpn_adj_rib_out` (the per-peer current state, updated at send time): `AnnounceEvpn` with the latest attributes if the NLRI is still there, else `WithdrawEvpn`. No backpressure on `nos-fdbd`/`nos-ribd` and no Cease: a 75 000-route Type-5 burst never flaps the session (`nos-e2e evpn-l3-chunked`).
- Logs, once per episode: `bgp: outbox full, coalescing` and `bgp: outbox backlog drained prefixes=<n>`.
- Not changed: `nos-logd` (already bounded by bytes, `LogStore::persist_queue_bytes`) and the `nos-ospfd`/`nos-ospfv3d` `LinkCommand` channels (fed by operator, BFD and neighbour-state events, not by a remote peer's read speed; a drop policy would risk losing commands that must be applied). `nos-fdbd`'s `watch_neigh` wake-up is a `channel(1)`: a pending wake absorbs the next.

### Performance

`tools/bench-bgp.sh` (see `docs/architecture/benchmark.md`) benchmarks this crate against GoBGP, BIRD and FRR on the same injected table, which is the only place the ceilings `rib.rs` documents get quantified rather than just noted: the single per-instance `Mutex<BgpRib>`, one prefix per outbound UPDATE (`OutboundUpdate` is per-prefix, so N prefixes to M peers means N×M framed writes where the others pack hundreds per PDU), the O(num_peers) `adj_rib_in` rescan per touched prefix in `recompute_and_propagate`, and the `info!` per learned route. Run it before and after anything that touches the RIB hot path, and with `RUST_LOG=info,nos_bgp::rib=warn` when the per-route logging would otherwise be what's being measured. `PROFILE_MEMORY=1 tools/bench-bgp.sh run nos-quiet <N>` (needs an image built with `CARGO_FEATURES=nos-bgp/dhat-heap`, see "Memory profiling" above) additionally captures a dhat heap-profile report to `target/bench-bgp/dhat-heap-<dut>-<N>.json` for the run, for attributing `peak_rss_mb` to actual call sites rather than just a number.

`RibRoute::as_path`/`cluster_list` are `Arc<Vec<_>>`, not plain owned `Vec`s — a dhat profile of the 4-peer/100k-route scenario showed `adj_rib_in`/`loc_rib` storage (`HashMap<IpNet, RibRoute>` growth) as 66% of peak RSS, driven by every candidate/storage clone (`recompute_and_propagate`'s candidate collection, `loc_rib` inserts, `handle_update`'s per-NLRI `..base_route.clone()`, `build_advertisement`'s policy-application clone) deep-copying these two lists even though RPL never mutates either in place (only `local_pref`/`med`/the three community lists are policy-settable). Sharing them via `Arc` turned those into refcount bumps; `build_advertisement`'s `Arc::make_mut` still pays for exactly one real copy when actually prepending an ASN/cluster-id — the one case where the content is genuinely different per destination peer. Communities stay plain `Vec`: `nos_rpl::vm::run`'s `Verdict::Accept` always hands back a freshly allocated `Vec` for all three community fields regardless of whether the script touched them, so `Arc`-wrapping them wouldn't save anything at the policy-application sites. Measured effect on the same 4-peer/100k benchmark: peak RSS 438→360MB, DUT CPU 41.6→31.8s, allocation count 16.5M→11.1M.

**IGP cost, decision step (d)** (RFC 4271 §9.1.2.2(d)): `igp_client.rs` polls the owning `nos-ribd` every 2s (`RibRequest::IgpCosts`, allowed to `bgpd`) for every non-BGP prefix's cost — `Static` 0, `Ospf` its SPF metric (`OspfRoute.metric`, kept in `Rib.ospf_metrics` beside the entries so a metric-only change never touches the kernel) — and hands it to `BgpRib::set_igp`, which re-decides every prefix on a change. `best_path` resolves each NEXT_HOP by longest-prefix match (lazily, only when steps 1-6 tie); a directly-connected one is a `Connected` route at cost 0. Verified by `ospf-spf` (`igp costs updated`).

**Next-hop feasibility** (RFC 4271 §9.1.2): `recompute_and_propagate` drops every peer-learned candidate whose next hop no entry of that same IGP table covers (`BgpRib::next_hop_feasible`, `igp_lookup` shared with the cost lookup) before `best_path` — so it is out of the decision process and the backup pick entirely, not merely tie-broken — logging `bgp: candidate excluded, next hop unresolvable`. Directly-connected next hops resolve because `nos-ribd` now holds every applied address as a `RouteSource::Connected` route (see `docs/internals/rib.md`). Two deliberate exceptions: nothing is excluded until the first `set_igp` (`igp_ready`, so a fresh start never blackholes what it just learned; the first poll always re-decides, even with an unchanged/empty table), and a route-server client's `propagate_add_path` view stays unfiltered (RFC 7947 transparency — whether *this* instance can resolve a next hop says nothing about whether the client can). `set_igp` re-decides every Adj-RIB-In prefix, not only the Loc-RIB, since an excluded candidate is precisely one an IGP change can admit. No link-local exception: `RibRoute.next_hop` can never be link-local (`decode_mp_reach` keeps only the global half of an RFC 2545 next hop — `mp_reach_accepts_global_plus_link_local_next_hop`). Verified by `nos-e2e next-hop-reachability`.

**Next-hop family guard** (#670): `next_hop_family_ok(prefix, nh, local_addr)` in `rib.rs`. `apply_verdict` ignores an `Addr` edit that breaks it (import checks with an assumed v6 session, so only v6 prefix + v4 literal is caught there); `build_advertisement` re-checks the final next hop, `self`/`Unchanged` fallbacks included, against the real `local_addr` and drops the route. VPN (`rd`) and Flowspec are exempt. Commit-time: `nos_rpl::unconditional_next_hop` + `bgp_peer_group::valid_next_hop_family`. Verified by `nos-e2e next-hop-reachability`.
